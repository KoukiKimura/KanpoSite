## 1. プロジェクト概要

### 1.1 プロジェクト名

漢方ブランド 公式サイト（KanpoSite）

### 1.2 プロジェクト背景

日本の伝統的な漢方・薬草文化を現代に伝えるブランドとして、商品販売だけでなく、ブランド背景、畑・栽培環境、古民家体験、読み物コンテンツを一体で発信する公式サイトを構築する。  
本サイトは単なる会社案内や単独ECではなく、ブランド体験全体を伝えるための情報発信基盤として位置付ける。

### 1.3 プロジェクト目的

- 漢方商品のオンライン販売を実現する
- ブランドのストーリー、理念、栽培背景を継続的に発信する
- 古民家・地域体験の認知向上と予約導線を構築する
- 商品SEO、記事SEO、地域SEOの3系統で検索流入を獲得する
- 初期リリースでは記事、FAQ、写真、古民家情報を静的データで管理し、将来的に運営者がコードを触らずに更新できる運用へ拡張する
- 将来的な多言語対応や会員機能追加に備えた拡張性を確保する

### 1.4 採用方針

| 領域 | 採用方針 |
|---|---|
| フロントエンド | `Next.js App Router` |
| CMS | `DecapCMS`（SEO対策専用。ユーザーによるコンテンツ更新はスコープ外。将来的に `microCMS` へ移行予定） |
| EC | `BASE`（商品ページは BASE 側で構築し、外部サイトとして別途設計書で管理。将来的に `Shopify` へ移行予定） |
| 商品取得 | オリジナルサイトから `BASE` 商品ページへの外部リンク遷移（サイト内カート・チェックアウトは持たない） |
| ホスティング | `ConoHa WING` |
| フォーム処理 | `ConoHa WING` + `PHP` + `ConoHa メール / SMTP`（`contact-api/` として `web/` とは別ディレクトリで管理。将来的に `Vercel Functions + Resend` へ移行可能な構成を維持する） |
| 出力方式 | `Next.js Static Export`（`output: 'export'`）。ISR / Server Actions は使用しない |
| 解析 | `Google Search Console`、`GA4` |
| 予約導線 | `Facebook` または外部予約サービスへのリンク |

### 1.5 対象サイトURL（予定）

- 本番: https://（ドメイン未定）
- 配信基盤: `ConoHa WING`

## 2. 想定ユーザー（ターゲット）

### 2.1 メインターゲット

| ターゲット区分 | 詳細 |
|---|---|
| 国内・健康意識の高い30〜60代女性 | 漢方・薬草・自然療法に関心があり、食や生活にこだわりを持つ層 |
| 国内・贈答需要層 | 両親・友人への贈り物として自然派・国産ブランド品を探している層 |

### 2.3 ユーザーの主な課題・ニーズ

- 信頼できる国産・自然由来の商品を探している
- 商品の原材料、栽培背景、世界観を理解したうえで購入したい
- 体験や滞在も含めてブランド全体を知りたい
- 検索で見つけた記事や施設情報から、商品や予約導線へ自然に移動したい

## 3. サイト構成方針

### 3.1 サイトの役割区分

本サイトは以下の3系統で構成する。

- ブランド・集客導線
  - ブランド紹介
  - コンセプト
  - 畑紹介
  - ストーリー
  - お知らせ
- 商品・販売導線
  - 商品一覧
  - 商品カテゴリ
  - 商品詳細
  - FAQ
  - 配送情報
  - 返品情報
- 古民家・地域導線
  - 古民家紹介
  - 体験案内
  - アクセス
  - 周辺導線
  - Facebook予約導線

### 3.2 データ責務の分離

| システム | 主な責務 |
|---|---|
| `BASE` | 商品主データ、価格、在庫、コレクション、決済・注文管理（外部サイトとして独立運用） |
| `DecapCMS` | SEO補助文言（`title`、`description`、OGP情報等）のみを管理。ユーザーによるコンテンツ更新機能は使用しない |
| `Next.js` | 画面描画、ルーティング、SEO制御、構造化データ、内部リンク、パンくず、表示テンプレート |

### 3.3 運用前提

- 商品主データは `BASE` を正本とし、`DecapCMS` に商品データを重複保持しない
- SEO補助情報（メタタイトル、ディスクリプション、OGP情報等）は `DecapCMS` で管理する
- コンテンツ更新（記事・FAQ・古民家情報等）は本フェーズのスコープ外とする
- 記事、お知らせ、FAQ、古民家情報、トップ特集等の本文データは初期リリースでは静的データで管理し、詳細な配置場所とデータ形式は基本設計書または詳細設計書で定める
- 商品表示用の静的データは `BASE` 正本から転記する表示コピーとして扱い、`BASE` 側の商品名、説明、価格、画像、公開状態を変更した場合は静的データも手動更新する
- 配送、返品、特定商取引法に基づく表記、EC利用規約に関わる購入条件は `BASE` 側を正本とし、オリジナルサイト側の固定ページは購入前説明用の要約として手動同期する
- 法務・配送・返品の固定ページには最終確認日を持たせ、`BASE` 側設定変更時に同期確認する
- 運営者の日常更新は `BASE` 管理画面で行う（商品、価格、在庫）
- 開発側は `Next.js` のレイアウト、表示ロジック、SEOロジックを管理する
- 将来的に `DecapCMS` を `microCMS` へ、`BASE` を `Shopify` へ移行できる設計とする

## 5. 機能要件

### 5.1 トップページ機能

- ブランドイメージを伝えるファーストビュー
- キャッチコピー、ブランドメッセージ、主要導線の配置
- 注目商品、新着商品、季節特集の表示
- ストーリー、お知らせ、畑、古民家への導線表示
- 静的データで管理する特集枠、バナー、写真の表示（将来的にCMS更新へ移行）
- 商品ページ、読み物ページ、古民家ページへの内部リンク最適化

### 5.2 商品販売機能

#### 商品一覧・カテゴリ

- オリジナルサイト上で商品情報（商品名、説明、価格目安、サムネイル等）を表示する
- 商品データは静的ファイルで管理し、将来的に `Shopify Storefront API` へ切り替えられる設計とする
- 静的商品データは `BASE` の商品情報を転記した表示コピーとし、`BASE` 側変更時の手動同期手順を基本設計書で定める
- カテゴリ別ページを持ち、一覧ページから遷移できるようにする
- 絞り込み・並び順のUIを提供する。絞り込み軸の基本方針は以下とする
  - カテゴリ: 静的カテゴリ定義を基準とする（将来的に `Shopify` コレクションへ移行）
  - 並び順: 新着順・価格昇順・価格降順を提供する。詳細な選択肢は基本設計書で定める

#### 商品詳細

- 商品名、短い説明、詳細説明、価格目安、サムネイルを表示する
- 商品画像を複数枚表示する
- 原材料、飲み方、注意事項、FAQを表示する
- 関連商品を表示する
- 初期リリースでは在庫状況をオリジナルサイト上で表示しない。正確な価格・在庫・購入可否は `BASE` 商品ページを正本とする
- `BASE` 商品ページへの外部リンク（「BASE で購入する」等のボタン）を設ける
- `Product` 構造化データ出力に必要な項目を保持する。`Offer` は静的データで価格整合性を担保できる商品に限って出力し、在庫状況は出力しない

#### 購買導線

- 商品詳細から `BASE` の該当商品ページへ外部リンクで遷移できること
- 決済、在庫、注文管理は `BASE` に委譲すること（外部サイトとして独立運用）
- サイト内でのカート・チェックアウト機能は実装しないこと
- 将来的に `BASE` から `Shopify` へ移行する際は、リンク先 URL とデータ取得元を切り替えるだけで対応できる設計とする

### 5.3 ブランド・コンテンツ機能

#### ブランド紹介・コンセプト

- ブランド紹介ページとコンセプトページを分離する
- ブランドの背景、理念、こだわり、代表メッセージを掲載する
- 画像と文章は初期リリースでは静的データで管理し、将来的にCMSで更新できるようにする

#### 畑紹介

- 畑・農場の紹介文と写真ギャラリーを表示する
- 栽培している素材、季節ごとの様子、こだわりを掲載する
- 地図や所在地情報を表示する

#### ストーリー・お知らせ

- `stories` と `news` を分けて運用する
- 一覧と詳細ページを持つ
- ストーリー詳細では関連商品や古民家ページへの導線を表示する
- SEO用のタイトル、ディスクリプション、サムネイル画像を管理できるようにする

#### FAQ

- 独立した `/faq` ページを設ける
- 商品、配送、古民家、問い合わせなどのFAQを掲載できるようにする

### 5.4 古民家・地域訴求機能

- 古民家紹介、アクセス、体験案内をページ分割して提供する
- 施設名、写真、所在地、アクセス、駐車場、予約方法、周辺案内を掲載する
- 体験内容、過ごし方、FAQを掲載する
- Facebookまたは外部予約サービスへのリンクを `/kominka` および `/kominka/experience` に掲載する
- 予約導線は独立ページではなく、古民家関連ページ内の外部リンクとして提供する
- `LocalBusiness` または `LodgingBusiness` 系構造化データ出力を想定した情報を保持する

### 5.5 お問い合わせ・法務機能

- 問い合わせフォームを提供する
- フォームには問い合わせ種別、氏名、メールアドレス、本文を含める
- フォームの入力バリデーションは以下を基本方針とする。詳細は基本設計書で定める
  - 問い合わせ種別、氏名、メールアドレス、本文は必須項目とする
  - メールアドレスは形式検証を行う
  - 本文は最大 1,000 文字を上限とする
  - 電話番号フィールドは任意項目として設ける
- フォーム送信は外部フォームサービスまたは別途 API 層経由で処理する（Static Export 制約のためサイト内サーバーサイド API は使用不可）
- 問い合わせ内容はメール通知または問い合わせ管理基盤へ連携できること
- 使用する送信サービス、API 実装方式は基本設計書で定める
- 初期リリースの問い合わせ通知先は環境変数または PHP API 側設定を正本とし、`DecapCMS` では管理しない
- フォーム送信 API にはスパム対策を適用する
- 初期リリースでは `honeypot`、送信頻度制御、許可オリジン検証等を基本とし、必要に応じて外部 CAPTCHA を追加できる構成とする
- 問い合わせログと rate-limit 情報は公開Webルート外に保存し、本文保存有無、保存期間、ローテーション、ファイル権限は基本設計書で定める
- rate-limit 用のIPアドレス、User-Agent等は必要最小限で保持し、目的外利用しない
- API エラー時の画面表示やログには、個人情報、内部パス、シークレットを出力しない
- 配送情報、返品情報、特商法表記、プライバシーポリシー、利用規約を独立ページとして設ける
- 配送情報、返品情報、特商法表記、利用規約のEC運用に関わる内容は `BASE` 側を正本とし、サイト側固定ページは要約と導線を掲載する
- プライバシーポリシーには問い合わせフォーム、Cookie、GA4等のアクセス解析に関する取り扱いを含める

### 5.6 CMS・外部連携機能

- `DecapCMS` の設定を実装する（SEO補助情報の管理に限定。コンテンツ編集機能は使用しない）
- `DecapCMS` は Git リポジトリベースで動作し、SEOメタ情報の更新を Webhook または手動ビルドでサイトへ反映する
- `DecapCMS` 管理画面は `/admin/` 配下に配置する方針とし、認証済みユーザーのみが利用できるようにする
- `DecapCMS` の Git backend、認証方式、編集可能ユーザー、更新先ブランチ、レビュー有無、手動ビルド手順は基本設計書で定める
- `DecapCMS` 更新後の再ビルドは GitHub Actions の push / workflow_dispatch を基本とし、Webhook を使う場合はシークレット検証を必須とする
- `BASE` との連携はサイト内からの外部リンクのみ。`BASE` API は使用しない
- SEO設定ファイルの欠落、構文不正、必須項目不足がある場合のビルド時エラーハンドリング方針は基本設計書で定める。本番サイトは直前のビルド済みファイルが維持される
- 初期リリースでは下書き確認専用の `preview/` 別アプリは構築せず、`ConoHa WING Staging` で静的表示、SEO補助情報、BASE外部リンクの反映を確認する。`preview/` 別アプリは将来 `microCMS` 移行時に再検討する
- 環境変数で各種トークン、ドメインを管理する
- 将来的に `DecapCMS` を `microCMS` へ、`BASE` を `Shopify` へ移行する際の切替方針を設計書で定める

### 5.7 共通機能

- レスポンシブデザイン
- グローバルナビゲーション
- フッター
- パンくずリスト
- 404ページ
- OGP設定
- サイトマップ生成
- robots.txt 設定

## 6. コンテンツ・データ要件

### 6.1 `DecapCMS` で管理するSEO情報

`DecapCMS` はSEO対策専用として使用し、ユーザーによるコンテンツ更新機能はスコープ外とする。
将来的に `microCMS` へ移行することを前提とした設計とする。

管理対象のSEO補助情報は以下のとおり。

- ページごとの `seoTitle`
- ページごとの `seoDescription`
- OGP画像（ページ共通・個別）
- `canonical` URL の補助情報
- サイト共通設定（サイト名、デフォルトOGP画像、Organization構造化データ用情報等）

### 6.2 `BASE` で管理する主なデータ（外部サイト）

以下のデータは `BASE` 側で管理する。オリジナルサイトからは商品ページへの外部リンクで遷移し、購入・決済処理はすべて `BASE` に委譲する。
`BASE` の設計・運用方針は別途設計書で管理する。

- 商品
- 商品画像
- 商品カテゴリ
- 価格
- 在庫
- バリエーション
- 決済・注文設定
- 配送設定
- 返品条件、特定商取引法に基づく表記、EC利用規約に関わる購入条件

### 6.3 商品ページで必要な項目

以下の項目を商品詳細ページに表示する。各項目の主データソースと実装方針を示す。

| 表示項目 | 主データソース | データ項目 / 実装方針 | 補足 |
|---|---|---|---|
| 商品名 | 静的データ（将来: Shopify `title`） | 静的ファイルで管理 | Shopify 移行時はフィールド切替 |
| 短い説明 | 静的データ（将来: Shopify `metafields.details.short_description`） | 静的ファイルで管理 | Shopify 移行時はフィールド切替 |
| 詳細説明 | 静的データ（将来: Shopify `descriptionHtml`） | 静的ファイルで管理 | Shopify 移行時はフィールド切替 |
| 価格目安 | 静的データ（将来: Shopify `priceRange.minVariantPrice`） | 静的ファイルで管理 | 初期は表示コピー。正確な販売価格はBASE商品ページを正本とする |
| 内容量 | 静的データ（将来: Shopify `metafields.details.volume`） | 静的ファイルで管理 | Shopify 移行時はフィールド切替 |
| 原材料 | 静的データ（将来: Shopify `metafields.details.ingredients`） | 静的ファイルで管理 | Shopify 移行時はフィールド切替 |
| 飲み方 | 静的データ（将来: Shopify `metafields.details.how_to_use`） | 静的ファイルで管理 | Shopify 移行時はフィールド切替 |
| 注意事項 | 静的データ（将来: Shopify `metafields.details.caution`） | 静的ファイルで管理 | Shopify 移行時はフィールド切替 |
| FAQ | 静的データ（将来: microCMS） | 静的ファイルで商品 slug と紐付けて管理 | microCMS 移行時はコンテンツ型を参照 |
| 画像複数枚 | 静的データ（将来: Shopify `images`） | 静的ファイルで管理 | Shopify 移行時はフィールド切替 |
| 関連商品 | 静的データ（将来: Shopify `metafields.details.related_products`） | 静的ファイルで管理 | Shopify 移行時は実装方式を基本設計書で定める |
| BASE 商品ページ URL | 静的データ | 商品ごとに BASE の商品ページ URL を保持する | BASE → Shopify 移行時はカート追加導線へ変更 |
| 最終確認日 | 静的データ | `lastVerifiedAt` として保持 | `BASE` 側と静的データの同期確認日 |

### 6.4 固定法務ページで必要な項目

配送、返品、特定商取引法に基づく表記、利用規約のEC運用に関わる内容は `BASE` 側を正本とする。オリジナルサイト側の固定ページは購入前説明用の要約とし、`BASE` 側設定と差異が出ないように手動同期する。

| 表示項目 | 主データソース | 実装方針 | 補足 |
|---|---|---|---|
| 配送方法・送料・配送条件 | `BASE` | 固定ページに要約を掲載 | `BASE` 側変更時に手動同期 |
| 返品・交換条件 | `BASE` | 固定ページに要約を掲載 | `BASE` 側変更時に手動同期 |
| 特定商取引法に基づく表記 | `BASE` / 提供原稿 | 固定ページに掲載 | 販売者情報、連絡先、販売条件の確認責任を定める |
| 利用規約 | `BASE` / 提供原稿 | 固定ページに掲載 | EC運用条件と矛盾しない内容にする |
| 最終確認日 | 静的データ | `lastVerifiedAt` として保持 | 法務固定ページと `BASE` 側設定の同期確認日 |

### 6.5 静的データとSEO補助情報

記事、お知らせ、FAQ、古民家情報、トップ特集等の本文データは初期リリースでは静的ファイルで管理する。将来的に `microCMS` へ移行する際は、同等のコンテンツ型へ切り替えられる構成とする。静的データの配置場所、ファイル形式、必須項目は基本設計書または詳細設計書で定める。

静的データ側で管理する主な識別・公開情報は以下のとおり。

- `slug`
- 公開日
- 更新日
- 最終確認日

`DecapCMS` で管理するSEO補助情報は以下のとおり。

- `seoTitle`
- `seoDescription`
- OGP画像
- OGP画像の代替テキスト
- `canonical` URL

### 6.6 `DecapCMS` 設定ファイル方針

`DecapCMS` はSEO補助情報のみを管理する。詳細なフィールド定義（型、必須可否）は「サイト詳細設計書.md」で別途定める。
将来的に `microCMS` へ移行する際のコンテンツ型は参考として以下に記載する。

管理対象のSEO設定の方向性は以下のとおり。

| 設定型 | 主な管理フィールド | 備考 |
|---|---|---|
| `seo_page` | `path`（対象パス）, `seoTitle`, `seoDescription`, `ogpImage`, `canonical`（任意） | ページごとのSEO情報 |
| `site_settings` | `siteName`, `siteDescription`, `ogpDefaultImage`, `logo`, `organizationName`, `organizationUrl`, `sameAs`, `socialLinks` | サイト共通設定および `Organization` 構造化データ用情報 |

将来的に `microCMS` へ移行する際のコンテンツ型（参考）:

| コンテンツ型 | 主な必須フィールド |
|---|---|
| `story` | `title`, `slug`, `body`（リッチテキスト）, `publishedAt`, `seoTitle`, `seoDescription`, `ogpImage` |
| `news` | `title`, `slug`, `body`（リッチテキスト）, `publishedAt` |
| `faq` | `question`, `answer`, `category`（商品 / 配送 / 古民家 / その他）, `relatedProductSlug`（任意） |
| `farm_page` | `title`, `body`（リッチテキスト）, `images`（複数） |
| `kominka_page` | `name`, `description`, `images`（複数）, `address`, `reservationUrl` |
| `kominka_access` | `address`, `mapEmbedUrl`, `parking`, `accessNote` |
| `kominka_experience` | `title`, `body`（リッチテキスト）, `images`（複数）, `reservationUrl` |
| `top_feature` | `title`, `image`, `linkUrl`, `publishedAt`, `expiresAt`（任意） |
| `site_settings`（完全版） | `siteName`, `siteDescription`, `homeHeroTitle`, `homeHeroLead`, `homeHeroImage`, `homeIntroText`, `ogpDefaultImage`, `logo`, `organizationName`, `organizationUrl`, `sameAs`, `contactEmail`, `socialLinks` |

## 7. SEO要件

### 7.1 共通SEO要件

- 全ページに `title`、`description`、`canonical` を設定する
- OGPタグを設定する
- パンくずを構造化データを含めて出力する
- `sitemap.xml` を生成する
- `robots.txt` を設定する
- 内部リンクをトップ、記事、商品、古民家間で整理する
- 構造化データの出力対象ページと型の方針は以下とする。詳細なスキーマ設計は基本設計書で定める

| 対象ページ | 構造化データ型 |
|---|---|
| 全ページ共通 | `WebSite`、`Organization` |
| 全ページ（パンくず） | `BreadcrumbList` |
| 商品詳細 | `Product`（`Offer` は価格整合性を担保できる商品に限る） |
| ストーリー詳細 | `Article` |
| FAQページ | `FAQPage` |
| 古民家関連ページ | `LodgingBusiness`（宿泊を伴う場合）または `LocalBusiness`（日帰り体験のみの場合）。基本設計書で確定 |

### 7.2 商品SEO要件

- 商品詳細ページに `Product` 構造化データを出力する。`Offer` は静的データで価格整合性を担保できる商品に限って出力する
- 商品名、価格目安、画像、説明を検索エンジンが理解しやすい形で表示する
- 初期リリースでは在庫状況をオリジナルサイト上で表示せず、構造化データにも `availability` を出力しない
- 商品カテゴリページをインデックス対象とする
- 配送情報と返品情報への導線を商品詳細から明示する

### 7.3 記事SEO要件

- ストーリー詳細に `Article` 構造化データを出力する
- 公開日、更新日、著者または運営主体を表示できるようにする
- 関連商品、関連古民家ページへの内部リンクを設ける

### 7.4 古民家・地域SEO要件

- 古民家ページに構造化データを出力できるようにする。宿泊を伴う場合は `LodgingBusiness`、日帰り体験のみの場合は `LocalBusiness` を基本とし、詳細は基本設計書で確定する
- 施設名、住所、地図、画像、予約導線を明示する
- アクセスページ、体験ページを独立させて地域検索ニーズに対応する

### 7.5 画像SEO要件

- 画像には説明的なファイル名を付与する
- すべての主要画像に `alt` テキストを設定する
- 画像周辺に文脈となるテキストやキャプションを配置できる構成にする
- Static Export のため `next/image` の自動最適化（Vercel Image Optimization）は使用しない
- 商品画像は静的ファイルまたは `BASE` リンク先で表示する（将来的に `Shopify` CDN の画像変換機能を活用）
- SEO補助情報として使用する OGP 画像は `DecapCMS` で管理し、WebP 形式を優先して登録する
- 画像最適化の具体的な実装方針は基本設計書で定める

## 8. 非機能要件

### 8.1 パフォーマンス要件

| 項目 | 目標値 |
|---|---|
| LCP | 2.5秒以内 |
| FCP | 1.8秒以内 |
| CLS | 0.1以下 |
| Lighthouse Performance | 85点以上 |
| Lighthouse SEO | 95点以上 |

### 8.2 セキュリティ要件

- HTTPS 常時SSLとする
- フォーム送信にはスパム対策を適用する（セクション 5.5 参照）
- フォーム送信 API エンドポイントには IP ベースまたは同等の送信頻度制御を実装すること
- 問い合わせログと rate-limit 情報は公開Webルート外に保存し、保存期間、削除、ローテーション、ファイル権限を管理すること
- 問い合わせログに本文やメールアドレスを保存する場合は、障害調査に必要な最小範囲に限定すること
- `BASE` の決済情報をサイト側で保持しない（決済は `BASE` に委譲）。将来的に `Shopify` へ移行する場合も決済情報はサイト側で保持しない
- APIキー、アクセストークン、Webhookシークレットは環境変数で管理する
- 公開不要なトークンを `NEXT_PUBLIC_` 付きで公開しない
- 依存パッケージを継続的に更新する
- セキュリティヘッダー（`X-Frame-Options`、`X-Content-Type-Options`、`Referrer-Policy` 等）の設定方針は基本設計書で定める

### 8.3 アクセシビリティ要件

- `WCAG 2.1 AA` 準拠を目標とする
- キーボード操作で主要導線に到達できること
- スクリーンリーダー利用を考慮したラベル付けを行うこと
- テキストコントラスト比は 4.5:1 以上を目標とする
- フォーム、画像、リンクに適切な補助情報を付与すること

### 8.4 ブラウザ・デバイス対応

| 対象 | 詳細 |
|---|---|
| モバイル | iOS Safari / Android Chrome の最新2バージョン |
| PCブラウザ | Chrome / Firefox / Safari / Edge の最新2バージョン |
| 画面サイズ | 375px から 1920px を想定 |

### 8.5 インフラ・運用要件

- 配信基盤は `ConoHa WING` を前提とし、`Next.js Static Export` によるビルド済み静的ファイルをデプロイする
- `DecapCMS` の更新時は Webhook または手動ビルドをトリガーとして再ビルド + デプロイを実行する
- `DecapCMS` 更新の本番反映は GitHub Actions を基本とし、ステージングと本番を `DEPLOY_ENV` 等で出し分ける
- フェーズ4ではローカルビルドまたは静的成果物でSEO補助情報・静的データの反映を確認し、ステージング反映確認は問い合わせAPIと合わせてフェーズ5で実施する
- `BASE` は外部リンクのみの連携のため、Webhook による自動再ビルドは不要（将来的に `Shopify` 移行時に整備）
- 初期リリースのステージング確認は `ConoHa WING Staging` を基本とし、ブランチデプロイ等の代替手段を含む詳細は基本設計書で定める
- `Google Search Console` と `GA4` を導入できること
- GA4 で計測する主要コンバージョンイベント（商品閲覧、BASE購入導線クリック、問い合わせ送信、古民家予約リンククリック等）の設計は基本設計書で定める
