**評価: B（概ね良好。ただし重大な技術的問題1件を含む複数の修正が必要）**

要件定義書のバージョン 1.1.0 は、`CMS_Shopifyとの併用案.txt` の提案内容を大きく反映しており、以前の「静的サイト + 将来CMS拡張」方針からの大幅な改善が確認できる。アーキテクチャ方針、データ責務分離、SEO要件、フェーズ管理の記述は全体として整合している。

ただし、ルーティング設計に**本番実装で必ずエラーになる重大な矛盾**が1件存在し、その他複数の不足・曖昧さが確認された。ステータスが「ドラフト」のまま運用には進められない状態である。

## 指摘一覧

### 🔴 Critical（実装に直接影響する重大な問題）

#### [C-01] P11 と P12 のルーティングが Next.js App Router 上で競合する

**該当箇所**: セクション 4「必要ページ一覧」、セクション 10「制約・前提条件」

**問題内容**:

| ページID | パス定義 |
|---|---|
| P11 | `/products/[category]` |
| P12 | `/products/[slug]` |

Next.js App Router では、同一階層に `[category]` と `[slug]` という別名の動的セグメントを同時に定義することはできない。実装すると以下のどちらかにしかならない。

- `app/products/[category]/page.tsx` を作れば、`[slug]` は同じルートに吸収される
- 両方を作ろうとすると、ビルドエラーまたは意図しない動作になる

**修正案**:

以下のいずれかに変更が必要。

```
案A: カテゴリページにプレフィックスを付与
  /products/category/[category]    → P11 商品カテゴリ一覧
  /products/[slug]                 → P12 商品詳細

案B: 既存の Web 実装に寄せる形
  /products?category=[category]    → P11 クエリパラメータ方式（SEO効果は下がる）
  /products/[slug]                 → P12 商品詳細

案C: Shopify collection handle と product handle を使って catch-all で分岐
  /products/[[...slug]]/page.tsx  → ルーティングロジックで判別（実装複雑度が上がる）
```

推奨は**案A**。SEO観点で独立URLを維持でき、実装も明快。

### 🟠 Major（リリース前に必ず対処が必要な問題）

#### [M-01] 利用規約ページ（/terms）が要件定義書に存在しない

**該当箇所**: セクション 4「必要ページ一覧」、セクション 10「制約・前提条件」

**問題内容**:  
EC サイトにおいて利用規約は法的・運用上の必須ページだが、P01〜P21 のページ一覧に `利用規約` が含まれていない。また、セクション 10 の正規ルーティング一覧にも `/terms` が記載されていない。

現状の `web` 実装には `/terms` が存在しており、要件定義書と実装の間で矛盾が生じている。

**修正案**:  
ページ一覧に以下を追加する。

| ページID | パス | ページ名 | 主データ | 優先度 |
|---|---|---|---|---|
| P22 | `/terms` | 利用規約 | 固定 | 必須 |

セクション 10 の正規ルーティング一覧にも `/terms` を追加する。

#### [M-02] P17「予約導線ページ」の設計方針が不明確

**該当箇所**: セクション 4 P17

**問題内容**:  
P17 のパスが `/facebook-reservation または外部URL` と記載されており、以下の点が曖昧。

1. これは Next.js 上に `page.tsx` を作るページなのか、`/kominka` からの外部リンクなのかが不明
2. `/facebook-reservation` というルートを独立して持つ必要性がない可能性がある
3. `実装差異調査結果.md` では「Facebookリンクはプレースホルダーのみ」と指摘されており、ページとして実装する前提が現状では空になっている

**修正案**:  
ページとして存在させる場合、以下の点を明記する。
- 実装方式（リダイレクトページ or テキストリンクのみ）
- URL が確定するまでは「準備中」表示とするか非公開とするかの運用方針
- URL が確定しない場合は P17 を削除し、`/kominka` の本文内リンクとして処理する

#### [M-03] 商品詳細の Shopify フィールドマッピングが未定義

**該当箇所**: セクション 6.3「商品ページで必要な項目」

**問題内容**:  
商品詳細ページに必要な項目（原材料、飲み方、注意事項、FAQ など）が列挙されているが、これらを Shopify のどのフィールドに格納するかが定義されていない。Shopify の標準フィールドでは `description` と `tags` のみであり、「原材料」「飲み方」等は **Shopify メタフィールド** として別途定義が必要。

このマッピングが未定義のまま実装に進むと、Storefront API クエリの設計が後付けになる。

**修正案**:  
セクション 6.3 または別紙として、以下を定義する。

| 表示項目 | Shopify フィールド / メタフィールド namespace | 補足 |
|---|---|---|
| 商品名 | `title` | 標準フィールド |
| 短い説明 | `description` | 標準フィールド（短縮版として利用） |
| 詳細説明 | `descriptionHtml` | 標準フィールド |
| 価格 | `priceRange.minVariantPrice` | 標準フィールド |
| 在庫状況 | `availableForSale` | 標準フィールド |
| 内容量 | `metafields.details.volume` | メタフィールド（要定義） |
| 原材料 | `metafields.details.ingredients` | メタフィールド（要定義） |
| 飲み方 | `metafields.details.how_to_use` | メタフィールド（要定義） |
| 注意事項 | `metafields.details.caution` | メタフィールド（要定義） |
| FAQ | `metafields.details.faq` | メタフィールドまたは CMS 管理の選択 |

---

#### [M-04] お問い合わせフォームのバックエンド処理方針が未定義

**該当箇所**: セクション 5.5「お問い合わせ・法務機能」、セクション 8.2「セキュリティ要件」

**問題内容**:  
「reCAPTCHA v3 等のスパム対策を適用する」と記載があるが、以下が未定義。

1. フォーム送信後のバックエンド処理方法（Vercel Functions / 外部サービス / メール転送サービス）
2. メール送信に使うサービス（SendGrid / Resend / AWS SES 等）
3. API エンドポイント設計（`/api/contact` 等）

現状の `web` 実装では送信処理が存在せず、クライアント側の state 操作のみで完了表示になっている（`実装差異調査結果.md` より）。

**修正案**:  
以下のいずれかを決定し要件定義書に記載する。

- `Vercel Functions` + `Resend`（または `SendGrid`）でメール送信
- `Formspree` / `Netlify Forms` 等の外部フォームサービスへ委譲
- `Shopify` お問い合わせフォームへリダイレクト

### 🟡 Minor（記述の精度・整合性に関する問題）

#### [m-01] セクション 10 の正規ルーティング一覧が不完全

**該当箇所**: セクション 10「制約・前提条件」

**問題内容**:  
セクション 10 の正規ルーティング一覧には P01〜P21 のうち一部しか記載されていない。`/`, `/about`, `/concept`, `/faq`, `/contact`, `/news`, `/facebook-reservation`, `/terms`（M-01 参照）が抜けており、「ルーティングはこれを正規とする」という制約として機能していない。

**修正案**:  
セクション 4 のページ一覧（P01〜P22）と完全に一致する正規ルート一覧をセクション 10 に記載する。

#### [m-02] CMS スキーマ定義（microCMS コンテンツ型）への言及がない

**該当箇所**: セクション 6.1「microCMS で管理する主なコンテンツ」

**問題内容**:  
管理するコンテンツ種別は列挙されているが、microCMS 上のコンテンツ型（APIスキーマ）の定義方針について記述がない。`実装差異調査結果.md` では「`lib/microcms`, `lib/shopify` の層分離を前提にしている」と指摘されているが、要件定義書のレベルで型定義の方針が示されていないと設計書フェーズで曖昧さが残る。

**修正案**:  
各コンテンツに必要なフィールド定義は「サイト詳細設計書.md」で別途定めることを明記するか、本ドキュメントに最低限の必須フィールドを記載する。

#### [m-03] ステータスが「ドラフト」のまま

**該当箇所**: ドキュメントヘッダー

**問題内容**:  
バージョン 1.1.0 であるが、ステータスが「ドラフト」のまま。本ドキュメントを基準に設計・実装を進める場合、承認ステータスの定義と承認フローが必要。

**修正案**:  
レビュー指摘事項を反映し、関係者の合意を得た上でステータスを「承認済み」に変更する。

---

#### [m-04] 非機能要件のセキュリティ要件に API レート制限の記述がない

**該当箇所**: セクション 8.2「セキュリティ要件」

**問題内容**:  
お問い合わせフォームの API エンドポイントに対するレート制限（Rate Limiting）の要件が記載されていない。reCAPTCHA のみでは bot による大量送信を完全には防ぎきれない。

**修正案**:  
以下を追加する。  
「フォーム送信 API エンドポイントには IP ベースのレート制限を実装すること（Vercel の Edge Middleware または外部サービスを利用）。」
