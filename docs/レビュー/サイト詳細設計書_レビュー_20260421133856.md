## 指摘事項

### Critical-01: `contact-api` が `microCMS site_settings.contactEmail` を取得できる前提になっているのに、接続情報が定義されていない

**対象箇所**

`docs/サイト設計/サイト詳細設計書.md:21`  
`docs/サイト設計/サイト詳細設計書.md:287`  
`docs/サイト設計/サイト詳細設計書.md:482`  
`docs/サイト設計/サイト詳細設計書.md:747`  
`docs/サイト設計/サイト詳細設計書.md:756`

**内容**

詳細設計書は「問い合わせ通知先の正本は `microCMS` の `site_settings.contactEmail`」という前提で統一されており、問い合わせ送信フローでも `contact-api/` が送信時に `microCMS site_settings.contactEmail` を取得する設計になっている。

しかし `11.3 contact-api/` の環境変数一覧には、`microCMS` へアクセスするための `MICROCMS_SERVICE_DOMAIN` や API キー、あるいは問い合わせ通知先取得専用の read-only 認証情報が存在しない。これでは `contact-api/` 単体では通知先を取得できず、正本が `microCMS` であるという前提を実装できない。

**推奨対応**

`contact-api/` 用に以下のいずれかを明記する。

- `MICROCMS_SERVICE_DOMAIN` と `MICROCMS_API_KEY` を `contact-api/` 側にも持たせる
- 問い合わせ通知先取得専用の read-only API キーを別名で定義する
- `contact-api/` は `microCMS` を直接読まず、別の設定ファイルやデプロイ時注入値を正本にする

現行方針を維持するなら、`contact-api/` が `microCMS` を直接読む設計を環境変数まで落とし切るべき。

### Major-01: トップページの下書き確認ルートが存在しない

**対象箇所**

`docs/サイト設計/サイト詳細設計書.md:74`  
`docs/サイト設計/サイト詳細設計書.md:76`  
`docs/サイト設計/サイト詳細設計書.md:95`  
`docs/サイト設計/サイト詳細設計書.md:96`

**内容**

`preview/` アプリのルート一覧には `story`、`news`、および `about` / `concept` / `farm` / `faq` / `kominka` 系ページの preview しか定義されていない。

一方でトップページは `site_settings` と `top_feature` をデータソースとしており、ブランド導入文や特集バナーなど運営者が確認したい変更点を含む。現状のルート設計では、トップページ用の draft データを確認する導線が存在しない。

**推奨対応**

以下のどちらかを明記する。

- `/preview/page/home` あるいは `/preview/home` を追加し、`site_settings` と `top_feature` をまとめて確認できるようにする
- トップページの preview は別方式で確認する、と設計書に明記する

`preview/` を正式採用している以上、トップページの確認導線が欠けたままだと運用設計として不完全。

### Major-02: `site_settings` スキーマがトップページ設計を満たしていない

**対象箇所**

`docs/サイト設計/サイト詳細設計書.md:95`  
`docs/サイト設計/サイト詳細設計書.md:96`  
`docs/サイト設計/サイト詳細設計書.md:474`  
`docs/サイト設計/サイト詳細設計書.md:483`

**内容**

トップページ詳細設計では、`Hero` を `site_settings` または固定、`Brand Intro` を `site_settings` から表示する前提になっている。

しかし `5.1 site_settings` のフィールド定義は `siteName`、`siteDescription`、`ogpDefaultImage`、`logo`、`contactEmail`、`socialLinks` のみで、トップページの導入文やヒーロー画像・ヒーロー文言に相当する項目が定義されていない。

このままだと、画面設計は `site_settings` 依存なのに、データモデルはその値を保持できないという矛盾が残る。

**推奨対応**

方針をどちらかに寄せるべき。

- `site_settings` にトップページ用の `homeHeroTitle`、`homeHeroImage`、`homeIntroText` などを追加する
- `site_settings` とは別に `home_page` シングルコンテンツを新設し、トップページ固有情報を分離する

保守性を考えると、共通設定とページ本文を分離する後者の方が設計として自然。

### Major-03: 問い合わせフォームで必須の `privacyConsent` が API 契約から抜けている

**対象箇所**

`docs/サイト設計/サイト詳細設計書.md:274`  
`docs/サイト設計/サイト詳細設計書.md:285`  
`docs/サイト設計/サイト詳細設計書.md:605`  
`docs/サイト設計/サイト詳細設計書.md:611`

**内容**

画面設計では `privacyConsent` が必須項目として定義されているが、`8.2 リクエスト仕様` の JSON には `privacyConsent` が含まれていない。

また、送信フローやステータスコードの説明でも、同意未チェック時に API がどう扱うかが書かれていない。これでは「同意チェックはクライアントだけで担保する」のか、「API でも必須検証する」のかが不明で、実装者ごとに判断が割れる。

**推奨対応**

以下のいずれかに統一する。

- API リクエストに `privacyConsent: true` を含め、サーバー側でも必須検証する
- 同意確認はフロント専用とし、API 契約からは明示的に除外する

個人情報取り扱いの観点では、サーバー側でも `true` を検証する方が安全。

### Minor-01: `contact-api` の環境切替ルールが詳細設計に落ち切っていない

**対象箇所**

`docs/サイト設計/サイト詳細設計書.md:39`  
`docs/サイト設計/サイト詳細設計書.md:590`  
`docs/サイト設計/サイト詳細設計書.md:591`  
`docs/サイト設計/サイト詳細設計書.md:722`  
`docs/サイト設計/サイト詳細設計書.md:743`

**内容**

環境構成では `production` / `staging` を前提にしており、`contact-api/` のディレクトリ構成にも `config/production.php` と `config/staging.php` が存在する。

一方、環境変数一覧で `DEPLOY_ENV` が定義されているのは `web/` のみで、`contact-api/` 側でどの設定ファイルを選ぶのかが明記されていない。基本設計書では `DEPLOY_ENV` に応じて本番 / 検証へ切り替える方針のため、詳細設計でもブートストラップ規則まで書いておいた方が実装時の解釈ずれを防げる。

**推奨対応**

`contact-api/` 側にも以下を追記する。

- `DEPLOY_ENV` を参照して `config/production.php` / `config/staging.php` を選択する
- もしくは配備時に対象ファイルを `config/runtime.php` へコピーする

どちらを採るにしても、選択規則を 8.1 または 11.3 に明記した方がよい。

## 結論

現行の詳細設計書は、上位設計との方向性は揃っているが、`contact-api` と `preview/` 周りに「設計の意図はあるが、実装条件が最後まで書き切れていない」箇所が残っている。

優先順位は次の通り。

1. `contact-api` の `microCMS` 接続情報を定義する
2. トップページの preview 導線を追加する
3. トップページ用コンテンツのスキーマを確定する
4. `privacyConsent` の API 契約を明確化する
5. `contact-api` の環境切替規則を明記する
