## 指摘事項

### Major-01: `preview/page/[pageKey]` の一般ページ系マッピングが未定義

**対象箇所**

- `docs/サイト設計/サイト詳細設計書.md:80`
- `docs/サイト設計/サイト詳細設計書.md:588`
- `docs/サイト設計/サイト詳細設計書.md:593`
- `docs/サイト設計/サイト詳細設計書.md:597`
- `docs/サイト設計/サイト詳細設計書.md:411`
- `docs/サイト設計/サイト詳細設計書.md:423`
- `docs/サイト設計/サイト詳細設計書.md:435`
- `docs/サイト設計/サイト詳細設計書.md:448`
- `docs/サイト設計/サイト詳細設計書.md:462`
- `docs/サイト設計/サイト詳細設計書.md:473`

**内容**

`/preview/page/[pageKey]` の対象には `about`, `concept`, `farm`, `kominka`, `kominka_access`, `kominka_experience` が含まれているが、7.2 の取得方式で具体的に定義されているのは `home` と `faq` の特殊処理だけである。

このため、実装者は次の判断を自前で補う必要がある。

- `pageKey=about` は `about_page` を読むのか
- `pageKey=concept` は `concept_page` を読むのか
- `pageKey=kominka` は `kominka_page` のシングルコンテンツ扱いでよいのか
- これらの pageKey で `contentType` / `contentId` を無視するのか、検証するのか

現状でも実装は推測で可能だが、`preview/` は別アプリでありルーティングと CMS 取得の対応が暗黙だとブレやすい。

**推奨対応**

7.2 に `pageKey -> microCMS コンテンツ型` の対応表を追加し、少なくとも以下を明記する。

- `about -> about_page`
- `concept -> concept_page`
- `farm -> farm_page`
- `kominka -> kominka_page`
- `kominka_access -> kominka_access`
- `kominka_experience -> kominka_experience`

加えて、これらの pageKey では `contentType` / `contentId` を受け取らず、対象シングルコンテンツを `draftKey` 付きでそのまま描画する方針まで固定した方がよい。

### Major-02: 問い合わせ API のリクエスト契約が基本設計書とずれている

**対象箇所**

- `docs/サイト設計/サイト詳細設計書.md:644`
- `docs/サイト設計/サイト詳細設計書.md:657`
- `docs/サイト設計/サイト詳細設計書.md:801`
- `docs/サイト設計/サイト詳細設計書.md:805`
- `docs/サイト設計/サイト基本設計書.md:505`
- `docs/サイト設計/サイト基本設計書.md:515`
- `docs/サイト設計/サイト基本設計書.md:624`
- `docs/サイト設計/サイト基本設計書.md:625`

**内容**

詳細設計書では問い合わせ API の payload に `privacyConsent` と `recaptchaToken` を含め、`web/` 側の `Shopify` 接続変数も `NEXT_PUBLIC_*` 名で定義している。

一方、基本設計書ではまだ次の旧契約が残っている。

- payload: `category`, `name`, `email`, `phone?`, `message`, `honeypot?`
- 環境変数: `SHOPIFY_STORE_DOMAIN`, `SHOPIFY_STOREFRONT_ACCESS_TOKEN`

このままだと、実装者が基本設計書を読んだときに問い合わせフォームの送信型と `.env` 命名規則を誤認しやすい。詳細設計単体では正しい方向に寄っているが、上位文書同期が未完了である。

**推奨対応**

基本設計書を詳細設計書に合わせて同期する。

- 問い合わせ payload に `privacyConsent` を必須追加する
- `recaptchaToken` は「有効化時のみ送る任意項目」と明記する
- `Shopify` の接続変数は `NEXT_PUBLIC_SHOPIFY_STORE_DOMAIN` / `NEXT_PUBLIC_SHOPIFY_STOREFRONT_ACCESS_TOKEN` に統一する

### Major-03: 記事詳細の表示要件が要件定義書を満たしていない

**対象箇所**

- `docs/要件定義/サイト要件定義書.md:366`
- `docs/サイト設計/サイト詳細設計書.md:148`
- `docs/サイト設計/サイト詳細設計書.md:152`
- `docs/サイト設計/サイト詳細設計書.md:348`
- `docs/サイト設計/サイト詳細設計書.md:367`
- `docs/サイト設計/サイト詳細設計書.md:390`

**内容**

要件定義書 7.3 では、記事系ページに「公開日、更新日、著者または運営主体を表示できるようにする」とある。

しかし詳細設計書では、記事詳細の Hero は「タイトル、公開日、OGP 画像」のみで、共通コンポーネント `ArticleMeta` も「公開日、カテゴリ」だけになっている。さらに `story` / `news` のデータモデルにも、著者表示や運営主体表示の扱いが書かれていない。

`updatedAt` を microCMS のシステム項目で代用する選択肢自体はあるが、その使い方が書かれていないため、要件を満たす実装方針としては未確定である。

**推奨対応**

記事詳細に関して、少なくとも以下のどちらかを明記する。

- `publishedAt` と microCMS システム項目の `updatedAt` を表示し、著者は固定文言の運営主体名で出す
- `authorName` を `story` / `news` に追加し、未設定時は運営主体名にフォールバックする

また `ArticleMeta` の役割も「公開日、更新日、著者または運営主体」に合わせて更新した方がよい。

### Minor-01: `robots.txt` の詳細設計が抜けている

**対象箇所**

- `docs/要件定義/サイト要件定義書.md:343`
- `docs/サイト設計/サイト基本設計書.md:673`
- `docs/サイト設計/サイト詳細設計書.md:723`
- `docs/サイト設計/サイト詳細設計書.md:742`

**内容**

要件定義書では `robots.txt` を設定することが明記され、基本設計書でも「ビルド成果物に含める。ステージングでは `noindex` を前提とする」と整理されている。

一方、詳細設計書の SEO セクションでは `description`、`canonical`、`og:image`、`sitemap.xml` までは定義されているが、`robots.txt` の生成方針と環境差分が抜けている。

Static Export 前提では `robots.txt` も成果物の一部として具体化しておかないと、`production` / `staging` のどちらに何を書き出すかが実装者依存になりやすい。

**推奨対応**

9.1 か 11 章に `robots.txt` の詳細を追加する。

- `production`: `Allow` と `Sitemap: <公開URL>/sitemap.xml`
- `staging`: `Disallow: /` を返す、または成果物に同等内容を含める
- `preview/`: `robots.txt` ではなく `noindex` と Basic 認証で保護する

## 結論

v1.4.1 は前回より安定しているが、まだ「preview の pageKey 契約」「問い合わせ API の上位文書同期」「記事メタ表示」「robots.txt」の4点に詰め残しがある。

優先順位は次のとおり。

1. `preview/page/[pageKey]` の対応表を定義する
2. 問い合わせ payload と `Shopify` 環境変数名を基本設計書まで同期する
3. 記事詳細の更新日 / 運営主体表示方針を確定する
4. `robots.txt` を詳細設計へ追加する
