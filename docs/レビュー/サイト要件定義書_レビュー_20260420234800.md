## 総合評価

**評価: B（要件定義書としておおむね妥当だが、ホスティング前提の誤りと関連ドキュメントとの重大な不整合が残存）**

要件定義書 v1.3.0 単体としては、`Next.js + microCMS + Shopify` の責務分離、ページ一覧、機能要件、SEO方針、非機能要件、フェーズ管理がバランスよくまとまっている。前回レビュー（v1.2.0 → v1.3.0）での指摘事項は適切に反映されている。

しかし、**要件定義書のホスティング前提が Vercel になっており、実際の ConoHa WING + Static Export と矛盾している**。ISR / revalidate を前提とした複数の機能要件・インフラ要件が成立しないため、修正が必要。

また、**基本設計書・詳細設計書が旧方針のまま更新されておらず、要件定義書との間に重大な不整合が残存している**。

Agent.md については、本レビューに先行して ConoHa WING 前提でプロジェクト構成に合わせた更新を実施済み。

## 指摘一覧

### 重大度の定義

| 重大度 | 意味 |
|---|---|
| **Critical** | 実装方針に直接影響する不整合。即時対応が必要 |
| **Major** | 要件の曖昧さや欠落。設計着手前に解決すべき |
| **Minor** | 改善推奨だが、実装に致命的影響はない |
| **Info** | 補足・改善提案 |

### Critical-01: 基本設計書のルーティング・アーキテクチャが要件定義書と不一致

**対象セクション**: 要件定義書 セクション4・10 ↔ `docs/サイト設計/サイト基本設計書.md` セクション1・2

**内容**

基本設計書のサイトマップと画面一覧は、要件定義書 v1.3.0 のルーティングと大きく乖離している。

| 項目 | 要件定義書 v1.3.0 | 基本設計書 v1.0.0 |
|---|---|---|
| ブランド紹介 | `/about`, `/concept` | `/brand`（1ページに集約） |
| 畑紹介 | `/farm` | `/field` |
| 古民家 | `/kominka`, `/kominka/access`, `/kominka/experience` | `/guesthouse`（単独） |
| ストーリー | `/stories`, `/stories/[slug]` | `/blog`（フェーズ2以降） |
| お知らせ | `/news`, `/news/[slug]` | なし |
| FAQ | `/faq` | なし |
| 商品カテゴリ | `/products/category/[category]` | なし |
| 商品詳細 | `/products/[slug]` | `/products/[id]` |
| 配送情報 | `/shipping` | なし |
| 返品・交換 | `/returns` | なし |
| 購買導線 | Shopify checkout に委譲 | `/cart`, `/checkout`, `/checkout/complete`（独自フロー） |
| EC方式 | Shopify Storefront API | Stripe / Square 想定 |
| ホスティング | Vercel | ConoHa WING（Agent.md） |
| 出力方式 | SSR / ISR（revalidate 前提） | Static Export |

**リスク**

- 開発者がどちらのドキュメントに従うべきか判断できない
- ページ実装のたびにルーティングが揺れる
- 設計レビュー自体が機能しない

**推奨対応**

基本設計書 v1.0.0 を要件定義書 v1.3.0 のルーティング・アーキテクチャに合わせて全面改訂する。同時に Agent.md のホスティング記述（ConoHa WING → Vercel）と出力方式（Static Export → SSR/ISR）を修正する。

### Critical-02: 詳細設計書のルーティング・コンポーネント名が要件定義書と不一致

**対象セクション**: 要件定義書 セクション4 ↔ `docs/サイト設計/サイト詳細設計書.md`

**内容**

詳細設計書も基本設計書と同じ旧ルーティング体系のまま。セクション構成やコンポーネント名（例: 「ゲストハウス」セクション）が旧名称で定義されている。

**推奨対応**

詳細設計書を要件定義書 v1.3.0 に合わせて改訂する。ルート名、セクション名、コンポーネント参照を統一する。

### Critical-03: 要件定義書のホスティング・出力方式が実態と矛盾

**対象セクション**: 要件定義書 セクション1.4、セクション5.6、セクション8.5

**内容**

本プロジェクトのホスティングは **ConoHa WING** であり、`web/next.config.mjs` も `output: 'export'`（Static Export）で設定済みである。しかし要件定義書 v1.3.0 では以下のように **Vercel 前提の記述** が残っている。

| 項目 | 要件定義書の記述 | 実態（ConoHa WING） |
|---|---|---|
| ホスティング | `Vercel` | ConoHa WING |
| 配信基盤（セクション1.5） | `Vercel` | ConoHa WING |
| 出力方式 | ISR / revalidate 前提 | Static Export（`output: 'export'`） |
| CMS更新反映（セクション5.6） | 「`revalidate` または再デプロイ」 | 再ビルド + デプロイのみ（revalidate 不可） |
| インフラ要件（セクション8.5） | 「`Vercel` を前提」「Preview Deploy」 | ConoHa WING では Preview Deploy 不可 |

**リスク**

- ISR / revalidate を前提とした機能要件が実現不可能
- 開発者が Vercel 前提で Server Actions や Route Handlers を実装してしまう
- CMS Webhook → revalidate の運用設計が成立しない

**影響範囲**

以下の要件定義書の記述を ConoHa WING + Static Export 前提に修正する必要がある。

1. セクション 1.4: ホスティングを `ConoHa WING` に変更
2. セクション 1.5: 配信基盤を `ConoHa WING` に変更
3. セクション 5.6: CMS更新反映を「再ビルド + デプロイ」に変更。Webhook は CI/CD トリガーとして使う方針に修正
4. セクション 8.5: インフラ要件を ConoHa WING 前提に全面改訂（Preview Deploy の代替手段を検討）
5. 商品データ取得方式: SSR ではなく SSG（ビルド時取得）またはクライアントサイド取得を明記

**推奨対応**

要件定義書のホスティング関連記述を ConoHa WING + Static Export に合わせて修正する。Agent.md は本レビューに先行して ConoHa WING 前提に更新済み。

### Major-01: 商品フィルタリング・絞り込みの要件が不明確

**対象セクション**: セクション 5.2「商品一覧・カテゴリ」

**内容**

「並び順、絞り込みのUIを提供する」とあるが、具体的な絞り込み軸が定義されていない。

- どのカテゴリ体系で絞り込むか（Shopify コレクション準拠か、独自分類か）
- 価格帯での絞り込みは必要か
- 在庫あり/なしの絞り込みは必要か
- 並び順の選択肢は何か（新着順、価格昇順/降順、人気順など）

**推奨対応**

基本設計書で具体的なフィルタ軸と並び順の選択肢を定義する旨を、要件定義書に明記する。または、要件として最低限のフィルタ軸を列挙する。

### Major-02: エラーハンドリング・API障害時の方針が未定義

**対象セクション**: セクション 5.6、セクション 8

**内容**

microCMS や Shopify Storefront API が一時的に応答しない場合の表示方針が定義されていない。

- API タイムアウト時にフォールバック表示を行うか
- ISR キャッシュが残っていれば古いデータで表示するか
- 完全なエラー時に専用エラーページを出すか

**推奨対応**

非機能要件またはCMS・外部連携機能セクションに、外部API障害時の基本方針を追記する。詳細はフェーズ1の基本設計書で定めるとしてもよい。

---

### Major-03: Cookie同意・プライバシー対応の方針が不足

**対象セクション**: セクション 8.2、セクション 9

**内容**

GA4 の導入が前提（セクション 1.4、8.5）だが、Cookie 同意バナーやトラッキング同意の取り扱い方針が記載されていない。フェーズ2 で多言語対応（英語）を予定しているため、将来的な EU ユーザーへの対応（ePrivacy / GDPR）も視野に入る。

**推奨対応**

- フェーズ1では日本国内向けとして最低限の Cookie ポリシー記載方針を定める
- フェーズ2の多言語対応時に Cookie 同意バナーを導入する旨を、セクション9のフェーズ計画に追記する

---

### Major-04: microCMS スキーマ定義の所在が不明確

**対象セクション**: セクション 6.5

**内容**

「各コンテンツの詳細なフィールド定義は『サイト詳細設計書.md』で別途定める」とあるが、現時点の詳細設計書 v1.0.0 にはスキーマ定義が含まれていない（ドラフト状態）。

要件定義書が v1.3.0 まで進んでいるのに対し、参照先の詳細設計書がドラフトのままでは、CMS 構築の着手時に必要な情報が得られない。

**推奨対応**

詳細設計書の改訂スケジュールを明確にするか、要件定義書内に最低限のスキーマ方針（コンテンツ型ごとの必須フィールド一覧）を追記する。

---

### Major-05: 問い合わせフォームの入力バリデーション要件が不足

**対象セクション**: セクション 5.5

**内容**

フォーム項目（問い合わせ種別、氏名、メールアドレス、本文）は定義されているが、バリデーションルールが未定義。

- メールアドレスの形式検証
- 本文の最大文字数
- 必須項目の指定
- 電話番号フィールドの要否

**推奨対応**

基本設計書で定める旨を明記するか、要件定義書内で最低限の必須/任意・文字数制限を規定する。

### Minor-01: reCAPTCHA v3 の具体名がセクション間で抽象度が揺れている

**対象セクション**: セクション 5.5、セクション 8.2

**内容**

- セクション 5.5 では `reCAPTCHA v3` を明記
- セクション 8.2 では「`reCAPTCHA v3` 等のスパム対策」と表記
- セクション 5.5 の別の箇所では「使用する送信サービス...は基本設計書で定める」とし、実装詳細を基本設計に委譲する姿勢

前回レビューで「特定実装名ではなく一般化すべき」とした指摘の反映が中途半端になっている。

**推奨対応**

統一方針を決める。reCAPTCHA v3 を要件として確定するなら両セクションで明記する。基本設計に委譲するなら両方とも「bot対策を適用する」に一般化する。

### Minor-02: 画像最適化の具体方針が不足

**対象セクション**: セクション 7.5、セクション 8.1

**内容**

画像SEO要件（ファイル名、alt、キャプション）は定義されているが、パフォーマンス要件（LCP 2.5秒以内）を達成するための画像最適化方針が未定義。

- WebP / AVIF 等の次世代フォーマット対応
- `next/image` による自動最適化の活用
- 画像CDN（Vercel Image Optimization / Shopify CDN）の利用方針

**推奨対応**

非機能要件またはSEO要件に画像最適化の基本方針を追記する。詳細実装は基本設計書で定める。

---

### Minor-03: 構造化データの出力対象が一部曖昧

**対象セクション**: セクション 7.2、7.3、7.4

**内容**

- 商品: `Product` / `Offer` → 明確
- 記事: `Article` → 明確
- 古民家: `LocalBusiness` または `LodgingBusiness` → 「系」と表記されており、どちらを採用するか未確定
- パンくず: `BreadcrumbList` → セクション7.1で言及あり
- FAQ: `FAQPage` → 未言及（`/faq` ページに出力すべき）
- サイト全体: `Organization` / `WebSite` → 未言及

**推奨対応**

出力する構造化データ型の一覧を整理する。具体的なスキーマ選定は基本設計書で確定するとしても、対象ページと型の方向性を要件定義書に記載する。

### Minor-04: Shopify Webhook による商品更新反映の記述が不足

**対象セクション**: セクション 5.6、セクション 8.5

**内容**

microCMS の Webhook → revalidate は明記されているが、Shopify 側の商品データ更新時の反映方式が「サイト表示へ反映される運用を整える」という曖昧な記述にとどまっている。

- Shopify Webhook → revalidate を使うのか
- 定期的な再ビルドで対応するのか
- リアルタイム性はどの程度求めるのか

**推奨対応**

商品更新の反映方式の方針（Webhook / 定期再ビルド / API直接取得）を要件レベルで記載する。

### Info-01: フェーズ計画に時期の目安がない

**対象セクション**: セクション 9

**内容**

フェーズ2、フェーズ3の想定時期が「フェーズ2」「フェーズ3」としか記載されておらず、時間軸が不明。ロードマップとしてはスケジュール感がないと優先順位判断が難しい。

**推奨対応**

概算の時期目安（例: 「フェーズ2: 初期リリース後 3〜6ヶ月」）を追記する。

**推奨対応**

**対象セクション**: セクション 8.2

**内容**

HTTPS、reCAPTCHA、環境変数管理は定義されているが、セキュリティヘッダー（CSP、X-Frame-Options、X-Content-Type-Options 等）の方針が未記載。Vercel のデフォルト設定に依存するか、カスタム設定するかの方針があるとよい。

**推奨対応**

基本設計書でセキュリティヘッダー方針を定める旨を追記する。

## 要件定義書の品質に関する所見

### 良い点

1. **責務分離が明確**: Shopify / microCMS / Next.js の三者の責務が明快に定義されている
2. **ページ一覧の網羅性**: 21ページの構成が具体的なパスとともに定義されており、実装者にとって迷いが少ない
3. **SEO要件の3系統整理**: 商品SEO・記事SEO・地域SEOの分離は、併用案の方針をよく反映している
4. **商品詳細のデータマッピング**: Shopify フィールドとの対応が表形式で明確
5. **フェーズ管理**: フェーズ1で「やらないこと」が明示されており、スコープクリープを防ぐ設計になっている
6. **前回レビュー指摘の反映**: FAQ正本の統一、商品説明マッピングの修正、問い合わせ機能の抽象化が適切に行われている

### 改善が必要な点

1. **関連ドキュメントとの整合性が未確保**（Critical-01〜02）
2. **ホスティング前提の誤り**: 要件定義書が Vercel / ISR 前提で書かれているが、実際のホスティングは ConoHa WING（Static Export）（Critical-03）
3. **フィルタリング・バリデーション等の詳細が未定義**（Major-01、05）
4. **障害時・例外時の方針が欠落**（Major-02）
5. **将来対応に向けたプライバシー方針が不足**（Major-03）
