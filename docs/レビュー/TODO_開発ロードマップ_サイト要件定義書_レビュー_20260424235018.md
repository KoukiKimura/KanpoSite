## Major

### Major-01: 問い合わせログ・rate-limit 保存先の個人情報保護要件が未定義

**対象**

- `docs/TODO_開発ロードマップ.md` 131行目: 問い合わせログ保存先と rate-limit 保存先を「環境別ディレクトリへ出力」
- `docs/要件定義/サイト要件定義書.md` 230〜241行目: 問い合わせフォームと送信APIの方針
- `docs/要件定義/サイト要件定義書.md` 432〜435行目: フォーム送信API、送信頻度制御、シークレット管理

**問題**

問い合わせフォームは氏名、メールアドレス、本文を扱うため、ログに個人情報が含まれる可能性が高い。  
しかし、保存場所が公開ディレクトリ外か、本文を保存するのか、保存期間、ローテーション、アクセス権限、IPアドレスの扱いが未定義。

`ConoHa WING + PHP` 前提では、誤って公開Webルート配下にログを置くと問い合わせ本文やrate-limit情報が外部から読めるリスクがある。

**推奨対応**

以下を要件定義書または基本設計書へ明記する。

- 問い合わせログとrate-limitファイルは公開Webルート外に保存する
- 本文・メールアドレスをログに残すか、障害調査用の最小情報に限定するかを決める
- 保存期間、削除・ローテーション、ファイル権限を定める
- rate-limit用のIP/User-Agentは必要最小限で保持し、目的外利用しない
- エラー表示には個人情報や内部パスを出さない

### Major-02: `DecapCMS` のGit認証・管理画面・再ビルド実行主体が未確定

**対象**

- `docs/要件定義/サイト要件定義書.md` 247〜248行目: `DecapCMS` 設定、Gitリポジトリベース運用
- `docs/要件定義/サイト要件定義書.md` 459行目: Webhook または手動ビルドで再ビルド + デプロイ
- `docs/TODO_開発ロードマップ.md` 110〜111行目: `DecapCMS` 設定・SEOメタ取得
- `docs/TODO_開発ロードマップ.md` 119行目: Webhook 起点の再ビルド設計
- `docs/TODO_開発ロードマップ.md` 136行目: GitHub Actions に `DEPLOY_ENV` 切替付きデプロイフロー

**問題**

`DecapCMS` はGitベースで動く前提だが、管理画面の配置パス、Git backend、認証方式、編集権限、コミット先ブランチ、Webhook起点、手動ビルドの実行者がまだ定義されていない。  
SEO専用とはいえ、運営者が管理画面から更新するなら、ここが未確定のままだとフェーズ4の実装・検証が止まる。

**推奨対応**

基本設計書またはTODOへ以下のタスクを追加する。

- `DecapCMS` 管理画面の公開パスとアクセス制御
- Git backend / OAuth / Git Gateway 等の採用方式
- 編集可能ユーザー、権限、レビュー有無
- 更新先ブランチと本番反映フロー
- Webhookシークレット、GitHub Actions起動条件、手動再ビルド手順

### Major-03: `BASE` 側法務情報とサイト内固定ページの正本関係が未定義

**対象**

- `docs/要件定義/サイト要件定義書.md` 145〜149行目: `/shipping`、`/returns`、`/legal`、`/privacy`、`/terms`
- `docs/要件定義/サイト要件定義書.md` 188〜190行目: 決済・在庫・注文管理は `BASE` に委譲
- `docs/要件定義/サイト要件定義書.md` 243行目: 配送情報、返品情報、特商法表記等を独立ページ化
- `docs/要件定義/サイト要件定義書.md` 391行目: 商品詳細から配送情報・返品情報へ導線を明示

**問題**

購入・決済・注文管理を `BASE` に委譲する一方で、オリジナルサイト側にも配送、返品、特商法、利用規約ページを固定ページとして持つ方針になっている。  
どちらの記載を正本とするか、`BASE` 側の設定変更時にサイト側固定ページを誰が更新するかが未定義。

**影響**

配送条件、返品条件、販売者情報、送料等が `BASE` とオリジナルサイトで食い違うと、購入前説明・問い合わせ対応・法務面で混乱が起きる。

**推奨対応**

以下のいずれかに統一する。

- `BASE` 側の法務・配送・返品情報を正本とし、オリジナルサイト側は要約 + `BASE` への導線にする
- オリジナルサイト側も正本として扱うなら、`BASE` 変更時の同期責任者、確認頻度、最終確認日を定義する
- 商品データと同様に、法務固定ページにも `lastVerifiedAt` や更新責任を持たせる

### Major-04: フェーズ4の反映確認が、フェーズ5のデプロイ整備に依存している

**対象**

- `docs/TODO_開発ロードマップ.md` 60行目: フェーズ4の完了条件はステージングで反映確認できる状態
- `docs/TODO_開発ロードマップ.md` 117行目: ステージングでSEO補助情報と静的データの反映を確認
- `docs/TODO_開発ロードマップ.md` 119行目: Webhook起点の再ビルド設計を反映
- `docs/TODO_開発ロードマップ.md` 136行目: GitHub Actions のデプロイフロー整備はフェーズ5

**問題**

フェーズ4でステージング反映確認と再ビルド設計を完了条件にしているが、実際にステージングへ出し分けるデプロイフローはフェーズ5に置かれている。  
このままだとフェーズ4完了時点で「何を使ってステージング反映を確認するのか」が曖昧になる。

**推奨対応**

以下のどちらかに整理する。

- フェーズ4に最小限のステージングデプロイ・手動再ビルド手順を移す
- フェーズ4の完了条件を「ローカルまたはビルド成果物で反映確認できる状態」に下げ、ステージング反映確認をフェーズ5へ移す

### Minor-02: ロードマップの運用ルールが「チェックボックス更新」前提だが、主要タスクはステータス表で管理されている

**対象**

- `docs/TODO_開発ロードマップ.md` 20行目: 完了時はチェックボックスを更新
- `docs/TODO_開発ロードマップ.md` 68〜148行目: 主要タスクはチェックボックスではなくステータス列で管理

**問題**

実際のフェーズ別TODOはチェックボックスではなく、`未着手` / `進行中` / `完了` のステータス列で管理されている。運用ルールだけが旧形式のまま残っている。

**推奨対応**

「完了時はステータスを `完了` に更新し、必要に応じて完了日を記録する」に修正する。

## 良い点

- `DecapCMS`、静的データ、`BASE` の責務分離が前回より明確になった。
- 在庫表示と `availability` を出さない方針が明記され、`BASE API` 不使用方針と整合した。

## 結論

前回の大きな設計矛盾は解消済みで、モック作成・静的テンプレート実装へ進める状態に近い。  
ただし、問い合わせログ、DecapCMS運用、法務ページ同期、ステージング反映フローは実装前に決めないと手戻りや運用事故になりやすい。次の修正ではこの4点を優先して、要件定義書または基本設計書に責務と手順を明記することを推奨する。
