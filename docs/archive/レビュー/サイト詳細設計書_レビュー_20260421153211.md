## 指摘事項

### Major-01: `FAQ` の下書き確認フローが未定義

**対象箇所**

- `docs/サイト設計/サイト詳細設計書.md:80`
- `docs/サイト設計/サイト詳細設計書.md:86`
- `docs/サイト設計/サイト詳細設計書.md:157`
- `docs/サイト設計/サイト詳細設計書.md:390`
- `docs/サイト設計/サイト詳細設計書.md:578`
- `docs/サイト設計/サイト詳細設計書.md:582`

**内容**

`/preview/page/[pageKey]` には `faq` が含まれているが、preview のクエリ契約で `contentType` / `contentId` が定義されているのは `top_feature|farm_page|kominka_page` のみである。

`faq` はコレクション型コンテンツであり、単一ページ本文ではなく複数項目の集合として描画される。現状の設計では、未公開の FAQ 項目や更新中の FAQ 項目を `/preview/page/faq` でどう差し替えるのかが定義されていない。

このままだと次のどちらかになり、実装者判断で分岐しやすい。

- `/preview/page/faq` は公開済み FAQ 一覧しか表示しない
- `faq` 用にも `contentType=faq&contentId=...` を受け取り、対象 draft を差し替える

**推奨対応**

`faq` について以下のどちらかを明記する。

- `/preview/page/faq` は公開済み FAQ 一覧のみを表示し、個別 FAQ draft preview は別ルートまたは別契約で扱う
- `contentType=faq&contentId=...` を正式サポートし、対象 draft FAQ を一覧へ差し替える

### Major-02: `site_settings.logo` と `socialLinks` が上位文書とまだ完全同期していない

**対象箇所**

- `docs/サイト設計/サイト詳細設計書.md:494`
- `docs/サイト設計/サイト詳細設計書.md:496`
- `docs/サイト設計/サイト詳細設計書.md:720`
- `docs/サイト設計/サイト基本設計書.md:260`
- `docs/要件定義/サイト要件定義書.md:331`
- `docs/要件定義/サイト要件定義書.md:349`

**内容**

詳細設計書では `Organization` 構造化データのために `site_settings.logo` と `site_settings.socialLinks` を利用する前提になっている。

しかし上位文書との同期状況は次の通りで、まだ揃いきっていない。

- 基本設計書: `socialLinks` はあるが `logo` がない
- 要件定義書: `site_settings` の主な必須フィールドに `logo` も `socialLinks` もない

要件定義書 7.1 では全ページ共通で `Organization` を出す前提なので、構造化データに必要な項目が上位のスキーマ方針に入っていない状態は不整合になる。

**推奨対応**

要件定義書と基本設計書の `site_settings` 定義を、詳細設計書に合わせて同期する。

- `logo`
- `socialLinks`

少なくとも「主なフィールド」レベルでは明示しておいた方がよい。

### Minor-01: 問い合わせ API の失敗レスポンス契約が不足している

**対象箇所**

- `docs/サイト設計/サイト詳細設計書.md:655`
- `docs/サイト設計/サイト詳細設計書.md:661`
- `docs/サイト設計/サイト詳細設計書.md:665`
- `docs/サイト設計/サイト基本設計書.md:506`
- `docs/サイト設計/サイト詳細設計書.md:817`

**内容**

問い合わせ API は `ok`, `message`, `errorCode` を返す JSON とされているが、詳細設計書のレスポンス例は成功ケースのみで、失敗時の `errorCode` の種類や payload 形式が定義されていない。

UI 側ではインラインエラーや再試行導線を出す前提であり、将来 `Vercel Functions + Resend` に切り替える設計でもあるため、失敗レスポンスの契約が曖昧だと実装差異が起きやすい。

**推奨対応**

8.3 か 8.4 に以下を追加する。

- 失敗時レスポンスの JSON 例
- `errorCode` の列挙
  - 例: `validation_error`, `origin_forbidden`, `rate_limited`, `mail_send_failed`
- `message` を UI 表示向けに使うのか、`errorCode` を分岐キーに使うのか

## 結論

v1.4.0 は実装着手に十分近いが、まだ「CMS preview 契約」と「CMS スキーマの上位文書同期」に小さな穴が残っている。

優先順位は次の通り。

1. `faq` の draft preview 契約を明確化する
2. `site_settings.logo` / `socialLinks` を要件定義書・基本設計書へ同期する
3. 問い合わせ API の失敗レスポンス契約を追加する
