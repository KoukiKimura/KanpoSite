## 総合評価

**評価: A（要件定義書として実装着手可能な品質に到達）**

v1.4.0 では、前回レビュー（v1.3.0 → v1.4.0）で指摘した **Critical-03（ホスティング・出力方式の矛盾）** および **Major-01〜05、Minor-01〜04、Info-01〜03** の全項目が適切に反映されている。

- ホスティングが ConoHa WING + Static Export に統一され、ISR / revalidate 前提の記述が排除された

**要件定義書単体としては、設計・実装に進める状態にある。** ただし、基本設計書・詳細設計書が v1.0.0（旧方針）のまま未改訂であり、ドキュメントエコシステム全体での整合性は未確保。

## 今回の新規指摘

### 重大度の定義

| 重大度 | 意味 |
|---|---|
| **Critical** | 実装方針に直接影響する不整合。即時対応が必要 |
| **Major** | 要件の曖昧さや欠落。設計着手前に解決すべき |
| **Minor** | 改善推奨だが、実装に致命的影響はない |
| **Info** | 補足・改善提案 |

---

### Major-01: クライアントサイド API 取得時のエラーハンドリングが未定義

**対象セクション**: セクション 5.6

**内容**

セクション 5.6 では「ビルド時に API が応答しない場合」のエラーハンドリング方針が記載されたが、**クライアントサイドからの取得**（在庫状況等のリアルタイム性が必要な表示）に対するエラーハンドリング方針が未定義。

- Shopify Storefront API がクライアントサイドから応答しない場合の表示方針（フォールバック、エラーメッセージ等）
- リトライポリシー
- ビルド時データとクライアントサイドデータの優先度

**推奨対応**

クライアントサイド API 取得のエラーハンドリング基本方針を基本設計書で定める旨をセクション 5.6 に追記する。

---

### Major-02: Organization 構造化データの情報ソースが未定義

**対象セクション**: セクション 7.1、セクション 6

**内容**

セクション 7.1 の構造化データ一覧に `WebSite` と `Organization` が全ページ共通として定義されているが、`Organization` の必要項目（組織名、ロゴ、URL、SNSリンク等）をどのデータソースから取得するかが未定義。

セクション 6.5 の `site_settings` コンテンツ型に `siteName`、`siteDescription`、`ogpDefaultImage`、`contactEmail` は含まれているが、`Organization` 構造化データに必要な `logo`、`sameAs`（SNSリンク）等は含まれていない。

**推奨対応**

`site_settings` のフィールド方針に Organization 構造化データに必要な項目（ロゴURL、SNSリンク一覧等）を追加するか、基本設計書で定める旨を明記する。

---

### Minor-01: セクション 8.2 に誤字の可能性

**対象セクション**: セクション 8.2

**内容**

> フォーム送信 API エンドポイントには IP ベースまたは同等の**送信頼度制御**を実装すること

「送信頼度制御」は「**送信頻度制御**」（レートリミット）の誤字と思われる。文脈から IP ベースのレートリミットを意図しており、「頻度」が正しい。

**推奨対応**

「送信頼度制御」→「送信頻度制御」に修正する。

---

### Minor-02: 404 ページがページ一覧に未記載

**対象セクション**: セクション 4、セクション 5.7

**内容**

セクション 5.7 の共通機能に「404ページ」が記載されているが、セクション 4 の必要ページ一覧（P01〜P21）に 404 ページが含まれていない。Next.js の App Router では `not-found.tsx` として実装するため独立ページとして扱うのが自然。

**推奨対応**

404 ページを共通機能としての記載のみで十分と判断する場合は現状維持でよい。ページ一覧に含める場合は `P22` として `/404` を追加する。どちらの方針かを明記する。

**内容**

`Agent.md` の関連ドキュメント表では要件定義書のバージョンが `v1.3.0` と記載されているが、現在の要件定義書は `v1.4.0` に更新されている。

**推奨対応**

Agent.md の関連ドキュメント表のバージョン表記を `v1.4.0` に更新する。

### Info-01: `api/` ディレクトリの位置づけとフォーム送信 API の関係が不明確

**対象セクション**: セクション 5.5、`Agent.md` フォルダ構成

**内容**

プロジェクトルートに `api/` ディレクトリが存在し、Agent.md では「将来の API 実装用領域」と説明されている。セクション 5.5 では「外部フォームサービスまたは別途 API 層経由で処理する」としている。

`api/` ディレクトリがフォーム送信 API の実装先となるのか、完全に外部サービス（例: Google Forms、Formspree 等）を利用するのかの方針が不明確。

**推奨対応**

基本設計書でフォーム送信の具体的な実装先（`api/` ディレクトリ、外部サービス、または両方の併用）を定める際に、`api/` の役割との関係を明確にする。

---

### Info-02: `top_feature` の有効期限切れハンドリングが未定義

**対象セクション**: セクション 6.5

**内容**

`top_feature` コンテンツ型に `expiresAt`（任意）フィールドが定義されているが、有効期限切れの特集枠をどう扱うか（非表示にするタイミング、ビルド時の除外ロジック等）の方針が未記載。Static Export のため、期限切れの判定タイミングはビルド時またはクライアントサイドに限られる。

**推奨対応**

基本設計書で有効期限切れの判定方針（ビルド時除外 / クライアントサイド非表示 / 運営者手動非公開）を定める。

---

### Info-03: 基本設計書・詳細設計書の改訂に関する注意喚起（再掲）

**対象**: `docs/サイト設計/サイト基本設計書.md`（v1.0.0）、`docs/サイト設計/サイト詳細設計書.md`（v1.0.0）

**内容**

前回レビュー Critical-01・02 で指摘した基本設計書・詳細設計書の不整合は、要件定義書 v1.4.0 の完成をもって**修正の前提条件が整った**。以下の主要な乖離が残存している。

| 項目 | 要件定義書 v1.4.0 | 基本設計書 / 詳細設計書 v1.0.0 |
|---|---|---|
| ブランド紹介 | `/about` + `/concept` | `/brand`（1ページ集約） |
| 畑紹介 | `/farm` | `/field` |
| 古民家 | `/kominka`, `/kominka/access`, `/kominka/experience` | `/guesthouse`（単独） |
| ストーリー | `/stories`, `/stories/[slug]` | `/blog`（フェーズ2以降） |
| お知らせ | `/news`, `/news/[slug]` | なし |
| FAQ | `/faq` | なし |
| 商品カテゴリ | `/products/category/[category]` | なし |
| 商品詳細 | `/products/[slug]` | `/products/[id]` |
| 購買導線 | Shopify checkout に委譲 | `/cart`, `/checkout`, `/checkout/complete`（独自フロー） |

**推奨対応**

## 要件定義書の品質に関する所見

### 良い点

1. **前回指摘の全面的な反映**: Critical-03 を含む全 13 項目が v1.4.0 で適切に反映されており、レビューサイクルが機能している
2. **ホスティング前提の整合性確保**: ConoHa WING + Static Export の制約が全セクションに一貫して反映されている
3. **責務分離の明確性維持**: Shopify / microCMS / Next.js の三者の責務分離が v1.3.0 から引き続き明快
4. **実装粒度の適切さ**: 要件定義書として適切な粒度を保ち、詳細実装は基本設計書に委譲する姿勢が一貫している
5. **microCMS スキーマ方針の追加**: コンテンツ型ごとの必須フィールド方向性が明示され、CMS 構築の着手基準を満たしている
6. **フェーズ計画の具体化**: 時期目安の追加によりロードマップとしての実用性が向上した

### 改善が必要な点

1. **関連ドキュメントの改訂が未実施**: 要件定義書は整ったが、基本設計書・詳細設計書が旧方針のまま（Info-03）
2. **クライアントサイド API のエラーハンドリング未定義**: ビルド時のみ方針が定められている（Major-01）
3. **Organization 構造化データの情報ソース不足**: 全ページ共通の構造化データに必要な項目が CMS スキーマに不足（Major-02）
4. **軽微な誤字**: 「送信頼度制御」→「送信頻度制御」（Minor-01）

---

## 結論

要件定義書 v1.4.0 は、前回レビューの全指摘を反映し、**実装着手可能な品質に達している**。今回の新規指摘は Major 2 件、Minor 3 件、Info 3 件であり、いずれも要件定義書の根幹を揺るがすものではない。

**次のアクションとしては以下を推奨する。**

1. Minor-01（誤字修正）を要件定義書に即時反映する
2. Major-01〜02 の方針を基本設計書の改訂時に確定する
3. **基本設計書・詳細設計書を要件定義書 v1.4.0 に合わせて全面改訂する**（最優先）
4. Agent.md の要件定義書バージョン参照を v1.4.0 に更新する
