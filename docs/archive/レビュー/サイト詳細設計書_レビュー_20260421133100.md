## 総合評価

**評価: B（主要な設計方針は整備されているが、実装着手前に解消すべき Critical・Major 不整合が残存）**

v1.1.0 では、前回の要件定義書レビュー（Critical-01/02）および基本設計書レビューで指摘された URL 体系・ルーティング・購買導線の不整合が基本設計書 v1.4.0 と整合する形で修正されている。アーキテクチャの大枠（`web/`・`preview/`・`contact-api/` の三層構成、Shopify / microCMS の責務分離、Static Export 前提の制約対応）は一貫しており、設計書としての構造は整っている。

## 今回の新規指摘

### 重大度の定義

| 重大度 | 意味 |
|---|---|
| **Critical** | 実装方針に直接影響する不整合。即時対応が必要 |
| **Major** | 設計の曖昧さや欠落。実装着手前に解決すべき |
| **Minor** | 改善推奨だが、実装に致命的影響はない |
| **Info** | 補足・改善提案 |

### Critical-01: Shopify 環境変数の `NEXT_PUBLIC_` プレフィックス欠落

**対象セクション**: セクション 6、セクション 11.1

**内容**

セクション 11.1 の `web/` 環境変数で `SHOPIFY_STORE_DOMAIN` および `SHOPIFY_STOREFRONT_ACCESS_TOKEN` が `NEXT_PUBLIC_` プレフィックスなしで定義されている。

しかし、セクション 6（CartDrawer 詳細設計）が規定するカート追加・数量変更・削除・checkout 遷移の操作はすべてクライアントサイドコンポーネントから Shopify Storefront API を呼び出す処理である。Next.js では `NEXT_PUBLIC_` プレフィックスのない環境変数はビルド時にサーバーサイドにのみ公開されるため、クライアントコンポーネントから参照できない。これは CartDrawer が全く機能しないことを意味する。

なお、Shopify Storefront API トークンはパブリックキー（公開鍵）であり、クライアントへの公開は Shopify の設計上許容されている。

**推奨対応**

セクション 11.1 の当該変数名を以下のように改める。

| 旧変数名 | 新変数名 |
|---|---|
| `SHOPIFY_STORE_DOMAIN` | `NEXT_PUBLIC_SHOPIFY_STORE_DOMAIN` |
| `SHOPIFY_STOREFRONT_ACCESS_TOKEN` | `NEXT_PUBLIC_SHOPIFY_STOREFRONT_ACCESS_TOKEN` |

### Major-01: reCAPTCHA v3 の設計からの欠落

**対象セクション**: セクション 3.8、セクション 8.2、セクション 11.1、セクション 11.3

**内容**

要件定義書 §5.5 では `reCAPTCHA v3` を問い合わせフォームのスパム対策として明示している。しかし詳細設計書の関連セクションに reCAPTCHA の記載が一切ない。

- **セクション 3.8 入力項目**: `honeypot`（hidden）のみ記載。reCAPTCHA トークン取得の記述がない
- **セクション 3.8 送信フロー**: ステップ 3「POST 送信」の前に reCAPTCHA v3 トークン取得ステップがない
- **セクション 8.2 リクエスト仕様**: `recaptchaToken` フィールドが未定義
- **セクション 11.1 環境変数**: `NEXT_PUBLIC_RECAPTCHA_SITE_KEY` が未定義
- **セクション 11.3 環境変数**: `CONTACT_RECAPTCHA_SECRET_KEY` が未定義

honeypot 単体によるスパム対策は要件定義書の要件を満たさず、このまま実装すると要件定義書との明確な乖離が生じる。

**推奨対応**

- セクション 3.8 の送信フローに「`reCAPTCHA v3` トークン取得」ステップ（ステップ 2.5 相当）を追加する
- セクション 8.2 のリクエスト仕様 JSON に `recaptchaToken` フィールドを追加し、セクション 8 に Google reCAPTCHA API による検証ステップを追記する
- セクション 11.1 に `NEXT_PUBLIC_RECAPTCHA_SITE_KEY`（サイトキー）を追加する
- セクション 11.3 に `CONTACT_RECAPTCHA_SECRET_KEY`（シークレットキー）を追加する

### Major-02: microCMS コンテンツ型スキーマの定義不足（ページ系・top_feature）

**対象セクション**: セクション 3.1、セクション 3.2、セクション 3.7、セクション 5.1

**内容**

セクション 5.1（microCMS データモデル）には `story`・`news`・`faq`・`site_settings` のスキーマのみが定義されており、以下のコンテンツ型が欠落している。

| コンテンツ型 | 参照セクション | 備考 |
|---|---|---|
| `top_feature` | セクション 3.1（トップページ特集バナー） | `expiresAt` フィールドが言及されているが定義なし |
| `about_page` / `concept_page` | セクション 3.2（`/about`、`/concept`） | microCMS をデータソースと明記 |
| `farm_page` | セクション 3.1、3.2（`/farm`） | microCMS をデータソースと明記 |
| `kominka_page` | セクション 3.7（`/kominka`） | microCMS をデータソースと明記 |
| `kominka_access` | セクション 3.7（`/kominka/access`） | 基本設計書 §5.2 でシングルコンテンツ型に確定済み |
| `kominka_experience` | セクション 3.7（`/kominka/experience`） | microCMS をデータソースと明記 |

これらのコンテンツ型はルーティング表（セクション 2）に `microCMS` データソースとして明記されているにもかかわらず、スキーマ定義が存在しない。CMS 構築・実装時に必要フィールドの判断根拠がなく、開発着手に支障をきたす。なお基本設計書 v1.4.0 §5.2 では `kominka_access` をシングルコンテンツ型として確定しているが、詳細設計書側への反映がない。

**推奨対応**

セクション 5.1 に上記コンテンツ型のスキーマ定義（フィールド名、型、必須可否）を追加する。基本設計書 §5 との整合を確認し、齟齬があれば基本設計書を正本として揃える。

### Major-03: `site_settings` の `logo` フィールド欠落

**対象セクション**: セクション 5.1、セクション 9.2

**内容**

セクション 9.2 の構造化データ一覧で全ページ共通として `Organization` を定義しているが、セクション 5.1 の `site_settings` スキーマに `Organization` 構造化データに必須の `logo` フィールドが含まれていない。

`socialLinks`（`sameAs` に相当）は追加されているが、`logo`（ロゴURL）は依然未定義のまま。要件定義書レビュー（Major-02）でも指摘されており、詳細設計書での解消が期待されていた。このまま実装すると Google Search Console への `Organization` 構造化データ登録時に警告・エラーが発生する。

**推奨対応**

`site_settings` のスキーマに `logo`（media 型、必須）を追加する。あわせて、セクション 9.2 またはセクション 5.1 の注記に `Organization` 出力時は `logo`・`sameAs` を `site_settings` から取得する旨を明記する。

### Major-04: GA4 計測 ID の環境変数が未定義

**対象セクション**: セクション 9.3、セクション 11.1

**内容**

セクション 9.3 に GA4 イベント設計（`view_item`・`add_to_cart`・`begin_checkout` 等 8 件）が詳細に定義されているが、セクション 11.1 の `web/` 環境変数一覧に GA4 計測 ID 用の変数が含まれていない。GA4 を機能させるためには計測 ID の環境変数が必須であり、記載の欠落は実装時の見落としにつながる。

基本設計書 v1.4.0 §8.8（GA4 計測設計）との整合も要確認。

**推奨対応**

セクション 11.1 に `NEXT_PUBLIC_GA_MEASUREMENT_ID`（GA4 計測 ID）を追加する。

### Minor-01: `news` コンテンツ型のフィールド定義が省略

**対象セクション**: セクション 5.1

**内容**

`news` コンテンツ型の定義が「`story` から `relatedProductHandles` を除いた構成を基本とする」のみで、フィールド一覧が記載されていない。CMS 構築担当者が `story` の定義を参照してフィールドを推測する必要があり、構築ミスの温床となる。

**推奨対応**

`news` のフィールド一覧を `story` と同形式で明示的に記載する。`relatedProductHandles` を除いた 7 フィールドの追記で済む。

### Minor-02: `api/` ディレクトリと `contact-api/` の関係が未解消

**対象セクション**: セクション 8.1

**内容**

プロジェクトルートに `api/` ディレクトリが存在するが、セクション 8.1 の `contact-api/` ディレクトリ設計との関係が未定義のまま。前回要件定義書レビュー Info-01 で指摘した問題が詳細設計書でも引き継がれている。

- `contact-api/` がプロジェクトルートの `api/` ディレクトリを指しているのか
- `api/` は将来の別用途として `contact-api/` とは独立して管理するのか

いずれの場合もセクション 1.1 のアプリ構成表またはセクション 8.1 の冒頭に注記として明記する必要がある。

**推奨対応**

`contact-api/` の実際のプロジェクト内パス（例: プロジェクトルート直下の `contact-api/` フォルダ）と、`api/` との関係を明確にする。

### Minor-03: `phone` フィールドのバリデーション詳細が不足

**対象セクション**: セクション 3.8

**内容**

`phone` フィールドの検証条件が「数字、`-`、空白を許可」のみで、最小桁数・最大桁数の記載がない。日本の電話番号は 10〜11 桁であり、桁数制限を定義しないと「1234」のような無効な入力が許容される。

**推奨対応**

セクション 3.8 の `phone` フィールド備考欄に文字数制限（例: 10〜15 文字以内）を追記する。`Zod` スキーマ実装時の基準として機能させる。

---

### Info-01: CartDrawer の localStorage 有効期限（TTL）が未定義

**対象セクション**: セクション 6.2、セクション 6.4

**内容**

セクション 6.2 で `kanpo_cart_summary` に「更新時刻」を保存するとあるが、有効期限（TTL）の判定方針が記載されていない。Shopify のカートは一定期間（約 10 日）で期限切れとなるため、古い `cartId` を参照した場合の挙動が不明確。セクション 6.4 に「`cartId` が不正な場合は localStorage を破棄して再作成する」とあるが、これはエラー発生後の事後処理であり、期限切れ前の予防的破棄方針がない。

**推奨対応**

セクション 6.2 または 6.4 に `kanpo_cart_summary` の TTL（例: 7 日間）と期限切れ時の処理方針（ページロード時に更新時刻を確認し、TTL 超過時は localStorage を破棄して新規作成）を追記する。

---

### Info-02: `top_feature` の `expiresAt` 判定タイミングが未定義（前回指摘の引き継ぎ）

**対象セクション**: セクション 3.1

**内容**

前回要件定義書レビュー Info-02 で指摘した問題が詳細設計書でも未解消。セクション 3.1 の UI 仕様に "`expiresAt` を過ぎた項目を非表示にする" と記載されているが、Static Export 環境ではビルド時以外に判定タイミングがない。Webhook が発火しない間は期限切れの特集枠がそのまま表示され続ける可能性がある。

**推奨対応**

セクション 3.1 の UI 仕様の当該記述に「`expiresAt` の判定はビルド時のみ行う。期限切れ特集の即時非表示が必要な場合は、運営者が microCMS 側で非公開設定を行う」等の方針を追記する。

### Info-03: `PREVIEW_SECRET` の検証フローが未記載

**対象セクション**: セクション 7.1、セクション 11.2

**内容**

セクション 7.1 に `PREVIEW_SECRET` が仕様として列挙され、セクション 11.2 に環境変数として掲載されているが、microCMS の preview URL から渡されるパラメータとの照合方法が記載されていない。セクション 2.1 では `draftKey` をクエリで渡すとしているが、`PREVIEW_SECRET` との連携手順が不明確なため、実装担当者が設計書から実装方法を読み取れない。

**推奨対応**

セクション 7.1 に `PREVIEW_SECRET` の検証フロー（microCMS から `?secret=xxx&draftKey=yyy` でアクセスされた際に、`secret` を `PREVIEW_SECRET` と照合し、一致した場合のみ `draftKey` 付きで microCMS からデータ取得する旨）を追記する。

## 詳細設計書の品質に関する所見

### 良い点

1. **要件定義書・基本設計書との URL 整合性**: v1.1.0 で全 URL が要件定義書 v1.4.1 および基本設計書 v1.4.0 と一致し、ルーティング体系の混乱が解消された
2. **アーキテクチャの三層分離の明確性**: `web/`・`preview/`・`contact-api/` の責務・実行基盤・環境構成が一覧で把握でき、全体像を俯瞰しやすい
3. **CartDrawer の具体性**: 状態管理・localStorage キー・操作仕様・フォールバックが詳細に記述されており、実装着手しやすい設計になっている
4. **contact-api のセキュリティ設計の堅実さ**: Origin 検証・honeypot・レート制御・ログマスキングが設計段階から盛り込まれており、OWASP 観点での基本対策が考慮されている
5. **環境別設計の一貫性**: `DEPLOY_ENV` による本番 / 検証切替が `web/`・`contact-api/` の両レイヤーに一貫して適用されている
6. **SEO / 構造化データの網羅性**: ページ種別ごとの `title` テンプレートと構造化データ型が整理されており、SEO 実装の基準として機能する

### 改善が必要な点

1. **環境変数の定義不備が複合的に存在する**: `NEXT_PUBLIC_` プレフィックス欠落（Critical-01）、reCAPTCHA 関連変数の欠落（Major-01）、GA4 ID の欠落（Major-04）が同時に存在し、これらが未修正のまま実装に入ると複数箇所で動作不良が生じる
2. **microCMS スキーマ定義の不完全性**: ページ系コンテンツ型（`top_feature`・`about_page`・`farm_page`・`kominka_page` 等）が未定義のままでは CMS 構築・実装が進められない（Major-02）
3. **要件定義書レビュー指摘の未解消**: `site_settings.logo` の欠落（Major-03）および `top_feature` の有効期限方針（Info-02）が要件定義書レビュー時点から依然未対応

---

## 結論

詳細設計書 v1.1.0 は、URL 体系・購買導線・アーキテクチャ方針において基本設計書 v1.4.0 との整合が確立し、設計の骨格は整っている。しかし **Critical 1 件・Major 4 件**の不整合が残存しており、このまま実装に着手すると Shopify クライアント API の動作不全（Critical-01）、reCAPTCHA 未実装による要件違反（Major-01）、CMS 構築の頓挫（Major-02）等が生じる。

**次のアクションとしては以下を推奨する。**

1. **Critical-01**（`NEXT_PUBLIC_` プレフィックス）を詳細設計書のセクション 11.1 に即時反映する
2. **Major-01**（reCAPTCHA v3）をセクション 3.8・8.2・11.1・11.3 に反映し、contact-api 側の検証ロジック設計も確定する
3. **Major-02**（ページ系 microCMS スキーマ）を基本設計書 §5 と整合しながらセクション 5.1 に追記する
4. **Major-03**（`site_settings.logo`）をセクション 5.1 に追記する
5. **Major-04**（GA4 環境変数）をセクション 11.1 に追記する
6. Minor / Info 項目は実装フェーズ前に順次対応する
