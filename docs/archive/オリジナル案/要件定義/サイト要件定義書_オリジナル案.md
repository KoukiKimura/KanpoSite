## 1. 目的

既存のオリジナルサイト設計、モックのデザイン方針、静的サイト構成をできるだけ維持しながら、日常更新の中心となるブログ・お知らせをスマートフォンから更新できるCMSへ置き換える。

本案では、ブランドサイトの表現力と自由度を優先する。ECは `Shopify Storefront API` を利用したヘッドレスECとして実装し、サイト側で商品表示、バリエーション選択、カート操作、Checkout導線を提供する。決済、注文管理、配送設定、在庫管理の正本はShopifyに委譲する。

## 2. 採用方針

| 領域 | 方針 |
|---|---|
| フロントエンド | `web/` の `Next.js App Router` を継続利用 |
| デザイン | `web_mock/` のモックデザインを公開サイトへ移植。基準テーマカラーは暫定で `MOSS` |
| 配信 | `Next.js Static Export` + `ConoHa WING` を基本継続 |
| CMS | `Notion` をブログ投稿CMSとして採用。依頼者はNotionモバイルアプリから記事を作成・編集する |
| 変換レイヤー | `web/` 内に自前 `Next.js` 変換レイヤーを実装し、Notion Database / Page / Block を公開サイト用データへ変換する |
| 旧CMS | `DecapCMS` は採用しない。SEO専用CMSではなく、ブログ更新CMSへ置き換える |
| EC | `Shopify Storefront API` を利用し、商品一覧、商品詳細、バリエーション選択、サイト内カート、Shopify Checkout遷移を実装する |
| EC管理 | 商品、価格、在庫、コレクション、決済、注文、配送、返品条件はShopifyを正本とする |
| 問い合わせ | 初期は `ConoHa WING` + `PHP` + `ConoHa メール / SMTP` を採用する |
| ブログ反映 | 初期は GitHub Actions の定期実行と手動 `workflow_dispatch` で再ビルド・再デプロイ。即時反映が必要になった場合のみNotion Webhookを追加検討 |

## 3. CMS・変換レイヤー方針

2026-04-26 時点の調査と依頼者要望を踏まえ、本案では `Notion` と自前 `Next.js` 変換レイヤーを採用する。

| CMS候補 | 評価 | 判断 |
|---|---|---|
| `Notion` | モバイルアプリでページ作成・編集・画像挿入が可能。WordPress UIが苦手な運営者でも日常投稿しやすい | 採用 |
| `microCMS` | APIベースCMSとしてNext.js連携しやすいが、依頼者の投稿体験はNotionより確認が必要 | 不採用 |
| `WordPress` + Jetpackアプリ | スマホアプリで投稿できるが、依頼者がWordPress UIを苦手としている | 不採用 |
| `Newt` | 公式サイトでサービス終了予定が告知されている | 不採用 |
| `Shopify Blog` | スマホ更新は可能だが、これはShopify案の範囲。本案ではオリジナルサイトの自由度を優先 | 本案では不採用 |

変換レイヤーは外部SaaS（Feather / Super / Potion / Notaku 等）ではなく、自前実装とする。理由は以下のとおり。

- 既存 `web_mock/` のデザイン再現と公開サイト全体の導線制御を優先するため
- `/blog`、`/blog/[slug]` を既存サイト内の通常ページとして扱い、商品・古民家・問い合わせへの内部リンクを制御するため
- SEOメタデータ、構造化データ、canonical、sitemap、OGPを既存Next.js側で一元管理するため
- 外部Notionサイト化サービスへの月額依存とデザイン制約を避けるため

実装前に、運営者のスマホで以下を実機確認する。

- 新規記事作成、既存記事編集、画像アップロード、公開、下書き保存が迷わずできること
- タイトル、本文、アイキャッチ、カテゴリ、関連記事、SEO文言を入力できること
- 投稿後のサイト反映に必要な待ち時間と手順が運用上許容できること
- 権限、2要素認証、料金プラン、バックアップ手順が要件に合うこと

### 3.1 ブログ・お知らせのSEO方針

ブログとお知らせは、初期リリースでは独立した `/news` 系ページを作らず、Notionの同一Database内で `Category = お知らせ` として管理し、公開URLは `/blog` 配下に統一する。

判断理由:

- Google Searchの評価はURL名そのものより、ページ内容の有用性、正規URL、内部リンク、sitemap、重複回避の影響が大きい
- 小規模サイトで `/blog` と `/news` を分けると、低頻度更新の薄い一覧ページが増えやすい
- 同じNotion記事を複数URLに出すと重複管理、canonical、計測が複雑になる
- `/blog` 配下に集約した方が、ブランドの読み物、商品導線、古民家導線を1つのコンテンツ群として育てやすい

初期仕様:

| 項目 | 方針 |
|---|---|
| 正規ブログ一覧 | `/blog` |
| 正規ブログ詳細 | `/blog/[slug]` |
| カテゴリ一覧 | `/blog/category/[category]` |
| お知らせ一覧 | `/blog/category/news` |
| お知らせ詳細 | `/blog/[slug]` |
| `/news` | 初期リリースでは作成しない |
| canonical | 各記事は `/blog/[slug]` を正規URLとする |
| sitemap | `/blog`、`/blog/[slug]`、必要な `/blog/category/[category]` のみを含める |

将来的にお知らせ単体の検索需要や更新頻度が高くなった場合のみ、`/news` の独立を再検討する。その場合も、既存記事を重複公開せず、URL移行が必要な場合は301リダイレクトまたはcanonical方針を設計する。

### 3.2 Shopify API EC方針

EC機能はShopifyテーマではなく、既存 `web/` のNext.jsサイトから `Shopify Storefront API` を利用するヘッドレスECとして実装する。

| 領域 | 方針 |
|---|---|
| 商品取得 | `Storefront API` で商品、バリエーション、画像、価格、販売可否、SEO情報、metafieldsを取得する |
| コレクション | `Storefront API` のCollectionを商品カテゴリとして利用する |
| カート | `cartCreate`、`cartLinesAdd`、`cartLinesUpdate`、`cartLinesRemove`、cart queryでサイト内カートを実装する |
| Checkout | Cartの `checkoutUrl` でShopify Checkoutへ遷移し、決済を完了する |
| 決済 | カード情報や決済処理はサイト側で扱わず、Shopify Checkoutへ委譲する |
| 注文管理 | Shopify Ordersを正本とし、サイト側で注文管理画面は作らない |
| APIトークン | Storefront API public access tokenを利用する。Admin API tokenはブラウザに公開しない |
| 商品補足情報 | 原材料、飲み方、注意事項、内容量、FAQ、関連商品はShopify metafields / metaobjectsを基本とする |
| 初期対象外 | Shopify Admin APIによる商品編集、顧客マイページ、定期購入、クーポン高度連携、配送日時指定 |

Static Export前提のため、商品ページとコレクションページはビルド時にShopifyから取得して静的生成する。価格・販売可否・カート操作は、必要に応じてクライアント側でStorefront APIから最新情報を取得し、Checkout時点のShopify正本に従う。

Shopify API利用により、オリジナル案は「Next.jsブランドサイト + Notionブログ + ShopifyヘッドレスEC」の構成になる。Shopifyテーマ上でサイト全体を作る `Shopify案` とは区別する。

## 5. 機能要件

### 5.1 ブログ更新

- スマートフォンからブログ記事を作成・編集・公開できること
- 記事にはタイトル、slug、本文、アイキャッチ画像、公開日、更新日、カテゴリ、タグ、SEOタイトル、SEOディスクリプションを持たせること
- トップページに最新記事を表示すること
- 記事詳細から関連商品、古民家、問い合わせへ内部導線を設けること
- Notion更新後は GitHub Actions の定期実行または手動 `workflow_dispatch` で公開サイトへ反映すること
- Static Export 制約上、即時の下書きプレビューは初期必須にしない。必要な場合は後続で `preview/` 用の動的プレビュー環境を検討すること

### 5.2 自前Next.js変換レイヤー

- `web/` 内にNotion取得・変換専用のデータ層を実装すること
- Notion Databaseから公開対象記事一覧を取得し、`Status = Published` の記事のみ公開対象にすること
- Notion Page / Blockを公開サイト用の型付きデータへ変換すること
- 対応する本文ブロックは、段落、見出し、箇条書き、番号付きリスト、引用、区切り、画像、リンク、calloutを初期対象とすること
- `Published` 記事に未対応ブロックが含まれる場合は本番ビルドを失敗させること。`Draft` 記事は公開対象外のため警告に留めること
- Notionにアップロードされた画像はAPI上のURLが期限付きになるため、ビルド時に取得して静的アセット化し、公開HTMLにはNotionの期限付きURLを直接埋め込まないこと
- `Title`、`Slug`、`Status`、`PublishedAt` の欠落をビルド時にエラーとして検出すること
- `generateStaticParams` によりブログ詳細ページをStatic Export対象として生成すること
- Notion APIキー、Database ID、後続導入時のWebhookシークレットは環境変数で管理し、公開可能な値のみ `NEXT_PUBLIC_` を付けること
- GitHub Actions の定期実行と手動 `workflow_dispatch` により、記事更新後の再ビルド・再デプロイを実行できること。Notion Webhookは即時反映が必要になった場合の後続拡張とすること

### 5.3 画像最適化・画像SEO

Notion記事画像と静的画像は、実用面とSEO面の両方を考慮し、ビルド時に最適化する。

| 項目 | 方針 |
|---|---|
| 入力画像 | Notionアップロード画像、または静的素材。推奨入力形式は JPEG / PNG / WebP |
| HEIC | 初期は非推奨。変換ライブラリで処理できない場合はビルドエラーとして投稿者にJPEG再アップロードを依頼する |
| 公開形式 | 本文・一覧・サムネイルは WebP を主形式とし、必要に応じて JPEG フォールバックを生成する |
| OGP画像 | SNS互換性を優先し、1200x630の JPEG または PNG を生成・指定する |
| サイズ | 用途別に 480 / 768 / 1200 / 1600px 程度の複数幅を生成し、`srcset` で出し分ける |
| 圧縮 | WebP quality 75〜82を目安にし、見た目と容量のバランスを確認する |
| ファイル名 | 記事slug、用途、連番を含む説明的なkebab-case名にする。拡張子は実ファイル形式と一致させる |
| HTML | 画像はCSS背景ではなく、`img` または `picture` で表示する |
| alt | Notion側の画像キャプションまたは専用プロパティから生成し、未設定時は記事文脈に沿った代替テキストを設定する |
| CLS対策 | width / height またはアスペクト比を指定し、読み込み時のレイアウトシフトを抑える |
| 遅延読み込み | ファーストビュー外の画像は `loading="lazy"` を基本とする |

画像最適化パイプラインは `sharp` 等の画像変換ライブラリで実装する。変換済み画像は `public/generated/notion/` などの生成物ディレクトリに配置し、ビルド成果物へ含める。元画像が過大な場合でも公開HTMLでは最適化済み画像のみを参照する。

### 5.4 商品・EC機能

- 商品一覧、商品カテゴリ一覧、商品詳細をオリジナルサイト上で表示すること
- 商品一覧の商品画像クリックで商品詳細へ遷移できること
- 商品データはShopifyを正本とし、`Storefront API` で商品名、handle、説明、価格、画像、バリエーション、販売可否、SEO情報、metafieldsを取得すること
- 商品一覧・商品詳細では在庫あり / なしを表示し、数量選択、カート追加を提供すること
- 数量選択は在庫数と販売可否に応じて制御し、UI上の選択肢は最大 9 個までを基準とすること
- サイト内にカートページまたはカートドロワーを実装し、数量変更、削除、小計表示、Checkout遷移を提供すること
- ヘッダーにはアイコンのみのカート導線を配置し、件数バッジを表示すること。100点以上は `99+` 表示を基本とすること
- カートはShopify Cartを正本とし、cart IDをブラウザのlocalStorageまたは同等のクライアント保存で保持すること
- カート作成、明細追加、明細更新、明細削除は `Storefront API` のCart mutationで行うこと
- CheckoutはCartの `checkoutUrl` からShopify Checkoutへ遷移すること
- 決済、注文確定、注文管理、配送設定、在庫管理はShopifyを正本とすること
- サイト側ではカード情報、決済情報、注文管理情報を保持しないこと
- Storefront APIのエラー、販売停止、在庫切れ、バリエーション不一致時は、画面上で購入不可または再選択を案内すること
- 商品補足情報はShopify metafields / metaobjectsで管理し、原材料、飲み方、注意事項、内容量、FAQ、関連商品を表示できること

### 5.5 古民家導線

- 古民家紹介をブランド体験の重要導線として掲載すること
- 予約システムは実装せず、Facebookまたは外部予約サービスへリンクすること
- 施設概要、写真、アクセス、過ごし方、注意事項を表示すること

### 5.6 問い合わせ

- 問い合わせ種別、氏名、メールアドレス、電話番号、本文、プライバシー同意を持つフォームを提供すること
- Static Export 制約により、フォーム送信は `ConoHa WING` 配下の `PHP` 問い合わせAPIで処理すること
- 通知メールは `ConoHa メール / SMTP` を利用すること
- 外部フォームサービスは、PHP APIの運用が困難な場合の代替案として扱い、初期採用しないこと
- 送信失敗時は代替連絡先を表示すること

## 7. SEO要件

- 全ページに `title`、`description`、`canonical`、OGPを設定する
- ブログ詳細に `Article` 構造化データを出力する
- 商品詳細に `Product` 構造化データを出力する。`Offer` はShopify価格を元に出力し、販売可否はShopifyの `availableForSale` を参照する
- 古民家ページは `LocalBusiness` を基本とし、宿泊提供が明確な場合のみ `LodgingBusiness` を再検討する
- Notion記事のslugは公開後に安易に変更しない
- お知らせは `/blog/category/news` に統合し、記事詳細のcanonicalは `/blog/[slug]` に統一する
- 画像はGoogleが認識しやすい標準HTML画像要素で表示し、説明的なファイル名、alt、画像周辺テキスト、適切な画像形式を設定する

## 8. 非機能要件

| 項目 | 要件 |
|---|---|
| パフォーマンス | Static Export の利点を維持し、Lighthouse Performance 85以上を目標 |
| アクセシビリティ | WCAG 2.1 AA を目標 |
| セキュリティ | Notion APIキー、後続導入時のWebhookシークレット、将来利用時のShopify Admin API tokenは環境変数管理。Shopify Admin API tokenはブラウザに公開しない。Storefront API public tokenなど公開可能な値のみ `NEXT_PUBLIC_` を付ける |
| 計測 | GA4を導入し、`view_item`、`add_to_cart`、`begin_checkout` を計測対象とする。`purchase` はShopify Checkout側のGA4 / Shopify連携で扱い、サイト側で注文完了計測を独自実装しない |
| 運用性 | スマホ投稿から公開反映までの手順を運用マニュアル化 |
| 障害対応 | Notion更新、Shopify商品取得、ビルド失敗時は直前の公開成果物を維持。カートAPI障害時は購入不可メッセージと問い合わせ導線を表示 |
