## 1. 詳細設計前提

### 1.1 対象範囲

本書はオリジナル案の公開サイト実装に必要な画面、ルーティング、データモデル、外部連携、ビルド、運用、SEO、セキュリティの詳細設計を定義する。

| 項目 | 方針 |
|---|---|
| 公開サイト | `web/` の `Next.js App Router` で実装し、`Next.js Static Export` で静的成果物を生成する |
| デザイン移植元 | `web_mock/` の既存モックを移植元とする。基準テーマカラーは暫定で `MOSS` |
| ブログCMS | `Notion` を投稿CMSとし、`web/` 内の自前変換レイヤーで公開サイト用データへ変換する |
| EC | `Shopify Storefront API` を使うヘッドレスECとし、商品表示、サイト内カート、Checkout導線を `web/` で実装する |
| 決済・注文 | Shopify Checkout 以降を正本とし、公開サイト側ではカード情報、決済情報、注文管理情報を保持しない |
| 問い合わせ | Static Export 制約に合わせ、`ConoHa WING` 配下の `PHP` APIで処理する |
| 配信 | `ConoHa WING` の本番 / 検証環境へデプロイする |

### 1.2 アプリ・モジュール構成

| アプリ / モジュール | 役割 | 実行基盤 | 備考 |
|---|---|---|---|
| `web_mock/` | 依頼者レビュー用モック | 静的ホスティング | Notion / Shopify / 問い合わせAPIには接続しない |
| `web/` | 公開サイト本体 | `ConoHa WING` 静的配信 | App Router、Static Export、SEO出力、Notion / Shopify連携 |
| `contact-api/` | 問い合わせ受付API | `ConoHa WING` PHP | 現状未作成。実装時に追加する |
| `.github/workflows/` | ビルド・デプロイ自動化 | GitHub Actions | schedule / workflow_dispatch / push を想定 |

現状のリポジトリでは `api/` が空ディレクトリとして存在するが、本設計では問い合わせAPIの配置先を `contact-api/` として定義する。既存 `api/` を使う場合は、実装前に命名を統一する。

### 1.3 環境構成

| 環境 | 配備対象 | 用途 |
|---|---|---|
| `mock_review` | `web_mock/` | デザイン・導線確認 |
| `staging` | `web/` + `contact-api/` | Notion反映、Shopify商品・カート・Checkout、問い合わせ送信の結合確認 |
| `production` | `web/` + `contact-api/` | 本番公開 |

### 1.4 正本データ

| 領域 | 正本 | 公開サイトでの扱い |
|---|---|---|
| ブログ・お知らせ | Notion Database / Page | ビルド時に取得し、静的HTMLへ変換する |
| ブログ画像 | Notion files / external images | ビルド時に取得して静的アセット化する |
| 商品 | Shopify Products | ビルド時に一覧・詳細ページを生成する |
| 商品カテゴリ | Shopify Collections | `/products/category/[handle]` を生成する |
| 価格・在庫・販売可否 | Shopify | 表示はビルド時値を使い、購入判断はCart操作時にShopify正本を確認する |
| カート | Shopify Cart | クライアント側でCart IDを保持し、Storefront APIで操作する |
| 決済・注文・配送・返品 | Shopify | Checkout以降はShopify管理範囲とする |
| ブランド・畑・古民家 | 静的データ | `web/` 内の型付きデータまたはコンポーネントで管理する |
| 法務固定ページ | 静的データ。EC条件はShopify設定を正本 | `lastVerifiedAt` を持たせ、Shopify側設定との差分確認日を管理する |
| 問い合わせ通知先 | `contact-api/` 設定 / 環境変数 | ブラウザへ公開しない |
| サイト共通SEO | 静的設定 + 各データソース | `generateMetadata`、sitemap、構造化データで利用する |

### 1.5 Static Export 制約

| 制約 | 対応 |
|---|---|
| サーバーランタイムを前提にできない | Notion / Shopifyの商品ページ生成はビルド時に実行する |
| 動的ルートを事前生成する必要がある | `generateStaticParams` で記事slug、カテゴリslug、商品handle、Collection handleを生成する |
| Notion更新が即時反映されない | schedule / workflow_dispatch / push による再ビルドで反映する |
| Shopify商品更新が即時反映されない | 商品ページは再ビルドで反映し、価格・販売可否・Cartは実行時に再確認する |
| API Routesを使えない | 問い合わせは外部PHP APIへPOSTする |
| Notion画像URLが期限付き | 公開HTMLにはNotion URLを直接埋め込まず、生成済み画像を参照する |

### 2.2 実装上の変更点

現状の `web/` には `/products/[slug]` が存在する。オリジナル案では Shopify Product `handle` を正本にするため、実装時は `/products/[handle]` として扱う。ファイル名は `web/src/app/products/[handle]/page.tsx` に変更するか、既存 `[slug]` を内部的にhandleとして扱う場合でもドキュメント、型、変数名を `handle` に統一する。

現状の `web/` には `/blog`、`/cart`、`/shipping`、`/returns`、`not-found.tsx` が未作成である。フェーズ2以降で追加する。

### 2.3 ルーティング規則

| 対象 | 規則 |
|---|---|
| ブログ詳細slug | Notion `Slug` を正本とし、公開後は原則変更しない |
| ブログカテゴリslug | Notion表示名とは分離し、URLは英数字のslugを使う |
| お知らせ | 独立した `/news` を作らず、`/blog/category/news` に統合する |
| 商品詳細handle | Shopify Product `handle` を正本とする |
| 商品カテゴリhandle | Shopify Collection `handle` を正本とする |
| 商品カテゴリURL | 商品詳細との競合回避のため `/products/category/[handle]` とする |
| カート | `/cart` はnoindex相当とし、sitemapには含めない |
| 古民家詳細 | 初期リリースでは `/kominka/access`、`/kominka/experience` を独立させない |
| FAQ | 初期リリースでは `/faq` を独立させず、必要ページ内のセクションとして扱う |

### 2.4 canonical / trailingSlash

canonicalは `NEXT_PUBLIC_SITE_URL` とルートパスから生成する。`trailingSlash` の最終設定は実装時に `next.config.mjs` とConoHa配信挙動を確認して確定する。確定後は、内部リンク、canonical、sitemap、パンくず、構造化データを同一方針に統一する。

## 3. 画面詳細設計

### 3.1 トップページ `/`

| セクション | 主データ | 表示内容 | 備考 |
|---|---|---|---|
| Hero | 静的データ | ブランドコピー、主要ビジュアル、商品 / ブログ / 古民家導線 | `web_mock/` の表現を移植 |
| Brand Intro | 静的データ | ブランドの短い紹介、コンセプト導線 | `/about` または `/concept` へ誘導 |
| Featured Products | Shopify Products | 注目商品3から6件 | featured対象の決め方はShopify tag / collection / 静的設定から選ぶ |
| Latest Articles | Notion記事 | 新着ブログ3件程度 | `Status = Published` のみ |
| News Pickup | Notion記事 | お知らせ3から5件 | `Category = news` |
| Farm Banner | 静的データ | 畑紹介の要約 | `/farm` へ誘導 |
| Kominka Banner | 静的データ | 古民家紹介の要約 | `/kominka` へ誘導 |
| Footer CTA | 固定 | 商品一覧、問い合わせ、古民家予約導線 | ページ下部導線 |

仕様:

- Notion / Shopify取得に失敗した場合はビルドを失敗させ、古い成果物を維持する
- トップに表示する商品と記事は公開中データのみとする
- 商品価格はビルド時点の表示であり、購入時はShopify Checkoutの値を正本とする

### 3.2 ブランド / コンセプト / 畑

| ページ | セクション | 主データ |
|---|---|---|
| `/about` | Hero、ブランド概要、運営者紹介、商品 / ブログ導線 | 静的データ |
| `/concept` | Hero、理念、価値観、商品 / 畑導線 | 静的データ |
| `/farm` | Hero、畑紹介、写真、栽培背景、所在地または地域説明 | 静的データ |

仕様:

- 本文は初期リリースでは静的データで管理する
- 写真は `public/` 配下の静的素材または `web_mock/` から移植した素材を使う
- 主要画像はCSS背景ではなく、可能な限り `img` / `picture` で表示し、altを設定する
- CTAはページ文脈に合わせて、商品、ブログ、問い合わせ、古民家へ誘導する

### 3.3 ブログ一覧 `/blog`

| 要素 | 仕様 |
|---|---|
| ソート | `PublishedAt` 降順 |
| 表示件数 | 初期は全件静的表示または12件単位。記事数増加時にページネーションを追加する |
| カード要素 | サムネイル、カテゴリ、タイトル、公開日、抜粋 |
| カテゴリ導線 | `CategoryNav` で `/blog/category/[category]` へ誘導 |
| お知らせ導線 | `/blog/category/news` |
| 構造化データ | 一覧ページ固有の `BreadcrumbList` を出力する |

記事数が少ない初期段階ではページネーションを必須にしない。ページネーションを導入する場合、Static Exportで生成可能な `/blog/page/[page]` 等のURL方針を別途確定する。

### 3.4 ブログカテゴリ `/blog/category/[category]`

| 要素 | 仕様 |
|---|---|
| 対象カテゴリ | Notionカテゴリslugに対応する記事 |
| 不正カテゴリ | 404を返す |
| お知らせ | `news` slugを固定で扱う |
| canonical | カテゴリURLを正規URLにする |
| sitemap | 公開記事が存在するカテゴリのみ含める |

カテゴリ表示名はNotion上の日本語名を使い、URLはslugを使う。カテゴリslugの対応表は `web/src/lib/content/categories.ts` などで管理する。

### 3.5 ブログ詳細 `/blog/[slug]`

| 要素 | 仕様 |
|---|---|
| Hero | タイトル、公開日、更新日、カテゴリ、アイキャッチ |
| 本文 | Notion Block変換結果を `NotionArticleBody` で表示 |
| 関連商品 | `RelatedProductSlugs` のShopify handleから表示 |
| 関連記事 | 同カテゴリまたはタグから最大3件 |
| 下部導線 | 商品一覧、古民家、問い合わせ |
| 構造化データ | `Article`、`BreadcrumbList` |

公開対象は `Status = Published` のみとする。`Published` 記事に必須項目欠落、slug重複、未対応ブロック、画像変換失敗がある場合はビルドエラーにする。

### 3.6 商品一覧 `/products`

| 要素 | 仕様 |
|---|---|
| 表示対象 | Shopifyで公開対象の商品 |
| カード要素 | 商品画像、商品名、価格、カテゴリ、販売可否、詳細導線 |
| カテゴリ導線 | Shopify Collections から生成 |
| 絞り込み | カテゴリ、価格帯、用途タグ、在庫有無を提供候補とする |
| 並び順 | 新着順、価格昇順、価格降順、推奨順 |
| GA4 | 商品カードクリックで `select_item` |

絞り込み・並び順は初期実装ではクライアント側の表示制御でよい。対象商品数が増え、SEO上の価値がある絞り込み条件のみ静的URL化を検討する。

### 3.7 商品カテゴリ `/products/category/[handle]`

| 要素 | 仕様 |
|---|---|
| 対象 | Shopify Collection `handle` |
| 表示内容 | Collection名、説明、所属商品一覧 |
| 不正handle | 404を返す |
| canonical | Collection URLを正規URLにする |
| sitemap | 公開対象Collectionのみ含める |

Collection説明文に薬機法・景品表示法上のリスクがある表現を含めないよう、Shopify運用時に確認する。

### 3.8 商品詳細 `/products/[handle]`

レイアウト:

```txt
[Breadcrumb]
[ProductGallery] [PurchasePanel]
                 - 商品名
                 - 価格
                 - 販売可否
                 - バリエーション選択
                 - 数量選択
                 - カート追加
                 - 配送 / 返品リンク
[ProductDetail]
  - 商品説明
  - 内容量
  - 原材料
  - 飲み方
  - 注意事項
[FAQ]
[RelatedProducts]
```

購買UI:

| 要素 | 仕様 |
|---|---|
| バリエーション選択 | Shopify Product variants / selectedOptionsを元に選択状態を管理する |
| 数量 | 1以上、在庫・販売可否に応じて制御する |
| カート追加 | `cartLinesAdd` を実行する |
| 在庫切れ | 購入不可表示とし、必要に応じて問い合わせ導線を出す |
| Checkout | 商品詳細から直接Checkoutせず、Cart経由を基本とする |

構造化データ:

- `Product` を出力する
- `Offer` はShopify価格を元に出力する
- `availability` は `availableForSale` を参照する
- ビルド時点の値であることを踏まえ、Cart操作時はShopify正本で再確認する

### 3.9 カート `/cart`

| 要素 | 仕様 |
|---|---|
| Cart ID | `localStorage` 等に保存する |
| 明細表示 | 商品画像、商品名、バリエーション、単価、小計、数量 |
| 数量変更 | `cartLinesUpdate` |
| 削除 | `cartLinesRemove` |
| Checkout | `cart.checkoutUrl` へ遷移 |
| 空カート | 商品一覧への導線を表示 |
| SEO | sitemap対象外、noindex相当 |
| GA4 | Checkout遷移で `begin_checkout` |

カートにはカード情報、決済情報、注文情報を保持しない。保存するのはCart IDとUI復元に必要な最小限の状態に限定する。

### 3.10 古民家 `/kominka`

| セクション | 内容 |
|---|---|
| Hero | 古民家の紹介コピー、写真 |
| Overview | 施設概要 |
| Gallery | 写真ギャラリー |
| Access | 住所またはアクセス情報の要約 |
| Experience | 過ごし方、利用イメージ |
| Reservation | 外部予約サービスまたはFacebookへの導線 |
| Related Links | 商品、ブログ、問い合わせ |

構造化データは `LocalBusiness` を基本とする。宿泊提供が明確で、予約・料金・宿泊施設としての情報が整った場合のみ `LodgingBusiness` を再検討する。

### 3.11 お問い合わせ `/contact`

入力項目:

| 項目 | 型 | 必須 | 検証 |
|---|---|---|---|
| `category` | select | 必須 | 定義済み値のみ |
| `name` | text | 必須 | 1から50文字 |
| `email` | email | 必須 | メール形式 |
| `phone` | text | 任意 | 入力時のみ形式・長さを検証 |
| `message` | textarea | 必須 | 最大1,000文字 |
| `privacyConsent` | checkbox | 必須 | trueのみ送信可 |
| `honeypot` | hidden | 任意 | 値がある場合はbot扱い |

送信フロー:

```txt
1. ユーザーがフォーム入力
2. クライアント側で必須・形式を検証
3. NEXT_PUBLIC_CONTACT_API_URL へPOST
4. contact-api/でOrigin / Referer、honeypot、rate-limit、本文を検証
5. SMTPで運営者へ通知メール送信
6. 成功時は同一ページ内で完了状態へ切り替え
```

失敗時は理由を一般化して表示し、内部パス、シークレット、個人情報を画面に出さない。

### 3.12 法務固定ページ / 404

| ルート | 仕様 |
|---|---|
| `/shipping` | 配送条件、送料、発送目安。Shopify設定を正本とする要約 |
| `/returns` | 返品・交換条件、連絡方法。Shopify設定を正本とする要約 |
| `/legal` | 特定商取引法に基づく表記。Shopify設定と矛盾させない |
| `/privacy` | 個人情報、Cookie、GA4、問い合わせログ方針 |
| `/terms` | 利用規約。Shopify Checkout条件と矛盾させない |
| `404.html` | トップ、商品一覧、ブログ一覧への導線を持つ |

法務固定ページには `lastVerifiedAt` を持たせ、Shopify側設定や実運用条件との確認日を管理する。

## 4. コンポーネント詳細設計

### 4.1 レイアウト系

| コンポーネント | 種別 | 役割 |
|---|---|---|
| `Header` | Server + 一部Client | ロゴ、グローバルナビ、アイコンのみのカート導線、カート件数バッジ、SPメニュー |
| `Footer` | Server | サイトマップ、SNS、法務リンク |
| `Breadcrumb` | Server | パンくず表示、`BreadcrumbList` 生成補助 |
| `Section` | Server | 共通余白・背景・最大幅 |
| `PageHero` | Server | ページ冒頭ビジュアル |

カート件数とSPメニュー開閉はクライアントコンポーネントに分離する。カート件数は 99 点を超える場合 `99+` 表示を基本とする。

### 4.2 記事系

| コンポーネント | 種別 | 役割 |
|---|---|---|
| `ArticleCard` | Server | 記事一覧カード |
| `ArticleMeta` | Server | 公開日、更新日、カテゴリ、タグ |

`NotionArticleBody` はNotion APIレスポンスを直接受け取らず、公開サイト用の中間データを受け取る。

### 4.3 商品・カート系

| コンポーネント | 種別 | 役割 |
|---|---|---|
| `ProductCard` | Server | 商品一覧カード。商品画像クリックで商品詳細へ遷移 |

Shopify Storefront APIの呼び出しはコンポーネント内に散在させず、`lib/shopify` の関数経由に統一する。

### 4.4 フォーム・法務・共通UI

| コンポーネント | 種別 | 役割 |
|---|---|---|
| `ContactForm` | Client | 入力、検証、送信、完了状態 |
| `FieldError` | Client | 個別エラー表示 |
| `SubmitStateMessage` | Client | 送信結果表示 |
| `FaqList` | ClientまたはServer | FAQアコーディオン |
| `LegalContent` | Server | 法務文面表示 |
| `ReservationLinkButton` | Server | 古民家外部予約導線 |

### 4.5 コンポーネント設計原則

- UIは正規化済みの公開サイト用型を受け取り、外部APIレスポンス型に依存しない
- クライアントコンポーネントは、カート、フォーム、メニュー、ギャラリー、絞り込みなど操作が必要な箇所に限定する
- 薬機法・景品表示法に関わる表現はコンポーネント側で自動生成しない
- 商品価格・販売可否の最終判断はShopify正本に従う
- カートUIは決済情報を扱わない

### 6.1 実装配置案

```txt
web/src/lib/notion/
├── client.ts
├── queries.ts
├── transform-page.ts
├── transform-blocks.ts
├── validate.ts
├── images.ts
└── types.ts

web/src/lib/content/
├── articles.ts
├── categories.ts
└── site.ts

web/public/generated/notion/
└── <article-slug>/
    ├── cover-1200.webp
    ├── cover-ogp.jpg
    └── body-image-01-768.webp
```

### 6.2 取得フロー

```txt
1. 環境変数からNotion token / database idを読む
2. Databaseを問い合わせ、Status = Published の記事一覧を取得する
3. 必須プロパティ、slug重複、カテゴリslugを検証する
4. 詳細ページ用にPage / Block childrenを取得する
5. Blockを公開サイト用中間型へ変換する
6. 画像を取得し、WebP/JPEGへ変換する
7. 記事一覧、詳細、カテゴリ一覧、metadata、sitemapへ渡す
```

### 6.3 バリデーション

| 対象 | 条件 | Published時 |
|---|---|---|
| `Title` | 空でない | エラー |
| `Slug` | 空でない、英数字・ハイフン推奨、重複なし | エラー |
| `Status` | `Draft` または `Published` のいずれかであること（それ以外の値はエラー） | エラー |
| `PublishedAt` | 有効な日付 | エラー |
| `Category` | 定義済みカテゴリに正規化できる | エラー |
| `CoverImage` | 取得・変換できる | エラー |
| 本文ブロック | 初期対応ブロックのみ | エラー |
| `RelatedProductSlugs` | Shopify handleとして解決できる | Published記事では警告ログを出し、該当商品の関連商品表示から除外する。公開前確認で警告が残る場合は運用判断する |

### 6.4 カテゴリ正規化

| Notion表示名 | URL slug | 用途 |
|---|---|---|
| お知らせ | `news` | 告知、営業日、イベント |
| 読みもの | `story` | ブランド、畑、商品背景 |
| 商品のこと | `product` | 商品説明、飲み方、使い方 |

カテゴリ追加時は `categories.ts`、`generateStaticParams`、sitemap、ナビ表示、運用マニュアルを同時に更新する。

### 6.5 画像変換

| 項目 | 方針 |
|---|---|
| 取得元 | Notion files / external image URL |
| 保存先 | `web/public/generated/notion/<article-slug>/` |
| 本文画像 | WebPを主形式にし、必要に応じてJPEGを生成 |
| OGP | 1200x630 JPEGまたはPNG |
| 幅 | 480 / 768 / 1200 / 1600px程度 |
| 品質 | WebP quality 75から82を目安 |
| alt | Notionキャプション、専用プロパティ、文脈から設定 |
| 失敗時 | Published記事はビルドエラー |

HEICは初期非推奨とする。変換できない場合は投稿者へJPEG再アップロードを依頼する。

### 6.6 セキュリティ

- Notion API tokenは `NEXT_PUBLIC_` を付けない
- NotionのHTMLをそのまま公開しない
- rich textのリンクURLは `http` / `https` / 内部リンクを許可し、危険なスキームを除外する
- 画像URLは期限付きURLを公開HTMLへ直接出さない

### 8.2 リクエスト

```json
{
  "category": "product",
  "name": "山田 太郎",
  "email": "sample@example.com",
  "phone": "090-1234-5678",
  "message": "お問い合わせ本文",
  "privacyConsent": true,
  "honeypot": ""
}
```

### 8.3 レスポンス

成功:

```json
{
  "ok": true,
  "message": "お問い合わせを受け付けました。",
  "errorCode": null
}
```

失敗:

```json
{
  "ok": false,
  "message": "入力内容を確認してください。",
  "errorCode": "validation_error"
}
```

`errorCode`:

| 値 | 意味 |
|---|---|
| `validation_error` | 入力不備 |
| `origin_forbidden` | Origin / Referer不一致 |
| `spam_detected` | honeypot等でbot判定 |
| `rate_limited` | 送信頻度超過 |
| `mail_send_failed` | メール送信失敗 |
| `server_error` | その他サーバーエラー |

### 8.4 サーバー側検証

| 項目 | 方針 |
|---|---|
| Method | `POST` のみ許可 |
| Content-Type | `application/json` を基本 |
| Origin / Referer | `CONTACT_ALLOWED_ORIGINS` と照合 |
| category | 定義済み値のみ許可 |
| name | 1から50文字 |
| email | メール形式 |
| phone | 任意。入力時のみ形式・長さ確認 |
| message | 1から1,000文字。過剰なURLや制御文字を検出 |
| privacyConsent | true必須 |
| honeypot | 値があればspam扱い |

### 8.5 レート制御・ログ

| 項目 | 仕様 |
|---|---|
| キー | IP + User-Agentのハッシュ |
| 保存形式 | JSON |
| 保存先 | `CONTACT_RATE_LIMIT_DIR` |
| ファイル保存期間 | 7日を目安（期限切れファイルは送信時にクリーンアップ。`CONTACT_RATE_LIMIT_WINDOW` の集計ウィンドウとは別概念）|
| ログ保存先 | `CONTACT_LOG_DIR` |
| ログ本文 | 原則保存しない |
| 個人情報 | メールアドレス、電話番号はマスク |
| 保存期間 | 問い合わせログ90日、rate-limitファイル7日を目安 |

## 10. セキュリティ詳細

### 10.1 秘密情報

| 値 | 管理 |

| Notion API token | GitHub Secrets / CI環境変数。ブラウザ非公開 |

|---|---|

| `Permissions-Policy` | 不要なブラウザ機能を無効化 |
| `Content-Security-Policy` | Notion生成画像、Shopify CDN、GA4、外部予約、地図等を洗い出して段階導入 |

### 10.3 薬機法・景品表示法対応

- 商品説明、ブログ、SEO文案、AI生成文は公開前に人間が確認する
- 医薬的効能、治療効果、体質改善を断定する表現を避ける
- Notionで `Published` にした記事も、ビルド前レビューまたは運用ルールで表現確認する
- Shopifyの商品説明とmetafieldsも同じ確認対象にする

## 12. ビルド・デプロイ詳細

### 12.1 ビルドフロー

```txt
GitHub Actions
  ↓
環境変数 / Secrets 読み込み
  ↓
Notion記事一覧・詳細取得
  ↓
Notion Block変換・画像静的アセット化
  ↓
Shopify商品・Collection取得
  ↓
型検証・slug重複検出・未対応ブロック検出
  ↓
web/ build
  ↓
out/ 生成
  ↓
contact-api/ を同梱または別配置
  ↓
ConoHa WING へアップロード
```

### 12.2 デプロイ用環境ファイル

ConoHa WING へのデプロイ（FTP アップロード）には `env/.env.deploy` を使用する。このファイルには FTP 接続情報（ホスト、ユーザー名、パスワード、ポート、リモートディレクトリ、サイト URL）を定義する。

| 変数名 | 用途 |
|---|---|
| `DEPLOY_FTP_HOST` | FTP サーバーホスト名 |
| `DEPLOY_FTP_USER` | FTP ユーザー名 |
| `DEPLOY_FTP_PASSWORD` | FTP パスワード |
| `DEPLOY_FTP_PORT` | FTP ポート（省略時: 21）|
| `DEPLOY_REMOTE_DIR` | アップロード先リモートディレクトリ |
| `DEPLOY_SITE_URL` | デプロイ完了時の確認 URL |

注意事項:

- `env/.env.deploy` は Git 管理外（`.gitignore` で除外済み）とし、リポジトリへコミットしない
- GitHub Actions でデプロイを自動化する場合は、上記変数を GitHub Secrets として登録し、ワークフロー内で参照する
- FTP パスワード等の秘密情報はリポジトリ、チャット、ログ等に直接記録しない

### 12.3 トリガー

| トリガー | 用途 |
|---|---|
| `push` | コード、静的データ、設定変更を反映 |
| `schedule` | Notion更新、Shopify商品更新の定期反映 |
| `workflow_dispatch` | 運営または開発者による手動反映 |
| Notion Webhook | 初期対象外。即時反映が必要になった場合のみ検討 |
| Shopify Webhook | 初期対象外。商品更新の即時性が必要になった場合のみ検討 |

### 12.4 障害時

| 障害 | 対応 |
|---|---|
| Notion取得失敗 | ビルド失敗、デプロイ中止 |
| Notion必須項目欠落 | Publishedはビルド失敗 |
| Notion画像変換失敗 | Publishedはビルド失敗 |
| Shopify取得失敗 | ビルド失敗、デプロイ中止 |
| `web/` build失敗 | デプロイ中止 |
| contact-api配置失敗 | デプロイ中止または問い合わせ機能を非公開にしてGo判断 |
| Cart API障害 | 画面上で購入不可メッセージ、問い合わせ導線 |
| 問い合わせAPI障害 | 送信失敗メッセージ、代替連絡先表示 |

本番へ壊れた成果物を配信しない。直前の公開成果物を維持する。
