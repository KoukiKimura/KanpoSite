## 1. 基本方針

### 1.1 設計前提

- 公開サイトは `web/` アプリの `Next.js App Router` による静的サイトとして構築し、`ConoHa WING` の本番 / 検証環境へ配置する
- 本番公開環境では `Next.js Static Export` を前提とし、ISR、Server Actions、Route Handlers は使用しない
- 依頼者レビュー用のモックは `web_mock/` 別アプリで管理し、ダミーデータによる静的実装とする
- 初期リリースでは下書き確認専用の `preview/` 別アプリは作成しない。将来 `microCMS` 移行時に再検討する
- 初期リリースの本文系コンテンツは静的データで管理する
- `DecapCMS` はSEO補助情報専用とし、本文コンテンツ更新には使わない
- 商品主データ、価格、在庫、決済、注文管理は `BASE` を正本とする
- オリジナルサイトは `BASE` 商品ページへの外部リンク導線を提供し、サイト内カート・チェックアウトは実装しない
- 問い合わせフォームは静的サイト外の API 層で処理し、初期リリースは `ConoHa WING` 配下の `PHP` 問い合わせ API と `ConoHa` メール / SMTP を採用する
- フロント側は `NEXT_PUBLIC_CONTACT_API_URL` を介して問い合わせ API を呼び出し、必要時に `Vercel Functions + Resend` へ切り替え可能な構成とする

### 1.2 システム構成概要

```txt
利用者ブラウザ
  ↓
ConoHa WING Production / Staging
  ├─ web/ Static Export 成果物を配信
  └─ contact-api/ PHP API を実行
       └─ ConoHa メール / SMTP で通知

依頼者レビュー
  ↓
web_mock/ Static Mock App

GitHub Repository
  ├─ GitHub Actions で build / export / deploy を実行
  ├─ DEPLOY_ENV に応じて env ファイルを切り替える
  └─ ConoHa WING の本番 / 検証環境へ web/ + contact-api/ を配備

DecapCMS
  └─ SEO補助情報のみをGitベースで管理

BASE
  └─ 商品、価格、在庫、決済、注文、配送・返品等のEC運用条件を管理
```

### 1.3 システム責務

| レイヤー | 主な責務 |
|---|---|
| `Next.js` | 画面描画、ルーティング、HTML生成、SEOメタデータ、構造化データ、内部リンク最適化 |
| 静的データ | 初期リリースの本文、商品表示コピー、FAQ、古民家情報、トップ特集、法務固定ページ要約 |
| `DecapCMS` | `seo_page`、`site_settings` などSEO補助情報 |
| `BASE` | 商品主データ、価格、在庫、決済、注文、配送・返品・特商法等のEC運用条件 |
| `web_mock/` | フェーズ1〜2 のダミーデータモック、依頼者向けデザイン確認 |
| `contact-api/` | 問い合わせ受付、スパム対策、通知メール送信 |
| `ConoHa WING` | 本番 / 検証の静的ファイル配信、PHP 問い合わせ API 実行 |

### 1.4 Static Export 制約に対する基本方針

| 項目 | 方針 |
|---|---|
| 動的ページ | `generateStaticParams` で全ルートを事前生成する |
| コンテンツ更新 | 静的データまたは `DecapCMS` SEO補助情報の更新後、再ビルドで反映する |
| モック確認 | `web_mock/` をダミーデータによる静的モックとして実装する |
| 下書き確認 | 初期リリースでは対象外。将来 `microCMS` 移行時に `preview/` 要否を再検討する |
| 問い合わせ処理 | `NEXT_PUBLIC_CONTACT_API_URL` により本番 / 検証先を切り替える |
| 画像最適化 | `next/image` は `unoptimized` 前提、または通常の `img` を用途に応じて利用する |
| URL 正規化 | `trailingSlash: true` を採用し、内部リンク、canonical、sitemap を末尾スラッシュありで統一する |
| 404 対応 | `not-found.tsx` から生成される `404.html` を利用する |
| 検証環境 | `ConoHa WING Staging` で静的成果物、SEO補助情報、BASE外部リンク、問い合わせAPIを確認する |

## 2. サイトマップ

```txt
/ (トップページ)
├── /about (ブランド紹介)
├── /concept (コンセプト)
├── /farm (畑紹介)
├── /stories (ストーリー一覧)
│   └── /stories/[slug] (ストーリー詳細)
├── /news (お知らせ一覧)
│   └── /news/[slug] (お知らせ詳細)
├── /faq (FAQ)
├── /products (商品一覧)
│   ├── /products/category/[category] (商品カテゴリ一覧)
│   └── /products/[slug] (商品詳細)
├── /kominka (古民家紹介)
│   ├── /kominka/access (古民家アクセス)
│   └── /kominka/experience (古民家体験)
├── /contact (お問い合わせ)
├── /shipping (配送情報)
├── /returns (返品・交換)
├── /legal (特定商取引法に基づく表記)
├── /privacy (プライバシーポリシー)
├── /terms (利用規約)
└── 404.html
```

### 2.1 ルーティング設計上の注意

- 商品カテゴリと商品詳細の競合を避けるため、カテゴリ一覧は `/products/category/[category]` を正規ルートとする
- `/products/[slug]` の `slug` は静的商品データの `slug` を利用し、将来 `Shopify` 移行時は `handle` に切り替えられるようにする
- `/stories/[slug]`、`/news/[slug]` は静的データの `slug` を利用し、将来 `microCMS` 移行時も同じ契約を維持する
- 予約導線は独立ページを作らず、`/kominka` および `/kominka/experience` 内の外部リンクとして配置する
- サイト内 `/cart`、`/checkout` は作成しない
- Cookie とアクセス解析の利用方針は `/privacy` に含める

## 5. データ設計概要

### 5.1 データソース別責務

| データ領域 | 正本 | 主な利用ページ |
|---|---|---|
| 商品主データ、価格、在庫、決済、注文 | `BASE` | BASE商品ページ |
| 商品表示コピー | 静的データ | 商品一覧、商品カテゴリ、商品詳細、トップ |
| 商品FAQ | 静的データ（将来: microCMS） | 商品詳細、FAQ |
| 記事・お知らせ | 静的データ（将来: microCMS） | ストーリー一覧/詳細、お知らせ一覧/詳細、トップ |
| 畑・古民家情報 | 静的データ（将来: microCMS） | `/farm`、`/kominka` 系 |
| SEO補助情報 | `DecapCMS` | 全ページ |
| 法務・配送・返品要約 | 静的データ。EC運用条件は `BASE` 側を正本 | `/shipping`、`/returns`、`/legal`、`/terms` |
| 問い合わせ通知先 | 環境変数または PHP API 側設定 | `contact-api/` |

### 5.2 `DecapCMS` 管理対象

| 設定型 | 主な管理フィールド |
|---|---|
| `seo_page` | `path`, `seoTitle`, `seoDescription`, `ogpImage`, `canonical` |
| `site_settings` | `siteName`, `siteDescription`, `ogpDefaultImage`, `logo`, `organizationName`, `organizationUrl`, `sameAs`, `socialLinks` |

`DecapCMS` 管理画面は `/admin/` 配下に配置する方針とし、Git backend、認証方式、編集可能ユーザー、更新先ブランチ、レビュー有無、手動ビルド手順は詳細設計で定める。

### 5.3 商品データ利用方針

| 項目 | 初期リリース | 将来 `Shopify` 移行時 |
|---|---|---|
| 商品一覧 | 静的商品データ | Storefront API / ビルド時取得 |
| 商品カテゴリ | 静的カテゴリ定義 | Shopify collection |
| 商品詳細 | 静的商品データ | Shopify product |
| 価格 | 価格目安として表示。正確な価格はBASE正本 | Shopify priceRange |
| 在庫 | サイト上では表示しない | Shopify availability |
| 購入導線 | BASE商品ページへの外部リンク | Shopify checkout またはカート導線 |

### 5.4 データ取得タイミング

| データ | 取得タイミング | 備考 |
|---|---|---|
| 静的本文データ | ビルド時 | リポジトリ内ファイルから参照 |
| 静的商品データ | ビルド時 | BASE正本からの表示コピー |
| `DecapCMS` SEO補助情報 | ビルド時 | Gitベースのファイルを参照 |
| BASE商品ページ | 実行時リンク遷移 | API連携は行わない |
| 問い合わせ送信 | 実行時 | `Contact API Layer` へ送信 |

## 7. 技術構成設計

| 技術 | 採用値 | 用途 |
|---|---|---|
| `Next.js` | `15.5.15` | フロントエンド、App Router |
| `React` | `^18.3.0` | UI 実装 |
| `TypeScript` | `5.x` | 型安全 |
| `Tailwind CSS` | `3.4.x` | スタイリング |
| `ESLint` | `8.x` | 静的解析 |
| `PHP` | `ConoHa WING` 提供バージョン | 問い合わせ API |
| `ConoHa メール / SMTP` | `ConoHa` 標準機能 | 問い合わせ通知メール |
| `Vercel Functions + Resend` | 切替候補 | 問い合わせ API / 通知基盤の代替構成 |

### 7.1 モック構成方針

| 項目 | 方針 |
|---|---|
| 実装形態 | `web_mock/` 別アプリ |
| 用途 | 依頼者向けのデザイン確認、導線確認 |
| データ | ダミーデータ固定。`DecapCMS` / `BASE` / `contact-api/` には接続しない |
| 描画方式 | `Next.js Static Export` |
| SEO | `robots.txt` と metadata で `noindex` |

### 7.2 問い合わせ API 設計方針

| 項目 | 方針 |
|---|---|
| 実行基盤 | `ConoHa WING` 配下の `PHP` |
| エンドポイント | `POST https://<domain>/contact-api/contact.php` |
| スパム対策 | `honeypot`、Origin / Referer 検証、送信頻度制御、サーバー側バリデーション |
| 通知方法 | `ConoHa` メール機能を利用し、SMTP 認証を優先 |
| 通知先 | 環境変数または PHP API 側設定 |
| ログ | 公開Webルート外に保存し、個人情報は最小限にする |
| 切替条件 | スパム増加、配信品質不足、保守負荷増大時は `Vercel Functions + Resend` に切り替える |

## 8. デプロイ・運用設計

### 8.1 デプロイ先

| 環境 | 配置先 | 役割 |
|---|---|---|
| 本番 | `ConoHa WING` 本番ドキュメントルート | 公開環境、PHP 問い合わせ API |
| 検証 | `ConoHa WING Staging` | static export、PHP 問い合わせ API、BASE外部リンク確認 |
| モック | `web_mock/` 確認URL | 依頼者向けデザイン確認 |

### 8.2 ビルド・デプロイフロー

```txt
web_mock/
  ↓
next build
  ↓
依頼者確認URLへ反映
```

```txt
DEPLOY_ENV=staging|production
  ↓
GitHub Actions
  ↓
対応する env ファイルを読込
  ↓
web/ build (Static Export)
  ↓
out/ 生成 + contact-api/ 同梱
  ↓
ConoHa WING へアップロード
```

### 8.3 Webhook / 手動ビルド

| トリガー | 実行内容 |
|---|---|
| `DecapCMS` SEO補助情報更新 | GitHub Actions の再ビルドワークフローを起動、または手動ビルド |
| 静的データ更新 | push / workflow_dispatch により再ビルド |
| BASE商品更新 | 初期リリースでは自動再ビルドなし。静的商品データを手動同期 |
| `workflow_dispatch` + `DEPLOY_ENV=staging` | 検証環境へ静的成果物 + PHP API を再配備 |
| `workflow_dispatch` + `DEPLOY_ENV=production` | 本番静的サイトを再ビルド |

### 8.4 障害時の方針

- ビルド失敗時はデプロイを中止し、直前の公開ファイルを維持する
- SEO設定ファイルの欠落、構文不正、必須項目不足がある場合はビルド時に検出する
- 問い合わせ API 障害時はフロント側で失敗メッセージを返し、代替連絡先を表示する
- `ConoHa` 側のメール送信失敗時は API ログに記録し、送信リトライは手動運用を基本とする
- BASE外部リンク先が未設定または不正な場合は、購入ボタンを非活性または問い合わせ導線へフォールバックする

## 9. SEO・セキュリティ実装方針

### 9.1 SEO 実装方針

| 項目 | 実装方針 |
|---|---|
| metadata | `generateMetadata` でページ単位に出力する |
| canonical | `NEXT_PUBLIC_SITE_URL` を基準に、末尾スラッシュありで生成する |
| OGP | `DecapCMS` または静的データから画像と文言を取得する |
| sitemap | ビルド時に生成し、末尾スラッシュありで統一する |
| robots.txt | `production` は `Allow: /`、`staging` と `web_mock` は `Disallow: /` |
| 構造化データ | `lib/schema` に集約し、ページごとに出力する |

### 9.2 構造化データ出力方針

| 対象 | 型 |
|---|---|
| 全ページ共通 | `WebSite`, `Organization` |
| パンくず表示ページ | `BreadcrumbList` |
| 商品詳細 | `Product`。`Offer` は静的データで価格整合性を担保できる商品に限る |
| ストーリー詳細 | `Article` |
| FAQ | `FAQPage` |
| 古民家 | `LocalBusiness`。宿泊提供が確定した場合は `LodgingBusiness` を再検討 |

### 9.3 セキュリティ実装方針

- セキュリティヘッダーは静的ホスティングに合わせて `.htaccess` または配信設定で付与する
- 問い合わせ API では `honeypot`、許可オリジン検証、送信頻度制御、送信内容のサーバー側バリデーションを必須とする
- 問い合わせログと送信頻度制御ファイルは公開ディレクトリ外の環境別保存先へ配置する
- 秘匿情報は環境変数のみで管理し、リポジトリへ含めない
- `NEXT_PUBLIC_` 付きの環境変数には公開可能な値のみを入れる
