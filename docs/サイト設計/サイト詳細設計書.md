## 1. 詳細設計前提

- 公開サイトは `web/` アプリで実装し、`Next.js Static Export` により `ConoHa WING` の本番 / 検証環境へ配備する
- 依頼者レビュー用のモックは `web_mock/` 別アプリで実装し、ダミーデータによる静的表示に限定する
- 下書き確認は `preview/` 別アプリで実装し、`Vercel` 上の server-side runtime で運用する
- 記事、FAQ、畑、古民家、共通設定は `microCMS` を正本とする
- 商品、価格、在庫、カート、チェックアウトは `Shopify` を正本とする
- 問い合わせは `contact-api/` 配下の `PHP` API で処理し、通知先は `microCMS` の `site_settings.contactEmail` を正本とする
- フェーズ1では独自 `/cart`、`/checkout` ページを作らず、ヘッダーの `CartDrawer` と `Shopify checkout` で購入導線を構成する

### 1.1 アプリ構成

| アプリ / モジュール | 役割 | 実行基盤 |
|---|---|---|
| `web_mock/` | 依頼者確認用の静的モック、ダミーデータ表示 | `Vercel` |
| `web/` | 公開サイト本体、静的HTML生成、SEO出力 | `ConoHa WING` |
| `preview/` | 下書き確認、preview URL 受け口 | `Vercel` |
| `contact-api/` | 問い合わせ送信、レート制御、通知メール送信 | `ConoHa WING` |

補足:
プロジェクトルートの `api/` ディレクトリはフェーズ1では使用しない予約領域とし、問い合わせ API は独立した `contact-api/` ディレクトリで管理する。`web_mock/` はモック確認専用、`preview/` は `microCMS` 下書き確認専用とし、用途を混在させない。

### 1.2 環境構成

| 環境 | 配備対象 | 用途 |
|---|---|---|
| `mock_review` | `web_mock/` | 依頼者向けデザイン確認 |
| `production` | `web/` + `contact-api/` | 本番公開 |
| `staging` | `web/` + `contact-api/` | 結合確認、問い合わせ送信確認、カート確認 |
| `preview` | `preview/` | 下書き確認、表示確認 |

### 2.1 preview ルート

`preview/` アプリは本番と同じ情報設計で確認できるよう、以下の preview 専用ルートを持つ。

| ルート | 対象 |
|---|---|
| `/preview/story/[slug]` | `story` |
| `/preview/news/[slug]` | `news` |
| `/preview/page/[pageKey]` | `home`, `about`, `concept`, `farm`, `faq`, `kominka`, `kominka_access`, `kominka_experience` |
| `/preview/health` | 動作確認用 |

補足:

- `pageKey=home` はトップページ全体を描画するが、draft 差し替え対象は `site_settings`, `top_feature`, `farm_page`, `kominka_page` に限定する
- `contentType=top_feature|farm_page|kominka_page` の下書き確認では `contentId=<microCMS content id>` をクエリで受け取り、対象 draft 項目のみを公開中構成へ差し替えて描画する
- `pageKey=faq` では `contentType=faq` と `contentId=<microCMS content id>` をクエリで受け取り、対象 draft FAQ を同カテゴリ一覧へ差し替えて描画する
- `pageKey=about|concept|farm|kominka|kominka_access|kominka_experience` では `contentType` と `contentId` を使わず、対応するシングルコンテンツを `draftKey` 付きでそのまま描画する
- `story` と `news` のトップ掲載枠は最新の公開済みデータを使い、未公開 draft は各詳細 preview ルートで確認する
- 注目商品は `Shopify` に下書き概念を持たないため、home preview でも公開済み商品データを使う

`microCMS` の preview URL は、対象コンテンツに応じて上記ルートへ接続し、`secret`、`draftKey`、必要に応じて `contentType` と `contentId` をクエリで渡す。

### 2.2 `web_mock/` ルート

`web_mock/` はフェーズ1〜2 の依頼者レビュー用アプリとし、主要レビュー対象のみをダミーデータで実装する。

| ルート | 用途 |
|---|---|
| `/` | トップページモック |
| `/products` | 商品一覧モック |
| `/products/[slug]` | 商品詳細モック |
| `/kominka` | 古民家モック |
| `/contact` | お問い合わせモック |

補足:

- `web_mock/` は `microCMS`、`Shopify`、`contact-api/` には接続しない
- ダミーデータは `web_mock/src/lib/mock/` 配下の JSON または TypeScript 定数で管理する
- `preview/` のような `secret`、`draftKey`、preview token 検証は持たない

## 3. 画面詳細設計

## 3.1 トップページ（`/`）

### セクション構成

| # | セクション | 主データ | 内容 |
|---|---|---|---|
| 1 | Hero | `site_settings.homeHeroTitle`, `site_settings.homeHeroLead`, `site_settings.homeHeroImage` | ブランドコピー、主導線 |
| 2 | Brand Intro | `site_settings.homeIntroText` | ブランドの短い説明 |
| 3 | Top Feature | `top_feature` | 特集バナー、任意複数件 |
| 4 | Featured Products | `Shopify` | 注目商品 3〜6件 |
| 5 | Stories Pickup | `story` | 新着記事 3件程度 |
| 6 | News Pickup | `news` | お知らせ 3〜5件 |
| 7 | Farm Banner | `farm_page` | 畑紹介への導線 |
| 8 | Kominka Banner | `kominka_page` | 古民家紹介への導線 |
| 9 | Footer CTA | 固定 | 商品一覧または古民家導線 |

### UI仕様

- Hero は PC で大判、SP で縦長表示とする
- 特集は `expiresAt` を過ぎた項目をビルド時判定で非表示にする
- `expiresAt` 到達後に即時で非表示化したい場合は、運営者が `microCMS` 側で対象特集を非公開にする
- 注目商品は `Shopify` 側の対象 collection または指定 handles で制御する
- 各一覧カードは本文全文を出さず、タイトル、日付、サムネイルに絞る
- トップページ固有のヒーロー文言と導入文は `site_settings` のホーム用フィールドから取得する
- `preview/page/home` の draft 差し替え対象は `site_settings`, `top_feature`, `farm_page`, `kominka_page` とし、記事・お知らせ・商品は公開済みデータを併用する

## 3.2 ブランド / コンセプト / 畑（`/about`, `/concept`, `/farm`）

| ページ | セクション |
|---|---|
| `/about` | Hero、ブランド概要、代表メッセージ、ストーリー導線 |
| `/concept` | Hero、理念、価値観、商品 / 畑への導線 |
| `/farm` | Hero、本文、写真ギャラリー、栽培背景、地図または所在地 |

### 共通仕様

- 写真ギャラリーは画像の縦横比を固定しすぎず、PC / SP でレイアウトを切り替える
- CTA は `商品を見る`、`ストーリーを見る` のように文脈依存で出し分ける

## 3.4 FAQ（`/faq`）

### 表示仕様

- `category` 単位でセクションを分ける
- 各項目はアコーディオン UI とする
- 商品詳細ページから遷移した場合は、該当商品の FAQ を先頭に表示できる構造にする
- `preview/page/faq?contentType=faq&contentId=...` では対象 draft FAQ を同カテゴリ一覧へ差し替えて確認する

### カテゴリ定義

| 値 | 用途 |
|---|---|
| `product` | 商品全般 |
| `shipping` | 配送 |
| `kominka` | 古民家 |
| `other` | その他 |

## 3.6 商品詳細（`/products/[slug]`）

### レイアウト

```txt
[Breadcrumb]
[ProductGallery] [PurchasePanel]
                 - title
                 - short description
                 - price
                 - stock
                 - quantity stepper
                 - Add to Cart
                 - Buy Now
                 - shipping / returns links
[DetailSection]
  - 詳細説明
  - 内容量
  - 原材料
  - 飲み方
  - 注意事項
[FAQ]
[RelatedProducts]
```

### 購買UI

| 要素 | 仕様 |
|---|---|
| `Add to Cart` | 現在商品を `Shopify cart` に追加し、`CartDrawer` を開く |
| `Buy Now` | 現在商品を cart に反映後、そのまま `checkoutUrl` へ遷移する |
| 数量 | 1 以上、在庫切れ時は非活性 |
| 在庫表示 | `availableForSale` を基準とする |

### FAQ / 関連商品

- FAQ は `microCMS faq.relatedProductSlug` で抽出する
- 関連商品は `metafields.details.related_products` を優先し、未設定時は同カテゴリ collection から補完する

### 構造化データ

- `Product`
- `Offer`
- `BreadcrumbList`

## 3.8 お問い合わせ（`/contact`）

### 入力項目

| 項目 | 型 | 必須 | 備考 |
|---|---|---|---|
| `category` | select | 必須 | 商品 / 配送 / 古民家 / その他 |
| `name` | text | 必須 | 1〜50 文字 |
| `email` | email | 必須 | RFC 準拠の形式検証 |
| `phone` | text | 任意 | 数字、`-`、空白を許可。10〜15 文字以内 |
| `message` | textarea | 必須 | 10〜1000 文字 |
| `privacyConsent` | checkbox | 必須 | 送信前同意 |
| `honeypot` | hidden | 任意 | bot 判定用 |
| `recaptchaToken` | hidden/runtime | 任意 | `reCAPTCHA v3` 有効時のみ送信する |

### 送信フロー

```txt
1. フロント入力
2. `React Hook Form` + `Zod` で検証
3. `reCAPTCHA v3` を有効化している環境ではトークンを取得する
4. `NEXT_PUBLIC_CONTACT_API_URL` へ POST
5. `contact-api/` で `privacyConsent` / Origin / honeypot / rate-limit / 本文検証を行う
6. `reCAPTCHA v3` を有効化している環境では Google Verify API でトークン検証を行う
7. `microCMS site_settings.contactEmail` を取得
8. SMTP で通知メール送信
9. 成功メッセージを表示
```

### 完了UI

- サンクスページは作らず、同一ページ内で完了状態へ切り替える
- 失敗時はエラー理由を一般化して表示し、代替連絡先リンクを併記する

## 6. CartDrawer 詳細設計

### 6.1 状態管理

| 項目 | 保持先 |
|---|---|
| `cartId` | `localStorage` |
| `lineItems` | React state |
| `itemCount` | `localStorage` + React state |
| `subtotalAmount` | `localStorage` + React state |
| `checkoutUrl` | `Shopify cart` レスポンス |

補足:

- `localStorage` には `cartId` と件数サマリーのみを保存し、`lineItems` は永続化しない
- `lineItems` は `CartDrawer` 表示時またはカート変更 API 成功時に `Shopify cart` レスポンスから React state を更新する
- 初回表示時に `cartId` のみ存在し `lineItems` が未取得の場合は、`CartDrawer` オープン時に `Shopify cart` を再取得する

### 6.2 ローカル保存キー

| キー | 用途 |
|---|---|
| `kanpo_cart_id` | `Shopify cartId` |
| `kanpo_cart_summary` | 件数、金額、更新時刻、有効期限 |

有効期限:
`kanpo_cart_summary` の TTL は 7 日間とする。ページロード時またはカート操作開始時に `updatedAt` を確認し、TTL を超過している場合は `kanpo_cart_id` と `kanpo_cart_summary` を破棄して新規 cart を作成する。

### 6.3 操作仕様

| 操作 | 処理 |
|---|---|
| ドロワー表示 | `lineItems` 未保持かつ `cartId` がある場合は `Shopify cart` を取得して一覧描画 |
| カート追加 | cart がなければ作成、あれば line item 追加し、返却 cart で `lineItems` とサマリーを更新 |
| 数量変更 | line item 更新後、返却 cart で `lineItems` とサマリーを更新 |
| 商品削除 | line item 削除後、返却 cart で `lineItems` とサマリーを更新 |
| checkout | `checkoutUrl` へ遷移 |
| 失敗時 | トーストまたはインラインで再試行案内 |

### 6.4 フォールバック

- `Shopify` カート API が失敗した場合は、`Shopify` ストアへの直接リンクを表示する
- `cartId` が不正な場合は localStorage を破棄して再作成する
- TTL 超過時は API エラーを待たずに localStorage を破棄して再作成する

## 7. preview アプリ詳細設計

### 7.1 認証 / 保護

| 項目 | 仕様 |
|---|---|
| Basic 認証 | `PREVIEW_BASIC_AUTH_USER`, `PREVIEW_BASIC_AUTH_PASSWORD` |
| preview secret | `PREVIEW_SECRET` |
| noindex | 全レスポンスで付与 |

`PREVIEW_SECRET` 検証フロー:

1. `microCMS` の preview URL から `?secret=xxx&draftKey=yyy` を受け取り、一覧系・トップページ特集の preview では必要に応じて `contentType`、`contentId` も受け取る
2. `secret` を `PREVIEW_SECRET` と照合する
3. 一致時のみ `draftKey` 付きで `microCMS` へアクセスする
4. `pageKey=home` かつ `contentType=top_feature|farm_page|kominka_page` の場合は、公開中トップページ構成へ対象 draft 項目のみを差し替えて描画する
5. `pageKey=home` かつ `contentType` 未指定または `site_settings` の場合は、`site_settings` シングルコンテンツを `draftKey` 付きで取得する
6. `pageKey=faq` かつ `contentType=faq` の場合は、公開中 FAQ 一覧へ対象 draft FAQ のみを差し替えて描画する
7. 不一致時は 403 または 404 を返す

### 7.2 取得方式

- `preview/` は server-side runtime で `microCMS` から都度取得する
- クエリの `draftKey` を付けて未公開データを取得する
- `secret` クエリが `PREVIEW_SECRET` と一致しない場合は `draftKey` を利用しない

`pageKey` と `microCMS` の対応:

| `pageKey` | 取得対象 | クエリ契約 |
|---|---|---|
| `home` | 公開済みトップ構成 + `site_settings` または対象 draft | `contentType=top_feature|farm_page|kominka_page` と `contentId` を条件付きで利用 |
| `about` | `about_page` | `contentType` / `contentId` は受け取らない |
| `concept` | `concept_page` | `contentType` / `contentId` は受け取らない |
| `farm` | `farm_page` | `contentType` / `contentId` は受け取らない |
| `faq` | 公開済み FAQ 一覧 + 対象 draft FAQ | `contentType=faq` と `contentId` を条件付きで利用 |
| `kominka` | `kominka_page` | `contentType` / `contentId` は受け取らない |
| `kominka_access` | `kominka_access` | `contentType` / `contentId` は受け取らない |
| `kominka_experience` | `kominka_experience` | `contentType` / `contentId` は受け取らない |

- `pageKey=home` は公開済みのトップページ構成を基準に描画し、draft 差し替えは `site_settings`, `top_feature`, `farm_page`, `kominka_page` のみに限定する
- `pageKey=about|concept|farm|kominka|kominka_access|kominka_experience` は対応する single content を `draftKey` 付きで直接取得して描画する
- `pageKey=faq` は公開済み FAQ 一覧を基準に描画し、`contentType=faq` 指定時のみ対象 draft FAQ を同カテゴリ一覧へ差し替える
- `story` と `news` は home preview では公開済み一覧を使い、未公開データ確認は `/preview/story/[slug]`, `/preview/news/[slug]` に分離する
- 注目商品は `Shopify` の公開済みデータを参照し、preview 専用の差し替えは行わない
- `web/` と同じ見た目に揃えるが、実装は別アプリとして独立させる

### 7.3 エラー仕様

| ケース | 挙動 |
|---|---|
| `secret` 不正 | 403 または 404 |
| `draftKey` 不正 | 404 または権限エラー表示 |
| `contentType` 不正 | 400 |
| `contentId` 不正 | 404 |
| `pageKey` に対して不要な `contentType` / `contentId` が付与されている | 400 |
| コンテンツ未存在 | 404 |
| `microCMS` 障害 | 一時エラー画面 |

## 8. contact-api 詳細設計

### 8.1 ディレクトリ構成

`contact-api/` はプロジェクトルート直下の独立ディレクトリであり、既存の `api/` ディレクトリとは別管理とする。

```txt
contact-api/
├── public/contact.php
├── src/bootstrap.php
├── src/microcms.php
├── src/validator.php
├── src/rate-limit.php
├── src/mailer.php
├── config/production.php
├── config/staging.php
└── var/
    ├── production/
    │   ├── logs/
    │   └── rate-limit/
    └── staging/
        ├── logs/
        └── rate-limit/
```

補足:

- `src/bootstrap.php` は `DEPLOY_ENV` を参照し、`config/production.php` または `config/staging.php` を読み込む
- `src/microcms.php` は `CONTACT_MICROCMS_SERVICE_DOMAIN` と `CONTACT_MICROCMS_READ_API_KEY` を使い、`site_settings.contactEmail` を read-only 取得する

### 8.2 リクエスト仕様

```json
{
  "category": "product",
  "name": "山田 太郎",
  "email": "sample@example.com",
  "phone": "090-1234-5678",
  "message": "お問い合わせ本文",
  "privacyConsent": true,
  "honeypot": "",
  "recaptchaToken": "optional-token"
}
```

`privacyConsent` は `true` を必須とし、未送信または `false` の場合は `400` を返す。

### 8.3 レスポンス仕様

```json
{
  "ok": true,
  "message": "お問い合わせを受け付けました。",
  "errorCode": null
}
```

失敗時レスポンス例:

```json
{
  "ok": false,
  "message": "入力内容を確認してください。",
  "errorCode": "validation_error"
}
```

`errorCode` 一覧:

- `validation_error`: 必須項目不足、形式不正、`privacyConsent=false`
- `origin_forbidden`: 許可オリジン外
- `spam_detected`: honeypot 検出、`reCAPTCHA` 検証失敗
- `rate_limited`: レート制限
- `settings_not_found`: `site_settings.contactEmail` 未設定または取得失敗
- `mail_send_failed`: SMTP 送信失敗

UI 方針:

- `message` はそのまま画面表示できる一般化メッセージとして扱う
- フロント側の分岐や再試行制御は `errorCode` を基準に行う

### 8.4 ステータスコード

| コード | 条件 |
|---|---|
| `200` | 送信成功 |
| `400` | 入力エラー、`privacyConsent` 未送信または `false` |
| `403` | 許可オリジン外、honeypot 検出、`reCAPTCHA` 検証失敗 |
| `429` | レート制限 |
| `500` | `microCMS` 取得失敗、`site_settings.contactEmail` 未設定、SMTP 送信失敗 |

### 8.5 レート制御

- キーは `IP + User-Agent` のハッシュで生成する
- 保存形式は `json`
- 保存先は `CONTACT_RATE_LIMIT_DIR`
- 期限切れファイルは送信時に簡易クリーンアップする
- 問い合わせ通知先の取得には `CONTACT_MICROCMS_READ_API_KEY` を利用し、`site_settings.contactEmail` 以外の更新権限は持たせない
- `CONTACT_RECAPTCHA_SECRET_KEY` が設定されている場合のみ Google Verify API による `reCAPTCHA v3` 検証を行う

### 8.6 ログ

| 項目 | 仕様 |
|---|---|
| 保存先 | `CONTACT_LOG_DIR` |
| ファイル名 | `YYYY-MM-DD.log` |
| 記録対象 | 成功、入力エラー、スパム判定、SMTP 失敗 |
| マスク | メールアドレス、電話番号は一部マスク |

## 9. SEO / 構造化データ / 計測

### 9.1 metadata

| ページ種別 | title 例 |
|---|---|
| トップ | `{siteName}` |
| 商品一覧 | `商品一覧 | {siteName}` |
| 商品カテゴリ | `{カテゴリ名} | 商品一覧 | {siteName}` |
| 商品詳細 | `{商品名} | {siteName}` |
| 記事詳細 | `{記事タイトル} | {siteName}` |
| 古民家 | `古民家 | {siteName}` |

生成規則:

- `description` は `seoDescription` を最優先とし、未設定時は `summary` または本文冒頭、さらに未設定時は `site_settings.siteDescription` を使用する
- `canonical` は `NEXT_PUBLIC_SITE_URL + pathname + '/'` を基準に生成し、`trailingSlash: true` 前提で末尾スラッシュありに統一する
- クエリ付き一覧やクライアント絞り込み状態は canonical に含めず、正規 URL は静的ルートへ固定する
- `og:image` は `ogpImage` を最優先とし、未設定時はページ hero 画像、さらに未設定時は `site_settings.ogpDefaultImage` を使用する
- `sitemap.xml` はビルド時に生成し、静的固定ページ、`microCMS` 動的ページ、`Shopify` 動的ページを含め、`preview/` ルートと `404.html` は除外する
- `robots.txt` はビルド成果物として生成し、`DEPLOY_ENV=production` では `Allow: /` と `Sitemap: {NEXT_PUBLIC_SITE_URL}/sitemap.xml` を出力し、`DEPLOY_ENV=staging` では `Disallow: /` を出力する
- `preview/` は `robots.txt` に依存せず、全レスポンス `noindex` と Basic 認証で保護する
- `web_mock/` は依頼者レビュー専用のため、`noindex` とし、本番 SEO の対象に含めない
