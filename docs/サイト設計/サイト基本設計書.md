## 1. 基本方針

### 1.1 設計前提

- 本設計書は `サイト要件定義書.md` v1.4.3 を正本として作成する
- 公開サイトは `web/` アプリの `Next.js App Router` による静的サイトとして構築し、`ConoHa WING` の本番 / 検証環境へ配置する
- 依頼者レビュー用のモックは `web_mock/` 別アプリで管理し、ダミーデータによる静的実装とする
- 公開サイトとは別に、運営者確認用の `preview/` 別アプリを `Vercel` 上に構築する
- コンテンツ管理は `microCMS`、商品・価格・在庫・購入導線は `Shopify` を正本とする
- 本番公開環境では `Next.js Static Export` を前提とし、ISR、Server Actions、Route Handlers は使用しない
- 問い合わせフォームは静的サイト外の API 層で処理し、フェーズ1は `ConoHa WING` 配下の `PHP` 問い合わせ API と `ConoHa` メール機能を採用する
- フロント側は `NEXT_PUBLIC_CONTACT_API_URL` を介して問い合わせ API を呼び出し、必要時に `Vercel Functions + Resend` へ切り替え可能な構成とする
- デプロイ先は `DEPLOY_ENV=production|staging` に応じて切り替え、本番 / 検証環境へ配備する

### 1.2 システム構成概要

```txt
利用者ブラウザ
  ├─ 本番閲覧
  │    ↓
  │  ConoHa WING Production
  │    ├─ web/ Static Export の成果物を配信
  │    └─ PHP 問い合わせAPIを実行
  │         └─ ConoHa メール / SMTP で通知
  │
  ├─ 検証閲覧
  │    ↓
  │  ConoHa WING Staging
  │    ├─ web/ Static Export の成果物を配信
  │    └─ PHP 問い合わせAPIを実行
  │         └─ ConoHa メール / SMTP で通知
  │
  ├─ 依頼者モック確認
  │    ↓
  │  Vercel Mock App
  │    └─ web_mock/ Static Mock App
  │
  └─ 運営者確認 / 下書き確認
       ↓
     Vercel Preview App
       └─ preview/ server-side runtime アプリ

GitHub Repository
  ├─ GitHub Actions で build / export / deploy を実行
  ├─ DEPLOY_ENV に応じて env ファイルを切り替える
  ├─ ConoHa WING の本番 / 検証環境へ web/ + contact-api/ を配備
  └─ Vercel と連携して web_mock/ と preview/ をデプロイ

microCMS
  └─ ストーリー、お知らせ、FAQ、畑、古民家、トップ特集、共通設定を管理

Shopify
  └─ 商品、コレクション、価格、在庫、チェックアウトを管理

切替候補
  └─ 問い合わせAPIは必要時に `Vercel Functions + Resend` へ移行可能
```

### 1.3 システム責務

| レイヤー | 主な責務 |
|---|---|
| `Next.js` | 画面描画、ルーティング、HTML生成、SEOメタデータ、構造化データ、内部リンク最適化 |
| `web_mock/` | フェーズ1〜2 のダミーデータモック、依頼者向けデザイン確認 |
| `microCMS` | 記事系コンテンツ、FAQ、畑、古民家、トップ特集、サイト共通設定 |
| `Shopify` | 商品主データ、価格、在庫、コレクション、カート、チェックアウト、注文管理 |
| `ConoHa WING` | 本番 / 検証の静的ファイル配信、PHP 問い合わせ API 実行 |
| `Vercel Preview App` | `preview/` 別アプリによる下書き確認、preview URL 提供 |
| `Contact API Layer` | 問い合わせ受付、スパム対策、通知メール送信。フェーズ1は `ConoHa PHP`、必要時に `Vercel Functions` へ切り替える |

### 1.4 Static Export 制約に対する基本方針

| 項目 | 方針 |
|---|---|
| 動的ページ | `generateStaticParams` で全ルートを事前生成する |
| コンテンツ更新 | `microCMS` / `Shopify` の Webhook を契機に再ビルドする。反映はビルド完了後であり即時ではない |
| モック確認 | `web_mock/` 別アプリをダミーデータによる静的モックとして実装し、`preview/` と役割を混在させない |
| 下書き確認 | 本番静的サイトでは行わず、`preview/` 別アプリ上で確認する |
| 問い合わせ処理 | フェーズ1は `ConoHa WING` 配下の `PHP` endpoint を利用し、`NEXT_PUBLIC_CONTACT_API_URL` により本番 / 検証先を切り替える |
| 画像最適化 | `next/image` は `unoptimized` 前提、または通常の `img` を用途に応じて利用する |
| URL 正規化 | `trailingSlash: true` を採用し、内部リンク、canonical、sitemap を末尾スラッシュありで統一する |
| 404 対応 | `not-found.tsx` から生成される `404.html` を利用し、`ConoHa WING` 側のエラードキュメント設定と合わせる |
| プレビュー | `draftMode` 等の runtime 機能は本番静的サイトでは使わず、`preview/` 別アプリに限定する |
| 検証環境差分 | `preview/` は下書き確認、`ConoHa WING Staging` は静的成果物 + PHP 問い合わせ API + カート導線の結合確認に利用する |

## 2. サイトマップ

```txt
/ (トップページ)
├── /about (ブランド紹介)
├── /concept (コンセプト)
├── /farm (畑紹介)
├── /stories (ストーリー一覧)
│   └── /stories/[slug] (ストーリー詳細)
├── /news (お知らせ一覧)
│   └── /news/[slug] (お知らせ詳細)
├── /faq (FAQ)
├── /products (商品一覧)
│   ├── /products/category/[category] (商品カテゴリ一覧)
│   └── /products/[slug] (商品詳細)
├── /kominka (古民家紹介)
│   ├── /kominka/access (古民家アクセス)
│   └── /kominka/experience (古民家体験)
├── /contact (お問い合わせ)
├── /shipping (配送情報)
├── /returns (返品・交換)
├── /legal (特定商取引法に基づく表記)
├── /privacy (プライバシーポリシー)
├── /terms (利用規約)
└── 404.html (カスタム 404)
```

### 2.1 ルーティング設計上の注意

- 商品カテゴリと商品詳細の競合を避けるため、カテゴリ一覧は `/products/category/[category]` を正規ルートとする
- `/products/[slug]` の `slug` は `Shopify` の `handle` を利用する
- `/stories/[slug]`、`/news/[slug]` は `microCMS` の `slug` を利用する
- 予約導線は独立ページを作らず、`/kominka` および `/kominka/experience` 内の外部リンクとして配置する
- フェーズ1では `/cart`、`/checkout` の自社ページは作成しない

## 4. 情報設計・導線設計

### 4.1 主要導線

```txt
トップ
  ├─ 注目商品 → 商品詳細 → カート追加 / Shopify checkout

  ├─ お知らせ一覧 → お知らせ詳細
  ├─ 畑紹介
  └─ 古民家紹介 → 体験案内 / 予約リンク

商品一覧
  ├─ 商品カテゴリ一覧
  └─ 商品詳細 → カート追加 → カートドロワー → 買い回り / Shopify checkout

  ├─ アクセス
  ├─ 体験案内
  └─ 外部予約リンク

  └─ 商品詳細やお問い合わせから相互遷移
```

## 5. データ設計概要

### 5.1 データソース別責務

| データ領域 | 正本 | 主な利用ページ |
|---|---|---|
| 商品情報 | `Shopify` | 商品一覧、商品カテゴリ一覧、商品詳細、トップ特集商品 |
| 商品FAQ | `microCMS` | 商品詳細、FAQ |
| 記事・お知らせ | `microCMS` | ストーリー一覧/詳細、お知らせ一覧/詳細、トップ |
| 畑・古民家情報 | `microCMS` | `/farm`、`/kominka` 系 |
| サイト共通設定 | `microCMS` | レイアウト、SEO初期値、連絡先 |
| 法務文面 | リポジトリ管理 | `/shipping`、`/returns`、`/legal`、`/privacy`、`/terms` |

### 5.2 `microCMS` コンテンツ型

| コンテンツ型 | 用途 | 主なフィールド |
|---|---|---|
| `story` | ストーリー記事 | `title`, `slug`, `body`, `publishedAt`, `seoTitle`, `seoDescription`, `ogpImage`, `relatedProductHandles` |
| `news` | お知らせ | `title`, `slug`, `body`, `publishedAt`, `seoTitle`, `seoDescription` |
| `faq` | FAQ | `question`, `answer`, `category`, `relatedProductSlug` |
| `farm_page` | 畑紹介 | `title`, `body`, `images` |
| `kominka_page` | 古民家紹介 | `name`, `description`, `images`, `address`, `reservationUrl` |
| `kominka_access` | アクセス情報（シングルコンテンツ型） | `address`, `mapEmbedUrl`, `parking`, `accessNote` |
| `kominka_experience` | 体験案内 | `title`, `body`, `images`, `reservationUrl` |
| `top_feature` | トップ特集 | `title`, `image`, `linkUrl`, `publishedAt`, `expiresAt` |
| `site_settings` | 共通設定 / トップ導入 | `siteName`, `siteDescription`, `homeHeroTitle`, `homeHeroLead`, `homeHeroImage`, `homeIntroText`, `ogpDefaultImage`, `logo`, `contactEmail`, `socialLinks` |

### 5.3 `Shopify` データ利用方針

| 項目 | データソース | 実装方針 |
|---|---|---|
| 商品一覧 | `products` | ビルド時に取得し静的生成する |
| 商品カテゴリ一覧 | `collections` | `handle` 単位で静的生成する |
| 商品詳細 | `product(handle)` | `handle` を `slug` として利用する |
| 価格・在庫 | `priceRange`, `availableForSale` | 基本はビルド時取得。リアルタイム性が必要ならクライアント更新を追加検討 |
| 関連商品 | `metafields.details.related_products` または collection | フェーズ4 開始前に方式を確定する |
| カート・チェックアウト | Storefront API | クライアントサイドでカート ID と line items を保持し、複数商品を跨いで利用できるカートドロワー経由で `Shopify checkout` に遷移する |

### 5.4 商品詳細データの実装方針

| 表示項目 | 主データソース | データ項目 / 方針 |
|---|---|---|
| 商品名 | `Shopify` | `title` |
| 短い説明 | `Shopify` | `metafields.details.short_description` |
| 詳細説明 | `Shopify` | `descriptionHtml` |
| 価格 | `Shopify` | `priceRange.minVariantPrice` |
| 在庫状況 | `Shopify` | `availableForSale` |
| 内容量 | `Shopify` | `metafields.details.volume` |
| 原材料 | `Shopify` | `metafields.details.ingredients` |
| 飲み方 | `Shopify` | `metafields.details.how_to_use` |
| 注意事項 | `Shopify` | `metafields.details.caution` |
| FAQ | `microCMS` | `relatedProductSlug` で商品と紐付ける |
| 関連商品 | `Shopify` | `metafields.details.related_products` または collection |

### 5.5 データ取得タイミング

| データ | 取得タイミング | 備考 |
|---|---|---|
| `microCMS` コンテンツ | ビルド時 | 再ビルドで反映 |
| `Shopify` 商品・コレクション | ビルド時 | 再ビルドで反映 |
| `Shopify` カート | クライアントサイド | `localStorage` に cart ID と直近サマリーを保持し、複数商品を跨いで維持する |
| 問い合わせ送信 | 実行時 | `Contact API Layer` へ送信。フェーズ1は `ConoHa PHP API` |

### 6.3 コンポーネント設計方針

- `layout`, `ui`, `article`, `product`, `kominka`, `form`, `seo` の責務で分割する
- データ取得はページまたは `lib` 層で行い、UI コンポーネント内で直接 API 呼び出しを行わない
- FAQ、商品、記事、古民家のカード・詳細部品は再利用可能な props 設計とする
- クライアントコンポーネントは、絞り込み UI、フォーム、カートドロワー、数量変更処理など必要箇所に限定する

### 7.7 問い合わせ API 設計方針

- お問い合わせフォーム送信は静的サイト外の API 層で処理する
- API 層は本リポジトリ配下の `contact-api/` ディレクトリで管理し、`DEPLOY_ENV` に応じて `ConoHa WING` の本番 / 検証環境へ配置する
- 公開サイトは `NEXT_PUBLIC_CONTACT_API_URL` に対してリクエストを送る構成とし、API 実行基盤はフロントコードから分離する
- フェーズ1では以下の構成を採用し、必要時に第2案 `Vercel Functions + Resend` へ切り替えられるようにする

| 項目 | 方針 |
|---|---|
| 実行基盤 | `ConoHa WING` 配下の `PHP` |
| エンドポイント | `POST https://<本番ドメイン>/contact-api/contact.php` または `POST https://stg.<公開ドメイン>/contact-api/contact.php` |
| スパム対策 | `honeypot`、`Origin / Referer` 検証、送信頻度制御、サーバー側バリデーション |
| 通知方法 | `ConoHa` メール機能を利用し、`SMTP` 認証を優先する |
| 通知先 | `microCMS` の `site_settings.contactEmail` を正本とする |
| 切替条件 | スパム増加、配信品質不足、保守負荷増大時は `Vercel Functions + Resend` に切り替える |

#### 問い合わせ API の採用理由

| 候補 | 評価 |
|---|---|
| `ConoHa WING + PHP + ConoHa メール` | 追加コストを抑えつつ、公開基盤と同一契約内で運用できるためフェーズ1採用 |
| `Vercel Functions + Resend` | 運用性は高いが、フェーズ1では追加基盤を増やさず、必要時の切替候補とする |
| 外部フォームサービス | 実装は軽いが、入力項目拡張・UI統合・送信制御の柔軟性が下がるため不採用 |

#### 切替可能構成の設計ルール

| 項目 | 固定するもの | 切替可能なもの |
|---|---|---|
| フロント実装 | `NEXT_PUBLIC_CONTACT_API_URL` を参照する送信処理 | API の実 URL、配備先環境 |
| リクエスト仕様 | `category`, `name`, `email`, `phone?`, `message`, `privacyConsent`, `honeypot?`, `recaptchaToken?` | バックエンド実装言語 |
| レスポンス仕様 | `ok`, `message`, `errorCode` を返す JSON | 実行基盤、通知サービス |
| 通知先管理 | `site_settings.contactEmail` を正本にする | 送信手段、送信元アドレス |

#### 問い合わせ API の基本仕様

| 項目 | 方針 |
|---|---|
| 許可オリジン | 本番ドメイン、ステージングドメイン、ローカル開発環境のみ |
| メソッド | `POST`, `OPTIONS` |
| ペイロード | `category`, `name`, `email`, `phone?`, `message`, `privacyConsent`, `honeypot?`, `recaptchaToken?` |
| バリデーション | クライアント側は `React Hook Form` + `Zod`、サーバー側は `PHP` で再検証する |
| レート制御 | IP / User-Agent 単位で一定時間内の送信回数を制限し、`contact-api/var/<environment>/rate-limit/` へファイル保存する |
| ログ | 送信成功 / 失敗、バリデーション失敗、スパム判定、メール送信失敗を `contact-api/var/<environment>/logs/` へ日次ファイルで記録する |
| 通知先取得 | 送信時に `microCMS` の `site_settings.contactEmail` を取得し、未設定時は設定不備としてエラー記録する |
| 検証動作 | `DEPLOY_ENV=staging` の `ConoHa WING Staging` で実送信確認する |
| Previewアプリ | `preview/` では下書き確認を主目的とし、問い合わせ送信の本番相当試験は行わない |
| フォールバック | API 障害時は代替連絡先を画面表示する |

### 8.5 障害時の方針

- ビルド失敗時はデプロイを中止し、直前の公開ファイルを維持する
- `microCMS` または `Shopify` の API 障害時はビルド失敗として扱い、公開中サイトを差し替えない
- 問い合わせ API 障害時はフロント側で失敗メッセージを返し、代替連絡先を表示する
- `ConoHa` 側のメール送信失敗時は API ログに記録し、送信リトライは手動運用を基本とする
- `Shopify` クライアントサイドフェッチ（カート API 等）障害時はカート操作を非活性にし、`Shopify` ストアへの直接リンクをフォールバックとして表示する
- `site_settings.contactEmail` が未設定の場合は問い合わせ送信を失敗扱いとし、管理画面側の設定不備として解消する

### 8.6 下書き確認・検証確認

- 依頼者レビュー用のモック確認は `preview/` ではなく `web_mock/` で行う
- `web_mock/` はダミーデータによる静的モックとし、実データや問い合わせ送信は扱わない
- `microCMS` の下書き確認は本番公開サイトでは行わない
- 運営者向けに `Vercel` 上の `preview/` 別アプリを用意する
- `microCMS` のプレビューURLは `preview/` アプリの preview ルートへ接続する
- `preview/` アプリは `noindex` 設定とアクセス制限を適用する
- 本番反映前の最終確認は `develop` を元にした `ConoHa WING Staging` で行う
- 問い合わせフォームの実送信確認と複数商品カート確認は `ConoHa WING Staging` で行う

## 9. SEO・セキュリティ実装方針

### 9.1 SEO 実装方針

| 項目 | 実装方針 |
|---|---|
| metadata | `generateMetadata` でページ単位に出力する |
| canonical | `NEXT_PUBLIC_SITE_URL` を基準に、末尾スラッシュありで生成する |
| OGP | CMSまたは共通設定から画像と文言を取得する |
| sitemap | ビルド時に生成し、末尾スラッシュありで統一する |
| robots.txt | ビルド成果物に含める。`production` は `Allow: /` と `Sitemap` を出力し、`staging` は `Disallow: /` を出力する |
| 構造化データ | `lib/schema` に集約し、ページごとに出力する |

### 9.2 構造化データ出力方針

| 対象 | 型 |
|---|---|
| 全ページ共通 | `WebSite`, `Organization` |
| パンくず表示ページ | `BreadcrumbList` |
| 商品詳細 | `Product`, `Offer` |
| ストーリー詳細 | `Article` |
| FAQ | `FAQPage` |
| 古民家 | `LocalBusiness`（日帰り体験のみのため確定。宿泊提供が確定した場合は `LodgingBusiness` に変更する） |

### 9.3 セキュリティ実装方針

- セキュリティヘッダーは静的ホスティングに合わせて `.htaccess` または配信設定で付与する
- 問い合わせ API では `honeypot`、許可オリジン検証、送信頻度制御、送信内容のサーバー側バリデーションを必須とする
- 問い合わせログと送信頻度制御ファイルは公開ディレクトリ外の環境別保存先へ配置する
- スパム流入が増加した場合は、第2案として `Vercel Functions + Resend` と外部 CAPTCHA の導入へ切り替え可能な構成を維持する
- 秘匿情報は環境変数のみで管理し、リポジトリへ含めない

### 9.4 アクセシビリティ実装方針

要件定義書 §8.3 の WCAG 2.1 AA 準拠目標に対して、以下の実装方針とする。

| 項目 | 実装方針 |
|---|---|
| キーボード操作 | フォーカス順序を論理的に保持し、`Tab` キーで主要導線へ到達できること |
| スクリーンリーダー | `aria-label`、`aria-expanded`、`alt` テキストを適切に付与する |
| コントラスト比 | テキストとその背景のコントラスト比は 4.5:1 以上を確保する |
| フォーム | 入力フィールドに `<label>` を紐付け、エラーメッセージは `aria-describedby` で関連付ける |
| 画像 | 装飾的な画像は `alt=""` を設定し、情報を持つ画像には意味のある `alt` テキストを付与する |
| 動的コンテンツ | メニューの開閉など動的に変化する UI には `aria-expanded` / `aria-controls` を使用する |

## 12. 開発ロードマップ

段階的に確認と実装を進め、各段階で依頼者確認を挟む。フェーズ1で `web_mock/` によるデザイン方向を固め、以降はその承認済みモックを土台に実装を進める。

| 段階 | 目的 | 主な作業 | 完了条件 |
|---|---|---|---|
| フェーズ1: モック作成 | デザイン確認 | `web_mock/` にダミーデータで主要画面のモックを作成し、トップ、商品一覧、商品詳細、古民家、お問い合わせの見た目と導線を確認する | 依頼者からデザイン方向の承認を得る |
| フェーズ2: モック修正 | UI確定 | `web_mock/` にフィードバックを反映し、配色、タイポグラフィ、余白、コンポーネント粒度、ナビゲーション構成を確定する | 再修正が小規模な範囲に収まる状態にする |
| フェーズ3: 静的テンプレート実装 | 画面骨格の実装 | 承認済み `web_mock/` を `web/` の `Next.js` コンポーネントへ落とし込み、共通レイアウト、テンプレート、ルーティング、法務ページを実装する | 全ページが静的ダミーデータで遷移可能になる |
| フェーズ4: データ連携実装 | CMS / EC 連携 | `microCMS`、`Shopify` 連携、一覧・詳細生成、SEOメタデータ、構造化データ、`preview/` 別アプリの下書き確認導線を実装する | 実データと下書き確認の両方が表示できる |
| フェーズ5: 問い合わせ・運用実装 | 運用機能の完成 | `ConoHa PHP API`、メール送信、送信頻度制御、複数商品カート、検証環境確認、`DEPLOY_ENV` 切替を含む ConoHa デプロイフローを実装する | 問い合わせとカートを含むフェーズ1対象機能が一通り動作する |
| フェーズ6: 総合確認・公開準備 | リリース判定 | 総合テスト、Lighthouse確認、SEO確認、運用手順書整備、公開判定を行う | 本番公開のGo判断ができる |

### 12.1 フェーズごとの確認ポイント

- フェーズ1では `web_mock/` によるデザインの方向性と導線の妥当性を優先し、実データ連携は行わない
- フェーズ2では依頼者の修正依頼を反映し、以後の実装で戻りが発生しにくい状態にする
- フェーズ3では承認済み `web_mock/` と `web/` 実装の差分を最小化する
- フェーズ4以降は `microCMS` と `Shopify` の接続確認を段階的に進め、データ責務の混在を避ける
- フェーズ4では `preview/` 別アプリの server-side runtime 確認を含める
- フェーズ5では `ConoHa WING Staging` で問い合わせ送信と複数商品カート確認を実施する
- フェーズ6でスパム量や配信品質に課題が出た場合、第2案 `Vercel Functions + Resend` への切替判断を行う

### 12.2 第2案への切替トリガー

- `ConoHa` メール送信の到達率に継続的な問題がある
- 問い合わせスパムが増加し、現行の `honeypot` と送信頻度制御だけでは対応が難しい
- API ログ、障害調査、運用保守の負荷が開発体制に対して重い
- ステージングと本番で問い合わせ API の差分管理が負担になり、外部実行基盤の方が妥当と判断した
