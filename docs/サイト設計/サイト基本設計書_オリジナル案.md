## 1. 基本方針

### 1.1 設計前提

- 本設計は `docs/要件定義/サイト要件定義書_オリジナル案.md` v1.3.1 を上位要件とし、開発進行は `docs/ロードマップ/開発ロードマップ_オリジナル案.md` v1.3.1 に従う
- 公開サイトは `web/` の `Next.js App Router` を継続利用し、`Next.js Static Export` により静的成果物として生成する
- 配信先は `ConoHa WING` の本番 / 検証環境を基本とする
- デザインは `web_mock/` の既存モックを公開サイトへ移植し、ブランドサイトとしての表現力と自由度を優先する
- ブログ・お知らせは `Notion` を投稿CMSとして採用し、自前の `Next.js` 変換レイヤーで公開サイト用データへ変換する
- ECは `Shopify Storefront API` を利用するヘッドレスECとし、商品表示、商品カテゴリ、バリエーション選択、サイト内カート、Shopify Checkout導線を `web/` 側で実装する
- 商品、価格、在庫、コレクション、決済、注文、配送、返品条件は Shopify を正本とする
- 問い合わせフォームは Static Export 制約に合わせ、初期は `ConoHa WING` 配下の `PHP` 問い合わせAPIと `ConoHa メール / SMTP` で処理する
- `DecapCMS` は採用しない。SEO補助情報もNotion記事プロパティ、Shopify商品SEO、静的設定で管理する
- Notion Webhookによる即時反映は初期対象外とし、GitHub Actions の定期実行と手動 `workflow_dispatch` による再ビルドを基本とする

### 1.2 システム構成概要

```txt
利用者ブラウザ
  ↓
ConoHa WING Production / Staging
  ├─ web/ Static Export 成果物を配信
  └─ contact-api/ PHP API を実行
       └─ ConoHa メール / SMTP で通知

web/ Next.js App Router
  ├─ 静的ページ、ブログ、商品、カートUIを描画
  ├─ Notion Database / Page / Block をビルド時に取得・変換
  ├─ Shopify Storefront API から商品・コレクションを取得
  └─ Storefront API のCart mutation / query と checkoutUrl でCheckoutへ遷移

Notion
  └─ ブログ・お知らせ記事を運営者がスマートフォンから作成・編集

Shopify
  ├─ Products / Collections / Metafields / Metaobjects を管理
  ├─ Cart / Checkout / Orders / Payment / Shipping を管理
  └─ Storefront API を公開サイトから利用

GitHub Repository
  ├─ GitHub Actions で build / export / deploy を実行
  ├─ schedule / workflow_dispatch でNotion更新を反映
  └─ 環境別の秘密情報は GitHub Secrets / 環境変数で管理

web_mock/
  └─ 依頼者レビュー用の静的モック
```

### 1.3 システム責務

| レイヤー | 主な責務 |
|---|---|
| `Next.js` | 画面描画、ルーティング、静的HTML生成、SEOメタデータ、構造化データ、内部リンク、カートUI |
| Notion変換レイヤー | Notion Database / Page / Block の取得、型付きデータ変換、未対応ブロック検出、画像静的アセット化 |
| Notion | ブログ・お知らせの投稿、編集、公開状態管理 |
| Shopify Storefront API | 商品、バリエーション、画像、価格、販売可否、コレクション、Cart mutation、checkoutUrl の提供 |
| Shopify Admin | 商品、価格、在庫、注文、決済、配送、返品、metafields / metaobjects の正本管理 |
| 静的データ | ブランド紹介、コンセプト、畑、古民家、法務固定ページ、サイト設定の初期正本 |
| `contact-api/` | 問い合わせ受付、サーバー側バリデーション、スパム対策、通知メール送信 |
| `web_mock/` | 依頼者向けデザイン確認、導線確認 |
| `ConoHa WING` | 静的ファイル配信、PHP問い合わせAPI実行 |

### 1.4 Static Export 制約に対する基本方針

| 項目 | 方針 |
|---|---|
| 動的ルート | `generateStaticParams` でブログ詳細、ブログカテゴリ、商品詳細、商品カテゴリをビルド時生成する |
| Notion更新 | 定期再ビルドまたは手動 `workflow_dispatch` で公開サイトへ反映する |
| Shopify商品更新 | 商品・カテゴリページはビルド時取得を基本とし、価格・販売可否・カートは必要に応じてクライアント側で最新取得する |
| 下書きプレビュー | 初期必須にしない。必要になった場合は後続で `preview/` または動的プレビュー環境を検討する |
| 問い合わせ処理 | 静的HTMLから `NEXT_PUBLIC_CONTACT_API_URL` 経由でPHP APIへ送信する |
| 画像最適化 | Notion画像はビルド時に取得し、WebP/JPEGへ変換して公開成果物に含める |
| URL正規化 | 内部リンク、canonical、sitemapを同一方針で統一する。現行設計の互換性を確認し、実装時に `trailingSlash` の最終方針を確定する |
| 障害時 | ビルド失敗時はデプロイを中止し、直前の公開成果物を維持する |

### 1.5 現行開発フェーズ

2026-04-27 時点では「フェーズ0: Notion・Shopify API設計」が未着手である。実装に入る前に、Notionのスマホ投稿体験、Notion Database設計、Notion画像最適化、Shopify Storefront API設定、商品・コレクション・metafields設計、カート/Checkout境界、再ビルド方式を確定する。

## 2. サイトマップ

```txt
/ (トップページ)
├── /about (ブランド紹介)
├── /concept (コンセプト)
├── /farm (畑紹介)
├── /blog (ブログ一覧)
│   ├── /blog/category/[category] (ブログカテゴリ一覧)
│   ├── /blog/category/news (お知らせカテゴリ一覧)
│   └── /blog/[slug] (ブログ詳細 / お知らせ詳細)
├── /products (商品一覧)
│   ├── /products/category/[handle] (商品カテゴリ一覧)
│   └── /products/[handle] (商品詳細)
├── /cart (カート)
├── /kominka (古民家紹介)
├── /contact (お問い合わせ)
├── /shipping (配送情報)
├── /returns (返品・交換)
├── /legal (特定商取引法に基づく表記)
├── /privacy (プライバシーポリシー)
├── /terms (利用規約)
└── 404.html
```

### 2.1 ルーティング設計上の注意

- ブログURLは `/blog` を正規とし、お知らせはNotion上のカテゴリ表示名を `お知らせ`、公開URL用カテゴリslugを `news` として `/blog/category/news` に統合する
- Notionのカテゴリ表示名は日本語でもよいが、公開URLに使うカテゴリslugは英数字に正規化する。お知らせは表示名 `お知らせ`、URL slug `news` を基本とする
- 初期リリースでは `/news`、`/news/[slug]` は作成しない
- ブログ詳細の `slug` は Notion Database の `Slug` を正本とし、公開後の変更は原則行わない
- 商品詳細の `handle` は Shopify Product の `handle` を正本とする
- 商品カテゴリの `handle` は Shopify Collection の `handle` を正本とする
- 商品カテゴリと商品詳細の競合を避けるため、カテゴリ一覧は `/products/category/[handle]` とする
- `/cart` はサイト内カートとして作成し、決済は Shopify Checkout の `checkoutUrl` へ遷移する
- `/cart` は静的HTMLとして生成するが、内容はクライアント側でShopify Cartを取得して表示する。SEO対象外とし、sitemapには含めない
- `/kominka/access`、`/kominka/experience`、`/faq` は初期リリースでは独立ページにせず、必要箇所のセクションとして扱う

  ├─ 関連商品 → 商品詳細
  ├─ 古民家紹介

  ├─ 施設概要 / 写真 / アクセス / 過ごし方

  └─ 商品詳細、カート、フッターから相互導線

ヘッダーにはカート件数を表示する。カート件数は Shopify Cart の状態を基準とし、未作成時は0件として扱う。

- サイトマップ
- SNSリンク

パンくずはブログ詳細、ブログカテゴリ、商品詳細、商品カテゴリ、古民家、法務ページで表示する。構造化データ `BreadcrumbList` も合わせて出力する。

### 4.5 商品一覧の絞り込み・並び順

| 項目 | 方針 |
|---|---|
| カテゴリ絞り込み | Shopify Collections を基準とし、`/products/category/[handle]` への導線と併用する |
| 価格帯絞り込み | Shopifyから取得した価格情報を用いる。ただしCheckout時点の価格を正本とする |
| 用途・タグ絞り込み | Shopify tags または metafields / metaobjects の利用を検討する |
| 並び順 | 新着順、価格昇順、価格降順、推奨順を提供する |
| 在庫絞り込み | `availableForSale` を参照し、在庫切れ商品は購入不可表示にする |

## 5. データ設計概要

### 5.1 データソース別責務

| データ領域 | 正本 | 主な利用ページ |
|---|---|---|
| ブログ記事 | Notion Database / Page | `/blog`、`/blog/[slug]`、トップ最新記事 |
| お知らせ | Notion Database のカテゴリ | `/blog/category/news`、トップお知らせ枠 |
| ブログ画像 | Notion画像をビルド時に静的アセット化 | ブログ一覧、ブログ詳細、OGP |
| 商品主データ | Shopify Products | 商品一覧、商品詳細、トップ注目商品 |
| 商品カテゴリ | Shopify Collections | 商品一覧、商品カテゴリ一覧 |
| 商品補足情報 | Shopify metafields / metaobjects | 商品詳細、FAQ、関連商品 |
| 価格・在庫・販売可否 | Shopify | 商品一覧、商品詳細、カート |
| カート | Shopify Cart | `/cart`、ヘッダー、Checkout導線 |
| 決済・注文・配送 | Shopify | Checkout以降、管理画面 |
| ブランド・畑・古民家 | 静的データ | `/about`、`/concept`、`/farm`、`/kominka` |
| 法務固定ページ | 静的データ。EC運用条件はShopifyを正本 | `/shipping`、`/returns`、`/legal`、`/terms` |
| 問い合わせ通知先 | PHP API側設定または環境変数 | `contact-api/` |
| サイト設定・SEO共通 | 静的設定 + 各データソース | 全ページ |

### 5.2 Notion Database 設計方針

| プロパティ | 型 | 必須 | 用途 |
|---|---|---|---|
| `Title` | title | 必須 | 記事タイトル |
| `Slug` | rich text または url相当の短文 | 必須 | `/blog/[slug]` のURL |
| `Status` | select | 必須 | `Draft` / `Published` |
| `PublishedAt` | date | 必須 | 公開日 |
| `UpdatedAt` | date | 任意 | 更新日。未設定時は最終編集日時を補助利用 |
| `Category` | select | 任意 | 記事カテゴリ。お知らせは `news` |
| `Tags` | multi-select | 任意 | タグ |
| `Excerpt` | rich text | 任意 | 一覧・OGP補助文 |
| `CoverImage` | files | 任意 | アイキャッチ画像 |
| `SEO Title` | rich text | 任意 | SEOタイトル。未設定時は `Title` を利用 |
| `SEO Description` | rich text | 任意 | SEOディスクリプション。未設定時は `Excerpt` を利用 |
| `RelatedProductSlugs` | rich text または multi-select | 任意 | 関連商品の Shopify handle。既存要件名に合わせて `Slugs` とするが、値はShopify Product handleを入れる |

公開対象は `Status = Published` の記事のみとする。`Published` 記事に必須項目の欠落や未対応ブロックがある場合はビルドエラーとし、`Draft` 記事は警告に留める。
`Slug` の重複、空白、URLに使えない文字、公開後の不用意な変更はビルド時または運用レビューで検出する。

カテゴリはNotion上の表示名と公開URL用slugを分離する。初期カテゴリは以下を基本とする。

| 表示名 | URL slug | 用途 |
|---|---|---|
| お知らせ | `news` | 告知、営業日、イベント等 |
| 読みもの | `story` | ブランド、畑、商品背景の読みもの |
| 商品のこと | `product` | 商品説明、飲み方、使い方 |

カテゴリ追加時は、Notion select値、URL slug、一覧ページ生成、sitemap対象、内部リンク表示名を合わせて追加する。

### 5.3 Notion Block 変換方針

初期対応ブロックは以下とする。

| ブロック | 変換方針 |
|---|---|
| paragraph | 段落として表示 |
| heading_1 / heading_2 / heading_3 | 見出し階層へ変換 |
| bulleted_list_item | 箇条書きへ変換 |
| numbered_list_item | 番号付きリストへ変換 |
| quote | 引用として表示 |
| divider | 区切り線として表示 |
| image | 静的アセット化し、`picture` または `img` で表示 |
| callout | 補足枠として表示 |
| link / rich text annotations | リンク、太字、斜体等を安全にHTML化 |

NotionのHTMLをそのまま公開せず、APIレスポンスを型付き中間データへ変換してからReactコンポーネントで描画する。

### 5.4 Shopify データ設計方針

| Shopify項目 | 用途 |
|---|---|
| `Product.id` | 商品識別 |
| `Product.handle` | `/products/[handle]` のURL |
| `Product.title` | 商品名 |
| `Product.descriptionHtml` | 商品説明 |
| `Product.images` / `featuredImage` | 商品画像 |
| `Product.priceRange` | 価格表示 |
| `Product.availableForSale` | 商品販売可否 |
| `Product.variants` | バリエーション選択、カート追加対象 |
| `ProductVariant.id` | Cart line の `merchandiseId` |
| `ProductVariant.availableForSale` | バリエーション販売可否 |
| `Product.seo` | 商品SEO補助 |
| `Product.metafields` | 原材料、飲み方、注意事項、内容量、FAQ、関連商品 |
| `Collection.handle` | 商品カテゴリURL |
| `Collection.products` | カテゴリ内商品一覧 |

商品詳細に必要な補足情報は Shopify Product metafields / metaobjects として定義する。初期利用する主な項目は以下とする。

| 項目 | namespace / key 例 | 型 |
|---|---|---|
| 原材料 | `custom.ingredients` | text / rich text |
| 飲み方 | `custom.how_to_use` | rich text |
| 注意事項 | `custom.caution` | rich text |
| 内容量 | `custom.quantity` | single line text |
| FAQ | `custom.faqs` または metaobject参照 | list / metaobject |
| 関連商品 | `custom.related_products` | product reference list |

### 5.5 データ取得タイミング

| データ | 取得タイミング | 備考 |
|---|---|---|
| 静的本文データ | ビルド時 | リポジトリ内データを参照 |
| Notion記事一覧・詳細 | ビルド時 | `Status = Published` のみ公開対象 |
| Notion画像 | ビルド時 | 期限付きURLを取得し、静的アセット化 |
| Shopify商品・コレクション | ビルド時 | 静的ページ生成に利用 |
| 価格・販売可否 | ビルド時 + 必要に応じてクライアント更新 | Checkout時点のShopify正本に従う |
| Shopify Cart | 実行時 | Storefront API Cart mutation / query を利用 |
| 問い合わせ送信 | 実行時 | PHP APIへ送信 |

### 5.6 Shopify Storefront API 利用境界

| 項目 | 方針 |
|---|---|
| API version | 実装時に固定し、環境変数または設定値で管理する。バージョン更新は別タスクとして確認する |
| Store domain | 環境変数で管理し、本番 / 検証で切り替えられるようにする |
| Storefront token | public access tokenを利用する。ブラウザ露出前提の権限に限定し、Admin API tokenとは分離する |
| ビルド時取得 | 商品詳細、商品一覧、コレクション一覧、商品カテゴリページの静的生成に利用する |
| 実行時取得 | カート作成、カート明細操作、最新販売可否確認、Checkout遷移に利用する |
| エラー処理 | `userErrors`、通信失敗、在庫切れ、販売停止、バリエーション不一致をUIで購入不可または再選択として扱う |
| キャッシュ | ビルド時取得結果は静的成果物に固定される。価格・販売可否など購入判断に関わる値はカート操作時にShopify正本で再確認する |
| sitemap | 商品・コレクションは公開対象のみ含める。`/cart`、Checkout URL、販売停止商品はsitemap対象外とする |

| 項目 | 方針 |
|---|---|

| エンドポイント | `POST https://<domain>/contact-api/contact.php` |

| スパム対策 | `honeypot`、Origin / Referer 検証、送信頻度制御、サーバー側バリデーション |
| 通知方法 | `ConoHa` メール機能を利用し、SMTP認証を優先 |
| 通知先 | PHP API側設定または環境変数 |
| ログ | 公開Webルート外に保存し、個人情報は最小限にする |

入力項目と検証方針:

| 項目 | 必須 | 検証方針 |
|---|---|---|
| 問い合わせ種別 | 必須 | 商品 / 配送 / 古民家 / その他など定義済み値のみ許可 |
| 氏名 | 必須 | 1〜50文字を目安にクライアント側・サーバー側で検証 |
| メールアドレス | 必須 | メール形式をクライアント側・サーバー側で検証 |
| 電話番号 | 任意 | 入力がある場合のみ形式と長さを検証 |
| 本文 | 必須 | 最大1,000文字を目安とし、制御文字や過剰なURLをスパム判定に利用 |
| プライバシー同意 | 必須 | 同意がない送信は受け付けない |
| `honeypot` | 任意 | 値が入っている場合はbotとして拒否 |

初期リリースでは問い合わせ本文をログへ原則保存しない。障害調査に保存が必要な場合も保存範囲を最小化し、問い合わせログは90日、送信頻度制御情報は7日を目安に削除する。

| Shopify Admin API token | 初期利用しない。将来利用時もブラウザへ公開しない |
| Webhook secret | 後続導入時のみ環境変数で管理 |
| 問い合わせ通知先 / SMTP情報 | PHP API側設定または環境変数で管理 |

## 8. 画像最適化・画像SEO設計

| 項目 | 方針 |
|---|---|
| 入力画像 | Notionアップロード画像、静的素材、Shopify商品画像 |
| Notion画像URL | 期限付きURLを公開HTMLへ直接埋め込まず、ビルド時に取得して静的アセット化する |
| 公開形式 | 本文・一覧・サムネイルは WebP を主形式とし、必要に応じて JPEG フォールバックを生成する |
| OGP画像 | SNS互換性を優先し、1200x630 の JPEG または PNG を生成・指定する |
| サイズ | 480 / 768 / 1200 / 1600px 程度の複数幅を用途別に生成する |
| 圧縮 | WebP quality 75〜82を目安にし、見た目と容量のバランスを確認する |
| `srcset` | 生成済み画像を `srcset` で出し分ける |
| alt | Notionキャプション、専用プロパティ、商品画像alt、文脈から生成する |
| ファイル名 | slug、用途、連番を含む説明的なkebab-case名にする |
| HTML | 本文・主要画像はCSS背景ではなく、`picture` または `img` で表示する |
| CLS対策 | width / height またはアスペクト比を指定する |
| 遅延読み込み | ファーストビュー外は `loading="lazy"` を基本とする |
| HEIC | 初期は非推奨。処理できない場合はビルドエラーとしてJPEG再アップロードを依頼する |

変換済み画像は `public/generated/notion/` などの生成物ディレクトリへ配置し、ビルド成果物に含める。Shopify商品画像はShopify CDN URLを利用するが、表示サイズ、alt、構造化データ、OGP利用時の互換性を確認する。

## 9. デプロイ・運用設計

### 9.1 デプロイ先

| 環境 | 配置先 | 役割 |
|---|---|---|
| 本番 | `ConoHa WING` 本番ドキュメントルート | 公開環境、PHP問い合わせAPI |
| 検証 | `ConoHa WING Staging` | Notion反映、Shopify商品・カート・Checkout、問い合わせ確認 |
| モック | `web_mock/` 確認URL | 依頼者向けデザイン確認 |

### 9.2 ビルド・デプロイフロー

```txt
web_mock/
  ↓
build
  ↓
依頼者確認URLへ反映
```

```txt
schedule / workflow_dispatch / push
  ↓
GitHub Actions
  ↓
環境変数・Secretsを読込
  ↓
Notion記事取得・変換・画像静的アセット化
  ↓
Shopify商品・コレクション取得
  ↓
web/ build (Static Export)
  ↓
out/ 生成 + contact-api/ 同梱
  ↓
ConoHa WINGへアップロード
```

### 9.3 再ビルドトリガー

| トリガー | 実行内容 |
|---|---|
| `schedule` | Notion記事更新を定期反映する |
| `workflow_dispatch` | 運営または開発者が手動で再ビルド・再デプロイする |
| `push` | コード、静的データ、設定変更を反映する |
| Notion Webhook | 初期対象外。即時反映が必要になった場合のみ追加検討 |
| Shopify商品更新 | 初期は手動または定期再ビルドで反映。即時性が必要な場合は後続でWebhook等を検討 |

### 9.4 障害時の方針

- Notion取得、Shopify取得、画像変換、ビルドのいずれかに失敗した場合はデプロイを中止する
- 直前の公開成果物は維持し、壊れた成果物を本番へ配信しない
- `Published` 記事の必須項目欠落、未対応ブロック、画像変換失敗はビルドエラーとする
- Shopify API障害時は、既存公開成果物を維持する。カート操作時の障害は購入不可メッセージと問い合わせ導線を表示する
- Checkout URL取得後の決済・注文障害はShopify側の管理範囲とし、ステータスと注文通知を確認する
- 問い合わせAPI障害時は送信失敗メッセージと代替連絡先を表示する

## 10. SEO・セキュリティ実装方針

### 10.1 SEO 実装方針

| 項目 | 実装方針 |
|---|---|
| metadata | `generateMetadata` でページ単位に出力する |
| canonical | `NEXT_PUBLIC_SITE_URL` を基準に正規URLを生成する |
| OGP | Notion記事プロパティ、Shopify商品SEO、静的設定から画像と文言を取得する |
| sitemap | ビルド時に生成し、静的ページ、ブログ、商品、カテゴリを含める。`/cart`、Checkout URL、ステージングURL、販売停止商品は含めない |
| robots.txt | `production` は公開、`staging` と `web_mock` は noindex / Disallow 方針とする |
| 構造化データ | `lib/schema` などに集約し、ページごとに出力する |
| 画像SEO | 標準HTML画像要素、説明的ファイル名、alt、画像周辺テキストを整備する |

### 10.2 構造化データ出力方針

| 対象 | 型 |
|---|---|
| 全ページ共通 | `WebSite`, `Organization` |
| パンくず表示ページ | `BreadcrumbList` |
| ブログ詳細 | `Article` |
| 商品詳細 | `Product`。`Offer` はShopify価格を元に出力し、販売可否は `availableForSale` を参照する |
| 古民家 | `LocalBusiness`。宿泊提供が明確な場合のみ `LodgingBusiness` を再検討する |
| FAQ掲載箇所 | 条件が整う場合のみ `FAQPage` を出力する |

### 10.3 セキュリティ実装方針

- Notion API token、Webhook secret、Shopify Admin API token、SMTP情報はリポジトリへ含めない
- Shopify Admin API token はブラウザに公開しない
- Storefront API public tokenなど公開可能な値のみ `NEXT_PUBLIC_` を付ける
- 問い合わせAPIでは `honeypot`、Origin / Referer 検証、送信頻度制御、サーバー側バリデーションを必須とする
- 問い合わせログと送信頻度制御ファイルは公開Webルート外に配置する
- カード情報、決済情報、注文管理情報はサイト側に保持しない
- セキュリティヘッダーは `.htaccess` または配信設定で付与する

初期リリースで付与するセキュリティヘッダーの基本方針:

| ヘッダー | 方針 |
|---|---|
| `X-Frame-Options` | `SAMEORIGIN` を基本とする |
| `X-Content-Type-Options` | `nosniff` を設定する |
| `Referrer-Policy` | `strict-origin-when-cross-origin` を基本とする |
| `Permissions-Policy` | 不要なブラウザ機能を無効化する方針で詳細設計時に対象を確定する |
| `Content-Security-Policy` | Notion生成画像、Shopify CDN、GA4、外部予約、地図等の利用先を洗い出して段階導入する |

### 10.4 GA4 計測方針

`GA4` は `NEXT_PUBLIC_GA_MEASUREMENT_ID` が設定されている環境のみで有効化する。Cookie とアクセス解析の利用方針は `/privacy` に明記する。

| イベント | 発火タイミング |
|---|---|
| `view_item` | 商品詳細表示 |
| `select_item` | 商品カードまたは注目商品クリック |
| `add_to_cart` | カートへ追加 |
| `begin_checkout` | Shopify Checkout へ遷移開始 |
| `generate_lead` | お問い合わせ送信完了 |
| `click_reservation` | 古民家の外部予約リンククリック |
| `view_article` | ブログ詳細表示 |

`purchase` は Shopify Checkout 側のGA4 / Shopify連携で扱い、サイト側で注文完了計測を独自実装しない。

### 10.5 薬機法・景品表示法への対応方針

- 商品説明、ブログ、SEO文案、AI生成文は、薬機法・景品表示法・健康効果表現・ブランドトーンの観点で人間が確認してから公開する
- 医薬的効能を断定する表現、体質改善や治療効果を保証する表現は避ける
- Notionで公開された記事もビルド前レビューまたは運用ルールにより表現確認を行う

## 13. 制約・注意点

- Static Export 前提のため、Notion更新やShopify商品更新は再ビルドまで公開HTMLへ反映されない
- 価格・販売可否はビルド時点と閲覧時点で差分が生じる可能性があるため、カート追加やCheckout時点ではShopify正本を参照する
- Notion画像URLは期限付きであるため、公開HTMLへ直接埋め込まない
- Notionの未対応ブロックが増えるとビルド失敗の原因になるため、運用マニュアルで利用可能ブロックを明示する
- Shopify Storefront API public tokenは公開可能な前提だが、Admin API tokenとは厳密に分離する
- Shopify Checkout以降の画面デザイン、決済、注文通知、配送設定はShopify側の制約と管理画面設定に従う
- 問い合わせAPIはPHP実行環境とメール送信品質に依存するため、ステージングで実送信相当の確認を行う
- 薬機法・景品表示法に関わる表現は、Notion運用時も公開前確認の対象にする
